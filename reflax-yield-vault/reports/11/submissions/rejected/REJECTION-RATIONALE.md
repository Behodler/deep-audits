# Rejected / Downgraded Findings — reflax-yield-vault-11

These findings were generated by the analysis pipeline at High/Medium severity and
subsequently **rejected or downgraded on manual review**. The pipeline over-weighted
owner privilege and relied on PoCs whose mocks decoupled from real on-chain behaviour.

Trust model context: reflax-yield-vault is a **self-owned, all-protocol-owned-client**
system. The `owner` is the protocol itself; clients are protocol-controlled accounts.
"Owner can move client funds to the owner" is the designed migration behaviour, not an
attack. Owner-gated actions whose funds flow to the owner are **centralization**
considerations, not High/Medium severity vulnerabilities.

---

## H-01 — emergencyWithdraw accounting desync → Centralization (folded into C-01)

`_emergencyWithdraw` (ERC4626MarketYieldStrategy.sol L386-395) transfers vault shares to
`owner()` without decrementing `clientBalances` / `totalDeposited`. Real, but:
- Only the trusted owner can call it (`onlyOwner`).
- Funds flow to the owner "for manual redistribution" — the same pattern as `totalWithdrawal`.
- "Permanent insolvency" only manifests if the protocol keeps operating normally after an
  emergency exit and the owner never redistributes — an owner-trust assumption.

**Disposition:** legitimate hardening note (the desync is a latent footgun if a *partial*
emergency withdraw is followed by continued operation). Folded into **C-01** as an
open hardening recommendation. Not a standalone High.

## H-02 — _totalWithdraw live-balance read → INERT (residual already L-06)

`_totalWithdraw` (L404-435) ignores the Phase-1 cached `amount` parameter and reads live
`clientBalances[token][client]`. Claimed "6x silent over-extraction" is **circular**: the
owner funds the extra via `depositAsOwner` (their own tokens) and withdraws it back to
themselves; the only "extra" swept is the client's own legitimately-recorded principal,
which `totalWithdrawal` is *designed* to send to the owner anyway. Reading the live balance
is arguably *more correct* for a migration than a stale snapshot.

The "underflow DoS" path is **unreachable**: every deposit increments `clientBalances` and
`totalDeposited` by the same delta (L320-321) and every withdrawal decrements both together,
so `clientBalances[client] <= totalDeposited` holds by construction — `totalDeposited -=
clientStoredBalance` can never underflow. The Halmos "proof" treated the two as independent
free symbols (a spurious symbolic artifact).

**Disposition:** invalid as High. Only real residual is the `WithdrawalExecuted` event
emitting the cached (not actual) amount — **already tracked as L-06**. No new entry.

## H-03 — withdrawAsOwner timelock bypass → Centralization (folded into C-01)

`withdrawAsOwner` (L279-281) drains a client to any recipient with no 24h timelock. But the
owner already holds two other escape hatches to the same funds (`totalWithdrawal` after 24h,
`emergencyWithdraw` immediately), so the "anti-rugpull timelock" is already cosmetic by
design. In an owner-trusted model this is a centralization property, not a High.

**Disposition:** folded into **C-01** as an acknowledged by-design centralization note.

## M-02 — ERC4626 vault-price donation DoS → FALSE POSITIVE

A donation of USDe to the sUSDe vault is **genuine yield** — equivalent to the vault earning
interest — and benefits every sUSDe holder including the strategy. It is:
- **Non-recoverable** (a direct underlying transfer to a 4626 vault mints the donor nothing),
  hence value-positive for the protocol and self-defeating as an attack.
- **Directionally wrong on deposit**: a higher share price makes `convertToShares(amount)`
  return *fewer* shares, lowering `minOut` — deposits get easier, not harder.
- **Transient at worst on withdraw**: `minOut` and the Curve sUSDe→USDe output both rise with
  the share price; they only diverge if the AMM price decouples from the vault price and stays
  decoupled — closed by arbitrage within blocks, and prevented entirely by a rate-oracle NG pool.

The PoC only "passed" because its mock AMM was hard-coded to a fixed 1:1 rate while the vault
price moved 10x — an unrealistic decoupling.

**Disposition:** rejected (false-positive).

## M-01 — slippage tolerance boundaries → Downgraded to Low

- MAX_BPS sub-case (`setSlippageTolerance(10000)` → zero principal credit) is owner-power →
  noted in **C-01**.
- Zero-default sub-case (withdrawals revert until `setSlippageTolerance` is called once) is a
  real but minor **deploy-ordering footgun**.

**Disposition:** net **Low**, carried in the QA bundle. The earlier Low→Medium upgrade of
ledger entry L-01 is reverted.
