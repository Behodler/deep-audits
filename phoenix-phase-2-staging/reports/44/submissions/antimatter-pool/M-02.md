## Finding description and impact

### Severity

**Medium.** No protocol funds move: the 2,258.93 LP slice stays on OWNER, unconverted. The impact is on protocol function and integrity. Every automated gate in Script B's pipeline passes on a mainnet cutover that never happened: the resume gate, the in-script post-conditions, `:verify` and the address-book patcher. The patcher then writes the attacker-created AM/sUSDS pair into the address book as the protocol's seeded pool. The pair address itself is the deterministic canonical AM/sUSDS pair. The harm is not a wrong address. The harm is that a pair the attacker created and priced is certified as the protocol's seeded pool, and Script C's ordering guard is satisfied, even though that guard exists to stop C until B has really landed.

The precondition is the same as M-01: **Script A must be broadcast before Script B**, which the runbook sanctions (`docs/SyaAntimatterMainnetCutover.md` L15). The attacker also needs AM and sUSDS, and must act inside the tx1-to-tx5 window.

The evidence splits into two parts:
- **PROVEN (fork PoC):** the seed is forced to revert, the resume "completes" after only the revoke, the production verifier passes, and the **real** node patcher exits 0 and FILLs `AntimatterSusdsPair = 0xb6da5138C761Eb7a3Ef7030212bfc9e2EAB8a4DA`. That is the canonical AM/sUSDS pair, which the attacker created and priced, and which the protocol never seeded.
- **INFERRED, not executed:** that Script C (`uniswap-helper`) would then proceed and deploy UniswapHelper with AM routes over the attacker-priced pair. The basis is C's ordering guard ([`script/DeployUniswapHelperMainnet.s.sol#L205-L220`](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/script/DeployUniswapHelperMainnet.s.sol#L205-L220); story-122 L148). The guard requires book `AntimatterSusdsPair != 0`, `== factory.getPair(AM, sUSDS)`, and code at that address, and the spoofed book satisfies all three. The helper resolves `amPair()` lazily (see the NatSpec at `script/DeployUniswapHelperMainnet.s.sol` L202-204), so the guard is the only thing that stops C from running before B has really landed. No Script C run was performed in this audit.

The classifier recorded a possible downgrade to Low for human review. Those arguments are: the profitable strategy is M-01, not this one; a tx5 revert is loud; and the Script C step is inferred. The downgrade was weighed when the whole downstream chain was still inferred. The book-poisoning step is now proven, and only Script C acting on the entry remains inferred. Re-weigh to Low if Script C gains a chain-anchored pair check or the runbook requires pair inspection after a tx5 revert.

### Description

Step 0 of `CutoverAntimatterPoolMainnet` treats an existing AM/sUSDS pair as "seed already done" if two things hold: the recorded seeder has code, and OWNER holds **any** balance of the pair's LP ([CutoverAntimatterPoolMainnet.s.sol#L262-L268](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/script/CutoverAntimatterPoolMainnet.s.sol#L262-L268)):

```solidity
if (existing != address(0)) {
    require(
        p.seeder != address(0) && p.seeder.code.length > 0 && IERC20(existing).balanceOf(OWNER) > 0,
        "Step 0: the AM/sUSDS pair ALREADY EXISTS and this cutover did not create it - ABORT (griefing risk R1, story 113). Do not seed into a pair someone else created; investigate first."
    );
    seedDone = true;
    console.log("  pair exists and OWNER holds its LP: seed already done (resume)", existing);
```

The gate checks nothing that ties the pair to *this* seed. It does not compare OWNER's LP with the recorded `liquidity` or with the pair's supply, it does not compare the pair's AM reserve with the AM minted, and it does not check `p.seeded` against the chain. Even a `p.seeded` check would not help: the seed record is written during forge's **local pass**, before any transaction lands ([#L364-L367](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/script/CutoverAntimatterPoolMainnet.s.sol#L364-L367), persisted at [#L399-L401](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/script/CutoverAntimatterPoolMainnet.s.sol#L399-L401)):

```solidity
(p.amMinted, p.liquidity) = seeder.seed(p.lpAmount, minP, minS, OWNER, block.timestamp + SEED_DEADLINE);
_end();
seededThisRun = true;
p.seeded = true;
```

```solidity
// Persist the seed record now (broadcast only), so a run that dies before the revoke keeps it.
p.amPair = pairNow;
_writeProgress(p, "in_progress");
```

The PoC asserts that after the local pass the progress file already says `deploymentStatus: "completed"` and `cutover.seeded: true`.

The attacker can **cause** the crash that leads to a resume. As in M-01, tx1 publicly reveals the cutover at least four blocks before tx5. If the attacker prices the pair AM-**dear** inside that window, `_requireFullConsumption` makes tx5 revert ([AntimatterPoolSeeder.sol#L230-L233](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/src/periphery/AntimatterPoolSeeder.sol#L230-L233)):

```solidity
uint256 susdsRequired = amAmount * rSusds / rAm;
if (susdsRequired > susdsAvailable) {
    revert AntimatterNotFullyConsumed(amAmount, susdsRequired, susdsAvailable);
}
```

`--slow` stops, so tx6 (the revoke) is never sent. The first resume aborts at Step 0, because OWNER holds no LP of the attacker-created pair. Once the attacker sends OWNER **1 wei** of its LP, the next resume takes the `seedDone` branch, sends only the revoke and writes `completed`.

Downstream, nothing catches this. `VerifyAntimatterPoolCutover` checks, on live state, only that the reserves are non-zero and OWNER's LP is non-zero ([VerifyAntimatterPoolCutover.s.sol#L64-L67](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/script/VerifyAntimatterPoolCutover.s.sol#L64-L67)):

```solidity
(uint112 r0, uint112 r1,) = IAmCutoverPair(pairAddr).getReserves();
require(r0 > 0 && r1 > 0, "verify: AM/sUSDS reserves are zero");
uint256 ownerLp = IERC20(pairAddr).balanceOf(OWNER);
require(ownerLp > 0, "verify: OWNER holds no AM/sUSDS LP");
```

Its seed-record checks (L72-76) compare the record only with itself, and the record holds the simulated figures. The patcher's `completed && seeded` gate ([`scripts/patch-mainnet-addresses-antimatter-pool.js#L73-L76`](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/scripts/patch-mainnet-addresses-antimatter-pool.js#L73-L76)) is satisfied by the same local-pass record:

```js
if (p.deploymentStatus !== 'completed') {
    fail(2, `deploymentStatus is "${p.deploymentStatus}", expected "completed" (broadcast not finished - resume it)`);
}
if (!p.cutover || p.cutover.seeded !== true) fail(2, 'cutover.seeded is not true in the progress file (the seed did not complete)');
```

**Attack path:**
1. Script A is broadcast first. The attacker holds AM and sUSDS.
2. Script B tx1 through tx4 land. The attacker creates the AM/sUSDS pair at 1 AM : 10 sUSDS (AM-dear).
3. tx5 reverts `AntimatterNotFullyConsumed`, `--slow` stops, and tx6 is never sent.
4. The operator re-runs `:broadcast`, as the runbook instructs. Step 0 aborts (and the seeder is still an approved minter; see antimatter-pool L-01 (pps44l1)).
5. The attacker transfers 1 wei of its pair LP to OWNER.
6. The operator re-runs `:broadcast` again. Step 0 sees seeder code and OWNER LP > 0, takes the `seedDone` branch and sends only the revoke. The progress file says `completed` / `seeded=true`. The patcher FILLs the attacker-created (canonical) pair as the seeded pool. `:verify` passes, and so would Script C's ordering guard. The tax ledger records a conversion that never happened.

### Impact

From fork block 26303964 (dedicated PoC `test_PoC_M02_dustLpSpoofsCompletedCutover`; exploratory `test_r44_04`):

- **tx5 reverts exactly** with `AntimatterNotFullyConsumed(2457703431673592711190, 24577034316735927111900, 2077157261663097322856)` (selector `0x80a5a897`): 2,457.70 AM needs 24,577.03 sUSDS at the attacker's ratio, and only 2,077.16 sUSDS is available.
- **The first resume reverts at Step 0** with `"Step 0: the AM/sUSDS pair ALREADY EXISTS and this cutover did not create it - ABORT ..."`.
- **After 1 wei of attacker LP is sent to OWNER, the second resume "completes":** `txCount == 1` (the revoke only), `seededThisRun == false`, and the progress file has `deploymentStatus: "completed"`, `cutover.seeded: true`, `cutover.amMinted: 2457703431673592711190` (a phantom figure) and `contracts.AntimatterSusdsPair.address: 0xb6da…a4DA` (the canonical pair, which the attacker created and priced).
- **The cutover did nothing:** 2,258.927005521607781703 phUSD/sUSDS LP sits unconverted on OWNER, and the cutover minted no AM. OWNER's "AM/sUSDS LP" is the attacker's 1 wei.
- **The real patcher** (`scripts/patch-mainnet-addresses-antimatter-pool.js`, run via ffi against a scratch copy of `mainnet-addresses.ts`) exits 0 and prints:
  ```
  FILL     AntimatterPoolSeeder <- 0xdb706310C4c59527E25f6D7F3c20196eBc1409BE
  FILL     AntimatterSusdsPair <- 0xb6da5138C761Eb7a3Ef7030212bfc9e2EAB8a4DA
  ```
- **The production `VerifyAntimatterPoolCutover` PASSES** when it reads that patched book (no override), on a cutover that never seeded.
- **Inferred:** Script C's ordering guard (`DeployUniswapHelperMainnet.s.sol` L205-220) is satisfied by the certified book entry. The next script in the runbook would therefore deploy UniswapHelper's AM routes over a pair whose price the attacker set, while the protocol's liquidity was never added.

The attacker gains nothing directly (a profit-seeker would run M-01 instead). The harm is a false-green pipeline: a cutover that did not happen is reported, verified and committed as done.

### Prior disclosure (disclosed; strengthened, and the disclosure understated it)

story-122 records this as **`[medium]`** (Auto-Completed, L370): *"Script B step-0 resume branch is weaker than a fresh run: accepts any existing AM/sUSDS pair if the recorded seeder has code and OWNER holds any LP of it ... Crashed broadcast + griefer dust LP could make resume "complete" without seeding. Hardening (require p.seeded or compare to a recorded pair) is a follow-up code change."* Review item 4 (L331) adds: *"This needs both a mid-broadcast crash and active griefing, and the private-RPC recommendation reduces it further."*

What the disclosure got wrong or understated:
1. **The crash need not be accidental.** The attacker induces it with an AM-dear pair created after tx1. story-113 L464 already disclosed the AM-dear revert grief (`[low] R1: residual two-sided "AM dear" grief`), but neither story connected it to the Step-0 resume branch.
2. **The private RPC does not reduce it.** tx1 through tx4 are mined publicly before tx5 (see M-01).
3. **Neither hardening proposed in story-122 L370 ("require p.seeded or compare to a recorded pair") would work:**
   - **`require p.seeded` fails.** `seeded=true` is written during forge's local pass, before any transaction lands (PoC-asserted). story-122 L371 discloses this local-pass write as a `[low]`. What it misses is that the write defeats the story's own proposed `require p.seeded` hardening.
   - **Comparing with `seeder.amSusdsPair()` fails.** As the story itself notes, that is a `factory.getPair` view, so it returns whatever pair exists.
   - **Comparing with a recorded pair (`p.amPair`) fails too.** UniswapV2 pair addresses are CREATE2-deterministic, so the local-pass record already names the address the attacker later creates (PoC: `assertEq(pair, PREDICTED_PAIR)`; story-122's own preview evidence at L242 shows `AntimatterSusdsPair (simulated): 0xb6da5138C761Eb7a3Ef7030212bfc9e2EAB8a4DA`).
4. **The story missed that the patcher passes.** story-122 noted that Step 9 would still pass (L331), and that the verifier checks the seed record only against itself (L330(b), L371). It relied on "zero-exit-only patchers" as the mitigation (L371). It did not note that the dust-LP resume exits 0. The patcher therefore FILLs the book, and Script C's ordering guard (`script/DeployUniswapHelperMainnet.s.sol` L205-220) is satisfied.

## Recommended mitigation steps

**Interim (operational): broadcast Script B before Script A.** Before A, no third party holds AM, and minting LP into the pair with sUSDS alone reverts (`test_r44_13`). The attacker can then neither force the AM-dear revert nor obtain LP to dust OWNER with. After a tx5 revert, the runbook should also require the operator to inspect the AM/sUSDS pair's creator, reserves and LP distribution before any resume, and to stop rather than resume if the pair is foreign.

**Code fix: on resume, require chain evidence of THIS seed.** A progress record written in the local pass must never count as proof that a transaction landed. Options, strongest first:
- Record the seed transaction hash, read from `broadcast/.../run-latest.json` after the fact, and check its receipt and `Seeded` event.
- Anchor the gate to chain state and the recorded figures together, for example:
  ```solidity
  uint256 ownerLp = IERC20(existing).balanceOf(OWNER);
  require(
      p.seeder != address(0) && p.seeder.code.length > 0
          && p.liquidity > 0 && ownerLp >= p.liquidity                        // OWNER LP >= recorded liquidity > 0
          && ownerLp * 100 >= IERC20(existing).totalSupply() * 99            // OWNER owns >= 99% of the pool
          && _amReserve(existing, c.antimatter) >= p.amMinted,               // the seeded AM is actually in the pair
      "Step 0: pair exists but holds no evidence of THIS seed - ABORT"
  );
  ```
  An attacker cannot meet these without giving the protocol the pool. The tripwire variant ("resume only if this cutover created the pair") also blocks the PoC.

  **Caveat:** `p.liquidity` and `p.amMinted` are local-pass (simulated) figures. Arbitrage after a real seed can also move the pair's AM reserve, and a real seed may land at a slightly different block. An honest resume could therefore false-abort on the reserve check. Two treatments are acceptable:
  - Treat the abort as fail-loud. On this attended, owner-only path, an operator who inspects the pair can safely stop the script, so a false abort costs only time.
  - Allow a small tolerance on the `_amReserve` comparison, e.g. 1%, together with the ≥ 99% share check. The share check is the one an attacker cannot meet.

**Verifier:** `VerifyAntimatterPoolCutover` should anchor the record to chain state, not just check the record's internal consistency (antimatter-pool L-02 (pps44l2)):
- OWNER's AM/sUSDS LP / `totalSupply` ≥ 99%.
- AM supply ≥ the recorded `amMinted`.
- The pair's AM reserve is consistent with the recorded `amMinted`.
- The pair price is within a sanity band of the phUSD/sUSDS price.
- Alternatively, check the seed receipt's `Seeded` event.

**Patcher and Script C:** the patcher should not FILL `AntimatterSusdsPair` on a local-pass record alone. Script C's precondition should add the same OWNER-share check, so a foreign pair cannot reach UniswapHelper.

Fixing M-01 (`minSUSDSPaired` in `seed()`) does **not** fix this finding: the AM-dear revert this attack relies on stays in place by design. Both fixes are needed.
