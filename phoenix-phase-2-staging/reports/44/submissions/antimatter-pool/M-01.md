## Finding description and impact

### Severity

**Medium, borderline High.**

The attack is fork-proven, and the profit goes to an unprivileged third party. It needs one precondition that the attacker cannot force: **Script A (`sya-harvester`) must be broadcast before Script B (`antimatter-pool`).** The runbook sanctions that order explicitly (`docs/SyaAntimatterMainnetCutover.md` L15: *"A and B, in either order. They touch disjoint state"*). Script A's last transaction, `StableStakerV2.setClaimEnabled(true)`, is what puts Antimatter (AM) into third-party hands. At fork block 26303964, `Antimatter.totalSupply() == 0` and 32 staker/pool positions hold 205.42 AM of pending reward (fork read, `reports/44/script-audits/sya-harvester/review.md`). If B goes first, no third party holds AM and the attack cannot be carried out (control test below).

Medium rather than High for three reasons:
- The enabling order is an owner choice made in advance from two sanctioned options, and the other option removes the attack completely.
- The attacker must already hold AM and must act on a specific one-shot operation inside a window of a few blocks.
- The loss is bounded to one 10% POL slice (about $2.3k).

**Re-rate to Plausible High if the owner commits to the A-before-B order and broadcasts Script B unchanged.** In that case the precondition is no longer hypothetical, and the theft needs only an attentive AM holder.

### Description

`CutoverAntimatterPoolMainnet` is the story-122 Script B. Its Step 0 requires that the AM/sUSDS pair does not exist yet ([CutoverAntimatterPoolMainnet.s.sol#L258-L271](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/script/CutoverAntimatterPoolMainnet.s.sol#L258-L271)):

```solidity
// ---- Step 0: the AM/sUSDS pair must not exist, unless THIS cutover created it ----
console.log("\n=== Step 0: AM/sUSDS pair precondition ===");
address existing = IAmCutoverFactory(c.factory).getPair(c.antimatter, c.sUSDS);
bool seedDone;
if (existing != address(0)) {
    require(
        p.seeder != address(0) && p.seeder.code.length > 0 && IERC20(existing).balanceOf(OWNER) > 0,
        "Step 0: the AM/sUSDS pair ALREADY EXISTS and this cutover did not create it - ABORT (griefing risk R1, story 113). Do not seed into a pair someone else created; investigate first."
    );
    seedDone = true;
    console.log("  pair exists and OWNER holds its LP: seed already done (resume)", existing);
} else {
    console.log("  factory.getPair(AM, sUSDS) == 0: OK");
}
```

This `require` is Solidity script code. It runs during forge's **local simulation** and is never sent on chain. The broadcast key (`package.json` L99) uses `--broadcast --skip-simulation --slow --ledger`, so the six transactions go out one at a time, and each waits for its receipt:

| tx | call |
|---|---|
| 1 | `CREATE AntimatterPoolSeeder` (immutables public; address `CREATE(OWNER, 1791)` = `0xdb70…09BE`) |
| 2 | `UniPoolerV2.rescueERC20(PhusdSusdsPair, OWNER, 2258.927 LP)` |
| 3 | `PhusdSusdsPair.approve(seeder, lp)` |
| 4 | `Antimatter.setApprovedMinter(seeder, true)` |
| 5 | `seeder.seed(lp, minPhUSD, minSUSDS, OWNER, now + 1h)` |
| 6 | `Antimatter.setApprovedMinter(seeder, false)` |

tx1 is mined at least four blocks before tx5 can be included. From tx1 onward, the seeder's address, its immutables and the cutover's purpose are all public. The seed calldata was fixed during the local pass, and nothing re-reads the pair before tx5 is sent.

On chain, `seed()` accepts a pair that already exists. It only rejects a pair where AM is **dear** ([AntimatterPoolSeeder.sol#L178-L189](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/src/periphery/AntimatterPoolSeeder.sol#L178-L189), [#L217-L234](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/src/periphery/AntimatterPoolSeeder.sol#L217-L234)):

For an AM-**cheap** pair, `susdsRequired` is tiny, so the check passes. `_addLiquidity` then calls Router02 with `amountAMin = amAmount` and `amountBMin = 0` ([#L243-L245](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/src/periphery/AntimatterPoolSeeder.sol#L243-L245)):

```solidity

    .addLiquidity(antimatter, sUSDS, amAmount, susdsDesired, amAmount, 0, lpRecipient, deadline);
if (amUsed != amAmount) revert AntimatterNotFullyConsumed(amAmount, susdsUsed, susdsDesired);
```

At the attacker's ratio, the router takes every unit of AM and only `am * rS / rA` of sUSDS. The unused sUSDS goes back to OWNER (L190). Nothing on chain bounds the price at which the protocol's newly minted AM enters the market. The script's in-run end-state checks (L373-393) run in the same local simulation, never against the mined tx5, so they cannot catch this divergence.

The script's NatSpec bases F3's safety on exactly the guarantee that does not hold on chain ([CutoverAntimatterPoolMainnet.s.sol#L49-L52](https://github.com/Behodler/phoenix-phase-2-staging/blob/669cbc11a41b1bd677ac422391532bb79199b9a6/script/CutoverAntimatterPoolMainnet.s.sol#L49-L52)):

```solidity
 *         F3 (story 113): the seeder's AM/sUSDS add passes `amountBMin = 0`. Acceptable ONLY because step 0
 *         guarantees the pair is created fresh inside the seed transaction, so there is no price to manipulate.
 *         R1: someone could create the pair first. Step 0 refuses to seed into it; the runbook recommends a
 *         private RPC (Flashbots Protect) for the broadcast.
```

A private RPC hides only **pending** transactions. tx1 through tx4 are **mined** publicly before tx5 is signed, so a private RPC does not cover the window.

**Attack path (post-Script-A):**
1. The owner broadcasts Script A, and `claimEnabled` becomes true. The attacker claims at least 1 AM, or buys it from a claimant.
2. The owner broadcasts Script B. tx1 (the seeder CREATE) is mined, followed by tx2, tx3 and tx4.
3. Inside the tx1-to-tx5 window, the attacker calls `factory.createPair(AM, sUSDS)` and mints LP at 1 AM : 1e-12 sUSDS.
4. tx5 `seed()` succeeds. It adds all 2,457.70 AM against 2.46e-9 sUSDS and returns 2,077.16 sUSDS to OWNER. tx6 (the revoke) lands.
5. The attacker swaps 1e-6 sUSDS for about 2,452.65 AM. They annihilate it with USDC into phUSD and sell the phUSD into phUSD/sUSDS.

### Prior disclosure (partial; what it got wrong)

- **story-113 L465** (`[low] F3`): *"router add for AM/sUSDS uses amountBMin = 0, so on a skewed AM-cheap pair AM is paired against less sUSDS (unused sUSDS returns to lpRecipient)."* **story-113 Decision 7 (L178-181)** says the owner "can read the AM/sUSDS reserves first", and that a front-runner's AM *"would give that AM to the LP holders, which means the protocol."*
- story-113 Decision 7 Alternatives (L181) already proposed `minSUSDSPaired` / a price band "before the mainnet cutover story"; story-122 did not adopt it.
- **story-122 L142**: *"F3: the AM/sUSDS add uses `amountBMin=0`. That is acceptable because the pair is created fresh in the same transaction, guaranteed by step 0."* The runbook repeats this at L63-64 and names a private RPC as the R1 mitigation at L47-52.

What the disclosure got wrong or understated:
1. **Step 0 never runs on chain.** The scripted broadcast leaves a public window of at least four blocks between the seeder CREATE and the seed, and nothing re-reads the pair before tx5 is sent.
2. **The harm is not "less sUSDS paired".** The harm is that the protocol's entire AM inventory sits at a price the attacker chose, and the attacker then buys it for nothing.
3. **Decision 7 models only a donation.** It does not consider an attacker who **owns the pair's LP**. The attacker's LP is minted first, so the AM is not given to the protocol.
4. **A private RPC does not close the window**, because tx1 through tx4 are mined publicly.
5. Neither story connects F3 to the A/B ordering. The runbook's "either order" is what decides whether any third party holds AM.

## Recommended mitigation steps

**Interim (operational, before any broadcast): broadcast Script B before Script A.** Before A, no third party holds AM: `totalSupply == 0`, claims are disabled, and no StableStakerV2 position has reward greater than principal (`reports/44/script-audits/antimatter-pool/side-effects.json`), so the `autoAnnihilate` excess path is closed too. A front-runner can then only `createPair`, which is harmless (`test_r44_05`), or donate sUSDS one-sided, which the attacker loses (`test_r44_06`). The control PoC confirms that the theft does not reproduce in this order. Correct the runbook (`docs/SyaAntimatterMainnetCutover.md` §Order L15-16, L47-52, L63-64) to match:
- Require B before A, and drop the "disjoint state" rationale.
- State that the private RPC protects only the seed transaction's mempool exposure. It does not cover the tx1-to-tx5 window, because tx1 through tx4 are mined publicly under `--slow`.

**Code fix: enforce the precondition inside the seed transaction itself.** Pass either an expected-fresh flag or a `minSUSDSPaired` floor to `seed()`:

```solidity
function seed(
    uint256 lpAmount, uint256 minPhUSD, uint256 minSUSDS,
    uint256 minSUSDSPaired,            // new: script passes susdsOut * (1 - 0.1%) from the same pro-rata quote
    address lpRecipient, uint256 deadline
) external onlyOwner returns (uint256 amBurnedEquivalent, uint256 liquidity) {
    ...
    if (susdsPaired < minSUSDSPaired) revert InsufficientSUSDS(susdsPaired, minSUSDSPaired);
    ...
}
```

When a fresh pair is intended, the alternative is `require(amSusdsPair() == address(0))` at the top of `seed()`. With either check, an AM-cheap pair makes tx5 revert (fail-loud) instead of leaking the protocol's AM. The tripwire above shows the `minSUSDSPaired` variant blocks the PoC.

These checks address only the AM-cheap direction. The AM-dear direction still reverts by design, and the weak resume gate it reaches is fixed separately (M-02). Until the on-chain guard lands, B-before-A is the only control that closes this vector.
