## Severity

**Medium.** The finding impacts availability and function under stated assumptions. It is not attacker-driven and no direct asset loss has been shown.

**Primary basis: availability, based on a human-confirmed dependency (a stated assumption).** On 2026-09-17 the owner confirmed that the frontend reads `StableStakerV2` from `server/deployments/mainnet-addresses.ts`. On story 096's lapsed-window resume, V2 is live on chain. It is unpaused, registered with the Pauser, and holds every migrated V1 staker, while V1 is drained and paused. However, the `:broadcast` tail stops at the address patcher with exit 2, so `mainnet-addresses.ts` keeps `StableStakerV2: 0x0`. It stays that way until the minter window reopens and a *completed* cutover run patches the file. That takes at least 6h: re-initiate, the 6h wait, then two more broadcast legs. For that whole period, UI users cannot reach their V2 positions, even though story 096 exists to let them reach their funds. **What the PoC proves and what it does not:** the PoC proves that V2 is live on chain while the address book still says `0x0`. It does **not** run the frontend. The UI read is the owner's statement and is taken here as an assumption.

**Future aggravator.** The UI will also read `Antimatter` from this file. It does not do so yet. When it does, the same window also hides the Antimatter token, which is V2's reward path.

**Secondary basis: a verification gate is lost. This is disclosed as coverage loss, not asset loss.** The runbook, verifier NatSpec and cutover console all say the tail "stops at `:verify`". That pending-state `:verify` is described as *the* run that checks live V2 balances (`V2 userInfo >= credited`, per-pool `V2 totalStaked >= floor`). It is never chained. Once 6b completes, the sticky `minterMove.v2LiveBeforeMinterMove` marker makes `:verify` skip both live checks. Three disclosures bound this basis:

- **The skip is intentional in source.** `VerifyStableStakerV2Cutover.s.sol` L602 gives the reason as "migrated users may have withdrawn". So the defect is the loss of the *earlier* run that the skip relies on, not the skip itself. Turning this into asset loss would need a second, independent per-user credit bug that the lost check would have caught. None is known: the pending `:verify` run by hand passes all 29 per-user credits (see Proof of Concept).
- **Chaining `:verify` would not make the tail succeed.** Even if the tail reached it, the pending-state `:verify` always reverts `verify: Phase6b: PENDING` by design. The practical difference today is therefore (i) the live checks never run automatically and (ii) the addresses are never patched. It is not the difference between a failing tail and a green one.
- **Observation, not a separate finding.** Once any migrated staker makes an ordinary withdrawal during the pending window, the pending-state live per-user check fails on that user. The runbook's CAVEAT concedes this for "a LATER pending-state :verify". Only a `:verify` run immediately after the resume is reliable, which is why losing the automatic run matters.

**Why this is a footgun and not trusted-owner behaviour (Law 3).** The path is attended and owner-operated, and the patcher fails loudly with `ERROR (2)` and a non-zero exit. But the operator has been told by the story, the `package.json` runbook, the verifier NatSpec and the script's final console line to expect a stop at `:verify` with `verify: Phase6b: PENDING`. Instead they get a generic "broadcast not finished" patcher error, no instruction to run `:verify`, and an address book that does not match the chain. A competent, non-malicious operator following the runbook would be surprised by this.

**Likelihood: low, because the path is rare, but deterministic once on it.** It needs a halted cutover whose 78h minter window lapses. On that path the tail stops at the patcher every time (fork-proven).

## Description

### The broadcast tail

`stable-staker-v2-cutover:broadcast` (`package.json` L53) chains the address patcher, `:verify` and `:preview` behind the forge broadcast with `&&`:

```bash
… forge script script/CutoverStableStakerV2Mainnet.s.sol:CutoverStableStakerV2Mainnet … -vvv \
  && node scripts/patch-mainnet-addresses-stable-staker-v2.js \
  && npm run stable-staker-v2-cutover:verify \
  && npm run stable-staker-v2-cutover:preview
```

### The root cause: `loadProgress` only knows one non-completed status

Story 094 added progress status `awaiting_reseed` and gave the patcher a dedicated, instructive branch for it. Story 096 added a second non-completed status, `awaiting_minter_window`, which the cutover writes when a resume past Phase 6 finds the minter window lapsed. It added no branch for that status. [`scripts/patch-mainnet-addresses-stable-staker-v2.js#L70-L89`](https://github.com/Behodler/phoenix-phase-2-staging/blob/91ed727/scripts/patch-mainnet-addresses-stable-staker-v2.js#L70-L89):

```js
function loadProgress() {
    if (!fs.existsSync(PROGRESS_FILE)) fail(2, `Progress file not found: ${PROGRESS_FILE}`);
    let p;
    try {
        p = JSON.parse(fs.readFileSync(PROGRESS_FILE, 'utf8'));
    } catch (e) {
        fail(2, `Progress unparseable: ${e.message}`);
    }
    if (p.chainId !== 1) fail(2, `Progress chainId is ${p.chainId}, expected 1 (mainnet)`);
    if (p.deploymentStatus === 'awaiting_reseed') {
        fail(2, 'LEG 1 ENDED AFTER THE MINTER EXECUTE (story 094) - deploymentStatus is "awaiting_reseed", nothing patched. '
            + 'This stop is expected. Once the execute has mined, run npm run stable-staker-v2-cutover:preview and then '
            + 'npm run stable-staker-v2-cutover:broadcast again: leg 2 re-seeds the mined R, finishes, and this tail patches, verifies and previews.');
    }
    if (p.deploymentStatus !== 'completed') {
        fail(2, `deploymentStatus is "${p.deploymentStatus}", expected "completed" (broadcast not finished, or a resume leg is outstanding)`);
    }
    if (!p.contracts || typeof p.contracts !== 'object') fail(2, 'Progress file has no "contracts" object');
    return p;
}
```

`awaiting_minter_window` falls through to the generic exit at L84–L86. The process exits 2 before `run()` writes anything, so `&&` skips both `:verify` and `:preview`.

## Impact

1. **Live V2 is missing from the address book for at least 6h (primary, under the stated assumption).** After a successful lapsed-window resume, V1 is drained and paused and every staker's position sits in an unpaused V2. `mainnet-addresses.ts` still holds `StableStakerV2: 0x0000000000000000000000000000000000000000`. It is only patched after the operator re-initiates the minter withdrawal, waits 6h, and completes both broadcast legs, after which the patcher finally sees `completed`. Given the owner's confirmation that the frontend reads `StableStakerV2` from this file, UI users cannot reach their V2 positions to view or withdraw them during that period. That is exactly the population and moment story 096 was written for ("the finding affects whether users can reach their funds"). V2 stays callable on chain directly. The impact is on protocol availability through its supported interface, not on assets.
2. **Antimatter (future).** The same window will also hide `Antimatter: 0x0` once the UI reads that key.
3. **Silent loss of verification coverage (secondary).** The only run the design relies on for the live `V2 userInfo >= credited` and `V2 totalStaked >= floor` checks never happens automatically. After 6b completes, `:verify` reports success without ever having compared live V2 balances to migrated credits. The event-based checks (a `DepositedFor` per `MigratedOut`, the loss bound, the vacuity guard) still run. This hides a credit defect only if one exists. None is known, and the manual pending `:verify` confirms all 29 credits today.
4. **Misleading operator signal.** Instead of the promised `verify: Phase6b: PENDING`, which says what was verified, the operator sees `ERROR (2): … (broadcast not finished, or a resume leg is outstanding)`. That wording reads like a failed broadcast and leaves the operator unsure whether the resume worked. The runbook's CAVEAT about "the one chained after a second pending resume" also describes a run that never occurs, because every pending resume hits the same exit.

**What each step asserts:**

- **(a)** After a Phase 0–6 halt, the minter window is aged past 78h and the story-096 resume runs. The progress file then reads `deploymentStatus: awaiting_minter_window` and `minterMove.v2LiveBeforeMinterMove: "true"`, names the live V2, and on chain `StableStakerV2.paused() == false` with V2 registered with the Pauser.
- **(b)** The helper reads the `:broadcast` tail **verbatim from `package.json`** (everything after the forge step) and runs it with `bash`. `npm` is shadowed by a shim that only records its arguments. The chain exits **2** with the exact patcher message, and `npm run stable-staker-v2-cutover:verify` is **never invoked**.

**PoC method disclosures (validator weaknesses):**

1. **Time is aged through storage, not `vm.warp`.** The minter withdrawal's `initiatedAt` slot is rewritten, because an hours-long warp leaves Tokemak's Chainlink feeds frozen at the fork block and the execute reverts `InvalidDataReturned()`. The sponsor's own fork tests use the same technique. The strategy only compares `block.timestamp` with `initiatedAt`.
2. **Phases run through the sponsor's `CutoverPhasesHarness`**, which is preview-pinned (`isPreview`) with an `OWNER` prank. The one audit seam, `persistLikeBroadcast()`, clears `isPreview` only around the same `_writeProgress` call that `run()` makes in broadcast mode, so the real progress file is written for the patcher and the verifier.
3. **Verifier logs are injected.** A fork RPC cannot return logs for locally executed transactions, so recorded `MigratedOut` / `DepositedFor` / DOLA `Transfer` logs are fed to the real verifier through a `_fetchLogs` override, as in the sponsor's `VerifyStableStakerV2CutoverHarness`. The `CUTOVER_START_BLOCK` / start-block log-window path is therefore not exercised.
4. **Corroborated by a real broadcast.** The same sequence was run with real `--broadcast --unlocked` transactions on an anvil mainnet fork at block 25994908 (`reports/36/script-audits/fork-logs/pending-path/`):
   - P3: leg 1 halted at the execute.

   The anvil run does not use harness seams 1–3 for the tail itself.

## Recommended Mitigation

The goal is to make the chain do what story 096 and the runbook say, and to put live V2 into the address book the moment V2 goes live.

### 1. Add an `awaiting_minter_window` branch to the patcher

This branch patches only the V2 keys and exits 0. In `loadProgress`, return a scope instead of failing:

```js
function loadProgress() {
    // … existing file / JSON / chainId checks …
    if (p.deploymentStatus === 'awaiting_reseed') {
        fail(2, /* unchanged story-094 message */);
    }
    if (!p.contracts || typeof p.contracts !== 'object') fail(2, 'Progress file has no "contracts" object');
    if (p.deploymentStatus === 'awaiting_minter_window') {
        // Story 096: V2 is LIVE (unpaused, stakers migrated) but Phase 6b is pending. Patch ONLY the keys the UI needs
        // to reach live V2; the DOLA strategy keys must not move until 6b completes (autoDOLA is not retired yet).
        return { progress: p, scope: 'v2-live-only' };
    }
    if (p.deploymentStatus !== 'completed') {
        fail(2, `deploymentStatus is "${p.deploymentStatus}", expected "completed" (broadcast not finished, or a resume leg is outstanding)`);
    }
    return { progress: p, scope: 'full' };
}
```

In `run()`, when `scope === 'v2-live-only'`:

- Run the existing `FIELDS` loop for `StableStakerV2` and `Antimatter` (fill-once; `SAME` counts as success, so the later completing run stays idempotent). Patch `Antimatter` now as well, because the UI will read it.
- **Skip** the story-092 block entirely: `YieldStrategyDola` stays on autoDOLA and `YieldStrategyDolaLegacy` stays `0x0`. The completing run patches them later.
- **Skip** the comment rewrites that describe a finished cutover ("V1 is drained … retired", the story-092 `YieldStrategyDola` notes). Instead, write a header that says `StableStakerV2 + Antimatter FILLED; Phase 6b PENDING (story 096) - DOLA strategy keys unchanged`.
- Keep the key-set drift check (exit 3) and the collision checks (exit 4).
- Print `V2 IS LIVE; addresses patched (V2/Antimatter only). Next: :verify runs now and is EXPECTED to report Phase6b: PENDING`, then exit 0 so the tail reaches `:verify`.

Update the header comment's exit-code table: exit 2 must no longer cover `awaiting_minter_window`.

### 2. Settle what the pending `:verify` does in the tail

Because the pending-state `:verify` reverts `Phase6b: PENDING` by design, choose one of the following and make every artefact agree with it:

- **(a) Preferred: a clean pending report.** When `minterMovePending` is true and every other check has passed, `:verify` prints a clear `PHASE 6b PENDING: Phases 1-7, Phase 8 pending shape and N per-user credits (incl. live V2 balances) verified` and **exits 0**. A pending state must still never print `CUTOVER VERIFIED`. The tail then also runs `:preview` as a smoke test, and any non-zero exit on this path is a real failure. Keep the "never report success while 6b is pending" guarantee (story 096 checklist, L79) through that distinct status line, and have the sponsor test assert the line rather than a revert.
- **(b) Keep the revert, and state it explicitly.** Leave `:verify` as it is, and make the patcher branch print, as its last line, `V2 IS LIVE: npm run stable-staker-v2-cutover:verify is running next and MUST end in 'verify: Phase6b: PENDING'; any other verify failure is real. If it did not run, run it NOW, before stakers withdraw.` With mitigation 1 in place the tail does reach `:verify`, so this matches story 096 Decision 5 as written.

Under either option, correct the text that currently promises something the chain does not do: the `package.json` L49 story-096 paragraph and its CAVEAT, `_printMinterMovePending` (`CutoverStableStakerV2Mainnet.s.sol` L2262), and the verifier NatSpec (L78–L83) and the L602–L603 comment. They must describe the actual tail: the patcher fills V2 and Antimatter, then `:verify` runs with the chosen outcome.

### 3. Add guard tests beside `test_broadcastChainsVerifyBeforePreview`

- **Patcher unit test.** Write an `awaiting_minter_window` progress fixture, run `node scripts/patch-mainnet-addresses-stable-staker-v2.js` through `vm.ffi` (or a node test), and assert that it exits 0, that `StableStakerV2` and `Antimatter` are filled, and that `YieldStrategyDola`, `YieldStrategyDolaLegacy` and `SDOLA` are byte-unchanged. Then re-run it against a `completed` fixture on the same file and assert `SAME` for V2/Antimatter and `PATCH`/`FILL` for the DOLA keys.
- **Chain test.** Read the `:broadcast` tail verbatim from `package.json`, run it with `npm` shadowed (as `run-broadcast-tail.js` does in the PoC) against the `awaiting_minter_window` fixture, and assert that `npm run stable-staker-v2-cutover:verify` **is invoked**.

### Interim operating procedure until the fix lands

On a lapsed-window resume, treat the patcher's `ERROR (2): deploymentStatus is "awaiting_minter_window"` as expected, and then do the following:

1. Run `npm run stable-staker-v2-cutover:verify` **immediately**, before any staker can withdraw, and confirm it ends in `verify: Phase6b: PENDING … N per-user credits (incl. live V2 balances) verified`.
2. Fill `StableStakerV2` and `Antimatter` in `mainnet-addresses.ts` by hand from the progress file, and ship the frontend address update, leaving the DOLA strategy keys untouched.
