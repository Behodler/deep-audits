## Severity

**Medium.**

Not High: no assets are at direct or indirect risk and nothing here touches mainnet state. `dev` broadcasts only to `http://localhost:8545`. That ceiling is real and is respected.

Not Low: the impaired function is the integrity of the rehearsal that gates a live cutover; the failure is **silent** — a divergent run is byte-indistinguishable from a good one at the artefact level; the guard that looks like the defence provably does not catch it; and the whole path was reproduced rather than argued. That is protocol-function impact with stated assumptions and external requirements, which is the C4 Medium shape.

This is an operational footgun, not an owner-misuse claim: a competent, non-malicious operator would be surprised that a leftover anvil silently absorbs a full rehearsal with every assertion green.

**Pinned apart from ledger entry `L-02 ce524709d965de786fc2b6f6a1e5d2e2139406346b8fd5f930fdabac679b36e0`** (status `open`), which proposes a `require(block.chainid == 31337)` guard. That is a *different root cause with a disjoint remedy*, and the distinction is established empirically below, not by judgement. This submission does not override, supersede or re-file L-02.

## Description

The `dev` key at `package.json:16` reads:

```json
"dev": "npm run clean:local && npm run start:anvil & sleep 3 && LOCAL_PROMO_KENDU=true npm run deploy:local && ./simulate-yield.sh && npm run extract:addresses && npm run generate:ts-anvil && npm run serve"
```

`&` binds **looser** than `&&`, so this is **two pipelines, not one**:

- **Pipeline A**, `npm run clean:local && npm run start:anvil`, is backgrounded. **Its exit status is discarded** — `npm run dev` reports success or failure for pipeline B alone.
- **Pipeline B** is the foreground chain, gated on nothing but a bare `sleep 3`: no port probe, no `cast block-number` poll, and no check that the node answering on 8545 is the one pipeline A started.

`script/DeployMocks.s.sol` contains exactly one reference to the chain it is running on — `console.log("Chain ID:", block.chainid)` at `:392` — and no assertion of any kind about it.

**Reproduced.** With a pre-existing anvil already listening on 8545 — the state a Ctrl-C out of `npm run serve` always leaves behind, because `serve` blocks forever and only the foreground pipeline dies — `npm run dev` produced:

```
pipeline A: Error: Address already in use (os error 98)      <- swallowed; exit status discarded
pipeline B: [PIPELINE_B] proceeded, dollar-question=0
port 8545: still held by the ORIGINAL anvil (pid 57286), block 11, deployer nonce 1
```

`deploy:local` then simulated cleanly — including `end-state phUSD ACL asserted` and the Phase 7.6 dispatcher-swap rehearsal — and **broadcast 265 transactions onto that non-genesis chain**, driving the deployer nonce `1 → 267`. Every one of DeployMocks' own post-conditions passed, and `progress.31337.json` was rewritten as if the chain were fresh.

**Why the obvious guard does not close this.** Ledger `L-02 ce524709d965` proposes `require(block.chainid == 31337)`. Verified against the stale node:

```
$ cast chain-id --rpc-url http://localhost:8545
31337
```

The stale chain **is** chainId 31337. L-02's proposed guard would pass and catch nothing. The missing assertion is **genesis freshness**, not network identity — a separate root cause with a separate remedy.

**The precondition is not exotic; it is manufactured by the normal end of a successful run.** Confirmed at teardown of the clean full run: after `serve` was killed, `npm run dev` returned **exit 0** while pipeline A's anvil was still listening on 8545 answering `eth_chainId` → `0x7a69`, and had to be killed by PID. Every ordinary `dev` session ends by arming the next one.

## Impact

`dev` is not merely a dev-stack boot. It is the **local rehearsal of the mainnet PhlimboV2→V3 cutover, the dispatcher swap and the terminal privilege sweep**, and its green output is read as evidence that those mainnet procedures are sound.

That claim rests on what the script actually asserts, not on a comment. Its recorded post-conditions are the mainnet cutover steps themselves: the Phase 7.4 V2→V3 migration with its completeness gate (`PhlimboV2.totalStaked() == 0`), stake conservation into V3, and `phUSD.setMinter(PhlimboV2, false)`; the Phase 7.6 dispatcher swap with its conservation gate on `hook.pull()`; and the terminal residual-privilege sweep, `phUSD.setMinter(deployer, false)` followed by the 10-entry end-state ACL table.

The intent to mirror mainnet is stated in-source too, though more narrowly than the rehearsal as a whole — the NatSpec at `script/DeployMocks.s.sol:92-96` is scoped to the `IPhlimboAPYLike` shim:

```solidity
/**
 * @notice Story 079. The shared admin surface of `PhlimboV2` and `PhlimboV3`, which are
 *         unrelated Solidity types. Byte-identical to the shim in
 *         `DeployMainnetPromotionReady.s.sol` so the local `_setDesiredAPYTwoStep` and the
 *         mainnet one are the same code operating through the same interface.
 */
interface IPhlimboAPYLike {
```

Under the stale-anvil mode every assertion still passes while the run is layered on top of an arbitrary prior deployment — addresses, nonces, phUSD ACL state and dispatcher indices are all **inherited rather than established**. A rehearsal that silently certifies itself on the wrong chain state is worse than one that fails, because the failure is invisible and the artefact it emits (`progress.31337.json`) is indistinguishable from a good run.

No on-chain assets are at risk; the asset at risk is the **evidence**. Likelihood is high — the precondition is produced by the normal exit path of the previous run, and it was reproduced in this audit. External requirement: an anvil instance already bound to 8545 at invocation time. Local chain only; this entry point produces no mainnet transaction.

## Proof of Concept

A Foundry test is the wrong instrument here. This is a shell/tooling defect: there is no on-chain state transition to assert, and a `forge test` cannot observe shell operator precedence, a discarded background exit status, or which node is bound to a port. Fabricating one would prove nothing about the defect. The evidence is the recorded command sequence and its observed output, given verbatim so it is re-runnable.

**Reproduction:**

```bash
# Shell 1 — the "leftover" node, exactly what Ctrl-C out of `npm run serve` leaves behind
anvil --host 0.0.0.0 --port 8545 --chain-id 31337 --block-time 2

# Shell 2
npm run dev
```

**Observed:**

```
[pipeline A] Error: Address already in use (os error 98)        # backgrounded => status discarded
[PIPELINE_B] proceeded, dollar-question=0

$ cast chain-id      --rpc-url http://localhost:8545   -> 31337     # a chainid guard would PASS
$ cast block-number  --rpc-url http://localhost:8545   -> 11
$ cast nonce <deployer> --rpc-url http://localhost:8545 -> 1        # NOT a genesis chain
   port 8545 still held by the ORIGINAL anvil, pid 57286

... DeployMocks simulation and broadcast ...
   265 transactions broadcast onto the pre-existing chain
   deployer nonce 1 -> 267
   'end-state phUSD ACL asserted: deployer + PhlimboV2 OUT, V3 + minter + staker + 5 hooks IN'
   Phase 7.6 dispatcher-swap rehearsal: PASSED
   progress.31337.json rewritten as if the chain were fresh
```

Every DeployMocks post-condition green, on the wrong chain state.

**Disclosure — this reproduction was itself cut short.** The run was terminated mid-broadcast by the audit harness's own 590 s tool limit (`EXIT=124`) — a tool limit, not a script failure. The decisive evidence (265 receipts, nonce 1 → 267, all post-conditions green in forge's **local/simulation** pass) was captured before termination. The post-condition results above are therefore facts about forge's local pass, which precedes dispatch, not about a completed broadcast; the finding does not depend on the broadcast having run to completion, since the defect is that the run was admitted onto the stale chain at all. The truncation also independently established that `dev`'s deploy leg needs more than ten minutes under `--slow` at `--block-time 2`.

## Recommended Mitigation

Add a genesis-freshness gate to `DeployMocks.run()` alongside the chain-id gate, before `vm.startBroadcast`:

```solidity
require(block.chainid == 31337, "DeployMocks: local only");
require(
    vm.getNonce(deployer) == 0,
    "DeployMocks: chain is not fresh - a prior deployment is already on 8545; kill it and re-run"
);
```

Independently, make the shell honest. The `dev` key cannot express this fix as a one-liner — the readiness
loop, the PID check and the trap are genuinely multi-line — so move the orchestration into a script beside
the two that already exist (`simulate-yield.sh`, `verify-stable-staker.sh`) and reduce `dev` to a call.

**1. New file `dev-local.sh`** (repo root, `chmod +x`, same conventions as `simulate-yield.sh`):

```bash
#!/usr/bin/env bash
# dev-local.sh - start a FRESH anvil, deploy onto it, serve. Never reuses a running chain.
set -Eeuo pipefail

RPC="http://localhost:8545"
ANVIL_PID=""

# (d) Ctrl-C out of `serve` must not leave anvil behind, because a surviving
#     anvil is exactly the stale-chain precondition the next run deploys onto.
cleanup() {
    if [[ -n "$ANVIL_PID" ]] && kill -0 "$ANVIL_PID" 2>/dev/null; then
        echo "dev: stopping anvil (pid $ANVIL_PID)" >&2
        kill "$ANVIL_PID" 2>/dev/null || true
        wait "$ANVIL_PID" 2>/dev/null || true
    fi
}
trap cleanup EXIT INT TERM

# (a) Refuse to start at all if something already owns 8545. This is the check
#     `require(block.chainid == 31337)` cannot make: a stale anvil is also 31337.
if cast block-number --rpc-url "$RPC" >/dev/null 2>&1; then
    echo "dev: a node is already listening on $RPC. Kill it (pkill anvil) and re-run." >&2
    exit 1
fi

npm run clean:local

# (b) Start anvil DIRECTLY, not via `npm run start:anvil`, so $! is anvil's own
#     pid rather than the npm wrapper's. Keep the flags identical to start:anvil.
anvil --host 0.0.0.0 --port 8545 --chain-id 31337 --block-time 2 &
ANVIL_PID=$!

# (c) Foreground readiness loop replaces `sleep 3`: poll until the node answers,
#     and fail loudly if anvil died instead of silently racing ahead.
ready=""
for _ in $(seq 1 50); do
    if ! kill -0 "$ANVIL_PID" 2>/dev/null; then
        echo "dev: anvil exited during startup (port in use?)" >&2
        exit 1
    fi
    if cast block-number --rpc-url "$RPC" >/dev/null 2>&1; then ready=1; break; fi
    sleep 0.2
done
[[ -n "$ready" ]] || { echo "dev: anvil did not answer on $RPC within 10s" >&2; exit 1; }

# (d) Confirm the node that answered is the pid we just started, not one that
#     appeared in the window between the pre-flight check and the launch.
listener="$(ss -lptnH "sport = :8545" 2>/dev/null | grep -o 'pid=[0-9]*' | head -1 | cut -d= -f2 || true)"
if [[ -z "$listener" ]]; then
    listener="$(lsof -t -iTCP:8545 -sTCP:LISTEN 2>/dev/null | head -1 || true)"
fi
if [[ -n "$listener" && "$listener" != "$ANVIL_PID" ]]; then
    echo "dev: $RPC is served by pid $listener, not the anvil we started ($ANVIL_PID)." >&2
    exit 1
fi
if [[ -z "$listener" ]]; then
    echo "dev: warning - neither ss nor lsof could name the listener on 8545;" >&2
    echo "     relying on the genesis-freshness assert in DeployMocks.run()." >&2
fi

# Belt and braces against the same precondition, in the shell rather than in Solidity.
if [[ "$(cast block-number --rpc-url "$RPC")" -gt 5 ]]; then
    echo "dev: chain is not fresh (block-number > 5). Refusing to deploy onto it." >&2
    exit 1
fi

LOCAL_PROMO_KENDU=true npm run deploy:local:forge
./simulate-yield.sh
npm run extract:addresses
npm run generate:ts-anvil
npm run serve   # blocks; Ctrl-C here reaches the trap above
```

**2. `package.json` — three edits.**

Replace the `dev` one-liner, which is the defect itself:

```diff
-    "dev": "npm run clean:local && npm run start:anvil & sleep 3 && LOCAL_PROMO_KENDU=true npm run deploy:local && ./simulate-yield.sh && npm run extract:addresses && npm run generate:ts-anvil && npm run serve",
+    "dev": "./dev-local.sh",
```

`&` binds looser than `&&`, so the existing value is two concurrent pipelines rather than one sequence:
`npm run clean:local && npm run start:anvil` is backgrounded as a unit and its exit status is discarded,
while `sleep 3 && … deploy:local && …` runs in the foreground regardless of whether anvil ever started.
Calling a script makes the sequence a real sequence, and `set -Eeuo pipefail` makes every step's failure
stop the run.

Split the double-clean out of `deploy:local`, so the deploy step stops deleting artefacts underneath a
live node (`deploy:local` currently re-runs `clean:local` a second time, after anvil is up, removing the
`broadcast/*/31337` directory the very next `forge script` writes into):

```diff
-    "deploy:local": "npm run clean:local && forge script script/DeployMocks.s.sol:DeployMocks --rpc-url http://localhost:8545 --broadcast --slow --gas-estimate-multiplier 300",
+    "deploy:local:forge": "forge script script/DeployMocks.s.sol:DeployMocks --rpc-url http://localhost:8545 --broadcast --slow --gas-estimate-multiplier 300",
+    "deploy:local": "npm run clean:local && npm run deploy:local:forge",
```

`dev-local.sh` calls `deploy:local:forge` and runs `clean:local` exactly once, before anvil starts;
`deploy:local` keeps its current meaning for anyone invoking it standalone.

Scope the global-state deletion in `clean:local`, which reaches outside the repo into the shared Foundry
home and will wipe temp state belonging to any *other* anvil on the machine:

```diff
-    "clean:local": "rm -rf broadcast/*/31337 server/deployments/progress.31337.json server/deployments/local.json && rm -rf ~/.foundry/anvil/tmp/*",
+    "clean:local": "rm -rf broadcast/*/31337 server/deployments/progress.31337.json server/deployments/local.json",
```

`start:anvil` is left as-is; it remains the way to run a standalone node, and `dev-local.sh` deliberately
does not go through it so that `$!` names anvil rather than npm. If you would rather keep the single
definition of the anvil flags, launch it under `setsid npm run start:anvil &` and kill the process
*group* (`kill -- -"$ANVIL_PID"`) in both `cleanup` and the pid comparison — the npm wrapper otherwise
survives the readiness check and outlives the trap.

Note explicitly in the `L-02 ce524709d965` remediation that the chain-id guard alone does **not** close this.
