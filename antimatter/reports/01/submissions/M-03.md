# [M-03] The daily phUSD cap governs only the stable leg: a cap of X permits 2X

**Ledger fingerprint:** `df5c16e2238a3c1c`
**Severity:** Medium
**Location:** `lib/antimatter/src/Antimatter.sol:227` (capped stable leg), `:236` (uncapped antimatter leg); context `:227-237`
**Root cause class:** `IssuanceCapCoversOnlyOneMintLeg`

## Finding description and impact

### Summary

`PhusdStableMinter.maxMintPerDay` is the protocol's only per-day issuance control. `annihilateFrom` routes only the **stable** leg through it (`Antimatter.sol:227`); the **antimatter** leg is minted by Antimatter itself at `:236`, on its own FlaxToken authorisation, where the counter cannot see it. A cap entered as X therefore permits 2X of phUSD to be issued.

Worse than the factor itself: the counter reports **100% utilisation at 50% of real issuance**, so the mis-sizing is invisible to the operator relying on it.

### Vulnerability details

```solidity
minter.mint(stable, stableAmount);   // :227  charges the daily counter: amount * rate / 1e18
...
_phUSD.mint(recipient, amount);      // :236  minted directly by Antimatter - counter never sees it
IERC20(address(_phUSD)).safeTransfer(recipient, mintedForStable);  // :237
```

Total phUSD issued per annihilation is `amount * (1 + exchangeRate/1e18)`, while the amount charged to the counter is `amount * exchangeRate/1e18`. At the nominal `exchangeRate == 1e18` this is a flat **2x** under-count. The general divisor is `(1 + exchangeRate/1e18)` and moves with the rate — see M-04, which is why the safe-config guidance below is rate-dependent.

Antimatter has no cap of its own, no pause, and `mint` at `:179` has no supply ceiling, so this rail is the **sole quantitative bound** on the uncollateralised issuance described in M-02.

### This is a Law-3 owner footgun, not an admin-abuse finding

No malicious-owner vector is claimed. The test is whether a competent, **non-malicious** operator would be **surprised**. They would: entering X as a daily phUSD issuance cap and receiving 2X of issuance is not an obvious consequence — discovering it requires knowing that a second contract (Antimatter) holds an independent FlaxToken mint authorisation that bypasses the counter entirely. Nothing on either side documents the coupling, and the counter's own reading actively misleads: it reads fully utilised at exactly the moment it has permitted double. Surprise ⇒ footgun ⇒ in scope, at honest severity.

### Impact

No direct asset loss. The impact is on the protocol's only per-day issuance control: a `maxMintPerDay` of X permits 2X, silently, on a token half of whose issuance is structurally uncollateralised (M-02). A control that misreports its own utilisation is worse than an absent control, because it manufactures false confidence at precisely the moment it matters.

The cap is exceeded **outright in a single transaction**, not merely asymptotically: cap 10,000e18, one `annihilateFrom` of 6,000e18 charges 6,000e18 to the counter but delivers 12,000e18 of phUSD.

### Severity justification

**Medium**, adjudicating a conflict the sanitization stage flagged (the code-scan input conceded "a downgrade to Low is defensible"). The Low argument is honest — no asset loss, no attacker-specific gain — but it mis-frames the impact class. C4 Medium covers "the function of the protocol ... could be impacted", and the function impaired here **is a safety control**. The protocol's only issuance rail is off by 2x in the unsafe direction, silently, and the operator has no way to notice.

Not High: no theft, no specific victim, and no attacker gain beyond what the design already grants.

**Assumptions:** `exchangeRate == 1e18` gives the flat 2x; the true divisor is `(1 + exchangeRate/1e18)` and moves with the rate.
**External requirement:** `maxMintPerDay` is set non-zero, i.e. the operator is relying on the rail at all.

Deliberately **not collapsed** with M-01 (unvalidated decimals) or M-05 (shared-budget DoS): same neighbourhood, different root causes, different impact classes, different mitigations.

## Safe-configuration guidance (until the code is changed)

> Set `maxMintPerDay` to **HALF** the phUSD issuance you intend to permit, for every stablecoin that Antimatter can annihilate — and only while `exchangeRate == 1e18`. The correct divisor is `(1 + exchangeRate/1e18)`, so it changes the moment the rate is moved (see M-04). Do not treat `maxMintPerDay` as a phUSD-issuance cap; it is a per-stable **deposit throttle** that happens to be denominated in phUSD.

Concretely: to permit 10,000 phUSD/day of issuance at `exchangeRate == 1e18`, enter `maxMintPerDay = 5,000e18`. Recompute as `intendedIssuance / (1 + exchangeRate/1e18)` on every rate change.

**Read these with the caveat that fixes their rank:** both assert against a hand-written mirror of the
minter's rolling window maintained in the invariant harness, not against `PhusdStableMinter`'s own counter.
They agree with the replay and they broke on two engines, which is why they are worth showing — but the
finding does not rest on them, and a reader should not treat a mirror-based invariant failure as
independent confirmation of the minter's accounting.

Medusa 1.5.1 produced a **single-call** counterexample pinning the ratio exactly:
`peakIssuedInWindow(USDC) = 9893392938000000000000` versus `peakChargedInWindow(USDC) = 4946696469000000000000`
— exactly 2.000x.

Anti-vacuity check: the minter's cap was **live** in the harness (121 swallowed inner reverts, dominated by
`"Daily mint limit exceeded"`), so the failure is not an artefact of an inert control.

## Recommended mitigation

In descending order of quality:

1. **Route the antimatter leg through the same counter.** Have `PhusdStableMinter` mint (or at least charge for) both legs, so one counter sees the whole issuance. This makes `maxMintPerDay` mean what its name says and simultaneously fixes M-05's asymmetric budget extraction.
2. **Add an equivalent per-period cap on Antimatter's own leg at `:236`.** Cheaper to implement, but leaves two counters an operator must keep in sync, and the sum of two independent caps is not the same control as one.
3. **Weakest — documentation only:** rename `maxMintPerDay` to reflect that it is a per-stable *deposit* throttle, and document the `(1 + exchangeRate/1e18)` relationship on both sides, so operators size it correctly. This does not restore the control; it only stops it lying.

Whichever is chosen, expose the true issuance figure alongside the charged figure so the utilisation reading is honest.
