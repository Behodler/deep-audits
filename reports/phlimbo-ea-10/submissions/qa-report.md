## Low Risk Findings

### [L-01] MigratorV2V3 has no self-pull forwarder: PhlimboV3-side unclaimable stable/promo banked to the migrator's own address is stranded <!-- id: pe10l1 -->

**Location**: `src/MigratorV2V3.sol` (`migrate` / `seedUsers` straggler path)

**Description**: When MigratorV2V3 processes a straggler pass, it can accrue pending
stable/promo on the PhlimboV3 side that is banked to `unclaimableStableOf[migrator]` /
`unclaimablePromoOf[migrator]` — i.e. the migrator contract itself is the beneficiary.
MigratorV2V3 exposes no function that calls `PhlimboV3.claimUnclaimableStable` /
`claimUnclaimablePromo` on its own behalf (no forwarder / self-pull). If the migrator's own
address is blocklisted mid-pass while it holds accrued pending (an exotic precondition), the
direct-transfer path fails and the value falls into the PhlimboV3-side unclaimable bank, which
the migrator then has no code path to reach.

**Impact**: No asset theft and no permanent loss. Value is fully recoverable by the owner
out-of-band via `emergencyTransfer`. Availability impact is confined to a single migrator
identity's residual bank and does not reach Medium (protocol function is not impacted). This is
a design/operational footgun kept in scope for completeness (recall beats report-tidiness).
Distinct from V3-L-08, V3-F-01, and V3-Q-01 (different banks / root causes).

**Likelihood**: Very low — requires the migrator's own address to be blocklisted at the exact
moment it holds accrued pending, and the residue is owner-recoverable regardless.

**Recommendation**: Add a forwarder on MigratorV2V3 that calls
`PhlimboV3.claimUnclaimableStable` / `claimUnclaimablePromo` for itself, so the migrator can
recover its own PhlimboV3-side bank without owner intervention.
