# [M-03] Self-feeding pot: decimals-blind sub-dust forfeiture is un-refundable, pot-directed, misreported, and accretes with no cap and no owner action

## Severity

**Medium**, raised from Low — **but flagged for human triage as borderline-Low.** See the triage flag below before accepting the Medium.

As a standalone value leak this is Low: the per-batch forfeiture is bounded at `0.999999` USDC. The Medium is claimed because of what the accretion *does*: it makes the safe-configuration condition that two `wont-fix` closures rest on — *"keep Σ(pot_i) < nudgeSize × mintPrice"* — **a condition that cannot be held by a one-time check; it requires a standing operational control.** The quantity drifts upward on its own, at a rate set entirely by third-party frontend quoting behaviour, with no owner action of any kind.

Confidence: **high on the mechanism**, **medium on the rate** (the rate depends on how much slack integrating frontends quote).

### ⚠ Triage flag — the Medium is substantially borrowed

Two honest qualifications, both of which pull toward Low:

1. **The dust is inert without M-01's exact arming precondition.** The residue accretes **in the payment token**. Absent the payment-token/nudge-token collision — i.e. unless `ITokenDispatcherV2(dispatcher).primeToken()` is a whitelisted nudge token on that instance — the residue is **never snapshotted by `_snapshotRewards` and never paid out**. It simply sits in the contract. This finding's Medium is therefore substantially **borrowed from M-01**: it prices a consequence that only exists inside M-01's configuration.
2. **The residue is un-refundable, not irreversible.** `rescueERC20` exists and is an owner call. The owner can sweep it at any time. What the code removes is the *caller's* ability to get it back through a later refund — a different and smaller claim.

With those corrections the residual standalone claim is: **a ≤ $1-per-batch leak, plus a monitoring requirement.** A triager who lands this at **Low** is well-founded. The Medium is defensible only on the "expiring closure" argument, which is itself conditional on M-01.

## ⚠ Classification: this is an EXPIRING CLOSURE, not a regression

**No patch was reverted. There is nothing to restore.** Nothing in this report should send a reader to restore a prior fix, because no prior fix is missing.

What has expired is the **rationale** behind two `wont-fix` closures — `43e8c48626ee74b51d538bd9ed12bf4898b976818f6fb44fea844ff3757daefe` and `858e9e807abee888b378db210bae982f23fe7b5d91052321e204d7ba568579b7`. ## Impact

```solidity
// src/BatchNFTMinterMultiToken.sol:146
uint256 internal constant DUST_THRESHOLD = 1e6;

// src/BatchNFTMinterMultiToken.sol:659-668
{
    uint256 available = paymentToken.balanceOf(address(this));
    uint256 refund = budget > available ? available : budget;
    if (refund / DUST_THRESHOLD != 0) {          // == refund >= 1e6
        paymentToken.safeTransfer(msg.sender, refund);
        totalPaid = paymentAmount - refund;
    } else {
        totalPaid = paymentAmount;               // surplus kept, silently
    }
}
```

Three properties compose into a defect none of them has alone:

1. **`DUST_THRESHOLD` is a raw-unit constant with no decimals normalisation**, while the payment token is *not fixed* — it is resolved dynamically as `ITokenDispatcherV2(dispatcher).primeToken()` (`_resolvePaymentPath`, `:705`).
2. **The gate is all-or-nothing**: a refund of `999,999` raw units is dropped in its entirety, exactly as `1` unit would be.
3. **Post-story-029 the refund is sourced from the per-call tracked `budget`**, so residue left by an earlier call is unreachable by any *later refund*.

**The escalating fact is that the 6-decimal arm is mandated upstream, not hypothetical.** `NudgeRatchet`'s constructor enforces it:

```solidity
// yield-claim-nft/src/dispatchers/NudgeRatchet.sol:84 @ d4cc563
require(IERC20Metadata(token_).decimals() == 6, "NudgeRatchet: token must be 6-decimal USDC");
```

— so on the dispatcher family this contract exists to serve, `DUST_THRESHOLD` is structurally *one whole payment token*, by upstream deploy-time enforcement. This is the default on the intended path, not a misconfiguration.

| `primeToken` decimals | `1e6` raw units equals | max forfeited per batch |
|---|---|---|
| 18 (phUSD) | `1e-12` token | `0.000000000000999999` |
| **6 (USDC, mandated by `NudgeRatchet`)** | **`1.000000` token** | **`0.999999` token** |

A **10¹² ratio** against an 18-decimal token. The NatSpec at `:142-145` documents only the benign 18-decimal arm.

**Concrete path**: prime token USDC, `price = 25.000000`, `nudgeSize = 10`. A caller batches `count = 4` with `paymentAmount = 100.500000` (a 0.5 USDC frontend quoting margin). `budget = 500000` at `:661`; `500000 / 1e6 == 0` so the else-branch is taken; no transfer is made; `totalPaid` is set to the full `100.500000`. The caller is reported as having spent their entire quote, 0.5 USDC stays behind, and it becomes part of the nudge pot.

**What story-029 changed, and why it matters here.** Post-029 the refund is sourced from the locally tracked `budget` — *this call's credit only* — rather than from `balanceOf`. That change is correct and is the point of the story. Its side effect is that residue left behind by a **prior** call becomes **un-refundable**: no later refund can reach it.

**Un-refundable is not irreversible.** The residue can still leave through `_payRewards` (the pot, on a qualifying batch) or through **`rescueERC20`, which is an ordinary owner call**. The owner can sweep it at any time. What is lost is the *caller's* route back, not the value.

The residue accretes into the standing pot `P` **monotonically, with no cap and no owner action**. And `P` is exactly the quantity that M-01's value-blind count-only gate releases in full.

**Crucially, that last sentence is the whole of this finding's Medium.** The residue accretes **in the payment token**. If the payment token is not also a whitelisted nudge token on that instance — M-01's arming precondition — the residue is **never snapshotted and never paid out**; it is inert value sitting in the contract awaiting `rescueERC20`. This finding does not stand alone at Medium.

| config | `C = nudgeSize × price` | break-even `P*` (`C` + ~21.60 gas) | @ max 0.999999/batch | @ realistic 0.5 USDC frontend slack |
|---|---|---|---|---|
| fixture: `price = 10`, `nudgeSize = 5` | 50.00 | 71.60 | **72 batches** | **144 batches** |
| mainnet: `price = 70`, `nudgeSize = 5` | 350.00 | 371.60 | **372 batches** | **744 batches** |

There are two independent channels arming the same condition. This one is the **slow** channel — **M-01 Leg 2**'s ratchet recycling arms it in 6-8 mints (metered over the streamer's `duration`). This channel matters because it **survives even if the ratchet wiring is removed**: it needs no dispatcher loop, no owner misconfiguration, and no adversary. Ordinary users, with ordinary frontend rounding slack, doing ordinary non-qualifying batches, are sufficient.

### The accounting misreport at `:666` (carried from L-01)

The caller is reported as having spent their **full quote** — `totalPaid = paymentAmount` — while part of it was retained. **No off-chain consumer can detect the forfeiture from the return value.** The documentation (`docs/multi-token-nudge.md:305-310`) describes the *destination* of the residue ("they stay behind as pot — which is the correct owner for them") but never the accounting misreport, so an integrator has no prompt to reconcile `totalPaid` against an observed balance delta. This is a distinct claim from the accretion, with a distinct fix, and survives even if the dust branch is left alone.

### Law-3 framing (carried from L-01)

Would a competent, non-malicious owner wiring the batch minter behind `NudgeRatchet` be surprised that per-batch refunds under one whole USDC vanish into the nudge pot while `totalPaid` reports the caller spent their full `paymentAmount`? **Yes.** Surprise implies footgun, and footguns are in scope. This is not an allegation of owner misconduct, and no malicious-owner vector is asserted.

Growth is accumulated as a **sum of positive deltas**, not an absolute level, so a qualifying drain cannot mask accretion between drains. A failing invariant with a deterministic, self-contained replay cannot be vacuous, so no mutation control is required for it; the harness additionally carries six named anti-vacuity tripwires, all of which held.

## Recommended Mitigation

Two parts. The second is the one that matters most, and it is operational rather than code.

### 1. Fix the dust branch

Make the branch **partial rather than all-or-nothing**, and make the threshold decimals-aware rather than a raw-wei constant:

```solidity
uint256 threshold = 10 ** (IERC20Metadata(address(paymentToken)).decimals() > 6
    ? IERC20Metadata(address(paymentToken)).decimals() - 6
    : 0);                                  // ~1e-6 of a whole token, at any decimals
```

or, minimally and with no metadata call, lower the constant to `1e2` — still dust at 6 decimals, still absorbs JS rounding slack, but caps the per-batch forfeiture at `0.000099` USDC instead of `0.999999`, a 10,000× reduction in the accretion rate. If the residue is deliberately retained, `totalPaid` at `:666` should report what was actually retained so integrators can reconcile it against an observed balance delta.

Alternative minimal forms (carried from L-01), any one of which closes the leak:

```solidity
// (a) scale the threshold off the resolved token
uint256 dust = 10 ** (IERC20Metadata(address(paymentToken)).decimals() / 3);

// (b) lower the constant to 1e2 — still dust at 6 decimals, still absorbs JS quoting slack
uint256 internal constant DUST_THRESHOLD = 1e2;

// (c) make the branch partial rather than all-or-nothing, and report honestly either way
totalPaid = paymentAmount - refund;   // set on both arms; forfeit only the sub-dust remainder
```

At minimum, `totalPaid` at `:666` should reflect what the caller actually retained, and the NatSpec at `:142-145` should document the 6-decimal arm alongside the 18-decimal one.

Note that fixing the dust branch **slows the accretion; it does not remove the exposure**. **M-01 Leg 2**'s ratchet channel arms the same condition in 6-8 mints and is unaffected by anything in this section. The durable fix for the exposure itself is M-01's value-aware payout cap.

### 2. Replace the safe-config assumption with a standing monitor

The closures at `43e8c486` and `858e9e80` rest on holding `Σ(pot_i) < nudgeSize × mintPrice`. That is not a configuration; it is a **quantity that drifts upward on its own**. It needs continuous observation, not a one-time check at triage:

- Monitor `IERC20(primeToken).balanceOf(batchMinter)` against `nudgeSize × price` on every live `BatchNFTMinterMultiToken` instance, on a schedule, with an alert threshold set well below break-even (e.g. `0.5 × nudgeSize × price`) so there is time to act.
- Sweep the residue with `rescueERC20` when it approaches the threshold, or fund the fix in part 1.
- Treat any alert as a re-rating event for both ledger entries rather than an operational nuisance — their own re-arm triggers are written in exactly these terms.

An alternative that removes the need for the monitor entirely: route forfeited residue somewhere that is **not** the pot the qualifying gate pays out — a treasury address, or an explicitly-tracked `forfeited` balance excluded from `_snapshotRewards`. That severs the self-feeding link at its source and leaves the residue's destination an owner decision rather than an emergent one.
