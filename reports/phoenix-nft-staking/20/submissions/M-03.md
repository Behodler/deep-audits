## Finding description and impact

### Summary

On `NFTStakerDepletion`, the per-second emission rate is derived as `budget / windowSeconds` and is
**independent of `totalStaked`**. During an in-place migration the pool is necessarily drained to zero
and then refilled one operator-chosen slice at a time, so the users in slice 1 split the **entire
pool-wide emission stream** among themselves while every later slice sits parked in the migrator
earning nothing — out of the same shared `rewardBudget`.

This is the same root-cause class as ledger finding `b58b172e2af4ec0851d1038f4c6c9e8b0c6433833ea58428b9b46e792c9718da`
(the run-18 linear-depletion rate-drift Medium, marked `fixed` at `321d0a9` by story-020), reached
through a different, untouched code path.

### Why this is filed as a POSSIBLE INCOMPLETE FIX

story-020 closed the **`unstake`** path. The **`migrateIn` → `depositFor`** path was not touched, and
the identical drift reproduces through it. Project law ranks an incomplete fix second only to a
regression, because *an incomplete fix is more dangerous than an unfixed bug — it reads as done.*

This is deliberately **not** filed as a literal REGRESSION: the fingerprint and the function surface
both differ (`depositFor`/`migrateIn` vs. the story-020-patched `stake`/`unstake` tail). Calling it a
regression would falsely imply story-020's patch broke. What is available is the incomplete-fix framing.

> ⚠ **Critical caveat — do not let the green replay read as coverage.**
> `PoC_DepletionRateDrift.t.sol` replays **3/3 GREEN** at `0d1a0b2`, with active and passive stakers
> receiving byte-identical totals. That result covers the **`stake`/`claim` accrual path** — the file
> imports only `NFTStakerDepletion` and never calls `migrateIn` or `depositFor`, so it does **not**
> exercise the migration path at all. It is **not** evidence that the linear-depletion class is closed,
> and it must not be cited against this finding. The two paths are independent.
> `tier3-and-poc-validation.md` §9 carries this caveat explicitly.

### Vulnerability details

`_recomputeSchedule` derives the rate with no reference to `totalStaked`
([`NFTStakerDepletion.sol#L512-L533`](https://github.com/Behodler/phoenix-nft-staking/blob/main/src/NFTStakerDepletion.sol#L512-L533)):

```solidity
uint256 windowSeconds = depletionWindowMonths * SECONDS_PER_MONTH;
...
uint256 budget   = V > committedDebt ? V - committedDebt : 0;
uint256 newRate  = (windowSeconds == 0) ? 0 : budget / windowSeconds;  // totalStaked-independent
rewardRate = newRate;
```

`depositFor` — the only re-injection entry point, reachable solely from
`InPlaceNFTStakerMigrator.migrateIn` — credits the slice and then calls `_recomputeSchedule` again
([`NFTStakerDepletion.sol#L748-L767`](https://github.com/Behodler/phoenix-nft-staking/blob/main/src/NFTStakerDepletion.sol#L748-L767)):

```solidity
function depositFor(address user, uint256 amount) external override nonReentrant onlyMigrator {
    require(amount > 0, "NFTStaker: zero deposit");
    require(poolState == PoolState.Active, "NFTStaker: not active");
    ...
    // Tail recompute: rate is `budget / windowSeconds`, totalStaked-independent
    _recomputeSchedule();
}
```

Sequence:

1. The operator calls `finalizeAndReset`, which requires `totalStaked == 0`
   ([`NFTStakerDepletion.sol#L778-L784`](https://github.com/Behodler/phoenix-nft-staking/blob/main/src/NFTStakerDepletion.sol#L778-L784)) — the pool
   is fully drained by construction.
2. Emissions resume the instant slice 1 is re-injected via
   [`InPlaceNFTStakerMigrator.migrateIn`](https://github.com/Behodler/phoenix-nft-staking/blob/main/src/InPlaceNFTStakerMigrator.sol#L186).
3. Because the rate is `totalStaked`-independent, the handful of slice-1 users receive the **full**
   pool-wide stream rather than their pro-rata share.
4. Slice-N users remain in the migrator's custody accruing nothing, while their share of the shared
   `rewardBudget` is consumed.
5. Payout is decided by which slice the operator assigned a user to — a variable no user controls and
   none can observe in advance.

### Impact

Value transfer between users out of a shared reward budget. Measured in
`PoC_EconMigrateReady.t.sol::test_ECON_G_depletionMigrateInOrderingOverPaysSliceOne`:

| Cohort | Received | Wall-clock exposure |
|---|---|---|
| slice-1 user | 48,977.29e18 phUSD | identical |
| slice-2 user | 40,758.11e18 phUSD | identical |

A **120%** ratio (slice-1 receives 1.20× slice-2) for identical exposure. Corroborating magnitudes on
adjacent surfaces in the same suite: **1000 bps** on the price-scaled copy (`test_ECON_A`) and
**1666 bps** self-advancing (`test_ECON_H`).

Protocol solvency is unaffected; the harm is redistribution among users, not loss to the protocol.

### Honest bounds

- **Likelihood:** certain on any staggered (multi-slice) migration of this contract. There is no
  attacker — ordinary operator slice ordering is the trigger. `test_ECON_C` measures ~426 users per
  30M-gas block, so a multi-slice migration is required above that population and is the expected shape.
- **Assumptions:** the migration spans more than one transaction, and `targetAPY` is non-zero during
  the staggered window.
- **External requirements:** none.
- **A clean remedy exists** and is cheap (below). It is simply not a documented runbook step today.

### Human arbitration required — both sides stated

The pipeline flagged this for human arbitration (DECISION-LOG D-24) rather than settling it. Both
readings are recorded here in full:

**For reopening `b58b172e…` as an incomplete fix.** The measured drift is the same root-cause class as
run-18's Medium and as the phlimbo-ea Linear-Depletion class. story-020 fixed one path; the class is
still reachable through another. A `fixed` disposition on the ledger currently signals that the class
is closed, and it is not.

**Against reopening — file as a separate Medium instead.** Run-18's finding was *automatic* drift on the
ordinary, permissionless `unstake` path: it fired with no one choosing it. This one is
*operator-chosen* slice ordering, during a migration the operator fully controls, with a clean and
free remedy (`setTargetAPY(0)` immediately after `finalizeAndReset`, restored after the last slice).
The trigger and the actor are genuinely different, which is why one reviewer proposed a
Low-with-Medium-ceiling reading.

**Weighing (recorded as reasoning, not as a settlement).** The counter-argument bears on *who* triggers
the drift, not on *whether* the class is closed. Operator control makes the remedy cheap and the
trigger predictable; it does not make the harmed users whole, and those users have no agency at all.
Combined with the incomplete-fix ranking, Medium is the honest floor — and the finding also stands
alone as a Medium on its own merits under C4 (a PoC-measured value leak between users, with stated
assumptions and no external requirements).

**A human must pick one of the two dispositions below.** An agent must not take either unilaterally.

## Recommended mitigation steps

**Operational (immediate, free, no code change).** Set `targetAPY` to `0` immediately after
`finalizeAndReset` and restore it only once the final `migrateIn` slice has landed. Emissions are then
zero for the whole staggered window, and slice order carries no economic weight. Document this as a
**mandatory** runbook step — the finding is precisely that it is not one today.

**Alternative (also sufficient).** Re-inject all parked users in a single `migrateIn` transaction where
population permits; `test_ECON_C` measures ~426 users per 30M-gas block.

**Structural (preferred, closes the class).** Suppress accrual for the duration of re-injection rather
than relying on the operator remembering. For example, keep `poolState` out of `Active` (or hold
`rewardRate` at zero) until an explicit `migrationComplete()` call by the owner, so that no window
exists in which a partially-refilled pool emits at the full `budget / windowSeconds` rate.

Whichever path is chosen, the ledger disposition for `b58b172e…` must be updated explicitly (see
"Pre-written dispositions"), so that the `fixed` status no longer implies the linear-depletion class is
closed while the migration path remains open.
