## F-20-01 — §4.5 "duplicates fail closed" is false under §4.2's own premise

**Escalate to the security pipeline.** This is a Law-1 override: the story's *intent* is unsafe,
not its implementation.

The spec asserts two things that cannot both be true:

> **§4.2** — "The dispatcher donates reward token into this contract on every mint... the donations
> generated by their own batch stay behind to seed the next claimant... it is **the only thing
> preventing a caller from funding their own reward within a single transaction**."

> **§4.5** — "**Duplicates** (`[USDC, USDC]`): both entries snapshot the same balance. The first
> transfer drains it; the second either reverts on insufficient balance or transfers into a
> now-empty pot. **Either way it fails closed and harms only the caller.** No dedupe pass."

§4.5's reasoning silently assumes the balance at payout equals the balance at snapshot. §4.2 says it
does **not** — the gap is exactly the batch's own donations `D`. So with snapshot `B` and `k`
duplicate entries, the payout pass transfers `k·B` against a live balance of `B + D`, and succeeds
whenever `k·B ≤ B + D`. The caller recaptures up to **100% of their own donations**, at zero
marginal mint cost relative to an honest single-entry claim.

Implementation is faithful to §4.5 (`src/BatchNFTMinter.sol:429` snapshots per element with no
dedupe; `:452-461` pays each entry unconditionally), so the defect is the spec clause.

**Proven, not argued** — `workspace/phoenix-nft-staking/test/PoC_DuplicateRewardWithDonations.t.sol`, both PASS:

- `test_DuplicateDoesNotFailClosedWhenDispatcherDonates` — B = 3e6, D = 15e6, 2 entries →
  recipient receives `2·B`; contract left with `D − B` instead of `D`.
- `test_ManyDuplicatesDrainOwnDonationsEntirely` — 6 entries → contract balance **0**;
  batcher takes `priorPot + all of its own donations`. Nothing remains to seed the next claimant.

**Production-live, not mock-only.** The pinned `DISPATCHER_INDEX = 4` is `BalancerPoolerV2`, whose
`primeToken()` is USDS while it forwards a `donationSplit`% **USDC** cut to `batchMinter` on every
dispatch. USDC is therefore a legal reward token (the §4.1 exclusion does not fire) *and* is donated
per mint — the exact configuration the PoC models.

**Impact:** protocol-funded incentive (SYA 30% USDC drip + the dispatcher's secondary cut) is
recaptured by the batcher that generated it. The donate-forward mechanic collapses into the "no-op
round-trip" §4.2 was written to forbid. No user principal at risk.

**Fix direction:** dedupe into a payout map, or pay `min(snapshot[i], liveBalance)` with subsequent
duplicates zeroed. **Trap:** do *not* implement this as a naive `balanceOf` re-read at the payout
site — that is precisely the §4.2 refactor trap and would hand every batcher its full donation back.

## F-20-03 — `NFTStakerDepletion.depositFor` still pays the migrator, not the user

**Escalate to the security pipeline.** story-021's own commit body says:

> "`depositFor` settles existing pending via `_safePayTo(user, ...)` rather than `_safePay(...)`,
> **which would pay the migrator**."

and the new contract's NatSpec elaborates that the `_safePay` form "would route an existing staker's
earned phUSD to the orchestrator while emitting `Claimed(user, ...)` ... **wrong in every case**."

The story then declares `NFTStakerDepletion.sol` untouched — verified true (`git show --stat f65aec9`
lists three files, all new). So the fix landed **only in the new fourth copy**. The original still has:

```solidity
// src/NFTStakerDepletion.sol:748-758
function depositFor(address user, uint256 amount) external override nonReentrant onlyMigrator {
    ...
    if (info.amount > 0) {
        uint256 pending = (info.amount * accRewardPerShare) / ACC_PRECISION - info.rewardDebt;
        if (pending > 0) {
            pending = _safePay(pending);          // <-- pays msg.sender == the MIGRATOR
            if (pending > 0) emit Claimed(user, pending);   // <-- event names the USER
        }
    }
```

`_safePay` delegates to `_safePayTo(msg.sender, …)` (`:593-595`), and under `onlyMigrator`
`msg.sender` is the orchestrator.

**Reachability:** `InPlaceNFTStakerMigrator.migrateIn` (`:226`) and `NFTStakerMigrator.migrate`
(`:102`) both call `depositFor`. The `info.amount > 0` branch fires whenever the deposit target
already holds a position — e.g. a parked user who re-staked directly between `finalizeAndReset` and
`migrateIn`, or a user migrating into a staker they are already in.

**Recoverability is asymmetric:**
- `InPlaceNFTStakerMigrator` has an unconditional owner `rescueERC20` (`:268`) → recoverable.
- `NFTStakerMigrator` has **no rescue function at all** — its only externals are `initiateMigration`
  and `migrate` → phUSD routed there is **permanently stranded**.

Plus a false `Claimed(user, …)` event and a `committedDebt` decrement recorded as if the user were paid.

**Fix:** one line — `_safePayTo(user, pending)` at `NFTStakerDepletion.sol:756`.

## F-20-04 — WATCH-17 maintenance-coupling drift: **recurrence, and now materialised**

The Law-1 override question posed on story-021's intent ("is a fourth hand-maintained 1000-line copy
itself a hazard?") answers itself: **F-20-03 is that hazard, realised inside the very commit that
created the copy** — and in the direction the watch note did not anticipate. WATCH-17 was framed as
"a future fix to `NFTStaker` won't propagate to the clones". What actually happened is the mirror
image: a fix was authored *in the clone* and never back-ported to the original that is wired to the
live migrators.

This is a **recurrence** of `WATCH-17-maintenance-coupling-drift` (opened run-17 for the PriceScaled
clone, widened run-18 to two clones), not a new class. It should now be widened to **three** clones
and promoted from watch-note to active hazard with a demonstrated instance.

Under Law 3 the no-shared-base design decision is the owner's and is not re-litigated here. What *is*
in scope is the non-obvious consequence: a competent, non-malicious maintainer fixing
`NFTStakerDepletion` has no signal that the correct code already exists 200 lines away in another file.

**Next-run obligation:** diff all four stakers pairwise (`NFTStaker`, `NFTStakerPriceScaled`,
`NFTStakerDepletion`, `NFTStakerPriceScaledMigrateReady`), not just the two the run-18 note names.

## F-20-05 — §4.1's threat model overstates what the guard protects

The §4.1 guard is implemented exactly as specified (`:426-428`, unconditional, per-element, ahead of
any fund movement) and its narrow claim about **sub-threshold** dust holds. But §4.1 also says the
guard "is **the thing** standing between a caller and the payment-token balance held mid-transaction."
That is not true: step 10's dust sweep already gives the contract's *entire* payment-token balance to
`msg.sender` whenever it is ≥ `DUST_THRESHOLD` (1e6 wei ≈ 1e-12 USDS), on a `count == 1` call with
empty arrays and **no `nudgeSize` qualification at all**.

Proven (`PoC_PaymentTokenSweep`, PASS): 500 USDS donated to the contract is swept in full to a
non-qualifying caller, and `batchMint` returns `totalPaid == 0` while the caller is net positive.

**This is not a code deviation.** The sweep is pre-existing, explicitly preserved by §4.6, and
documented in the contract itself (`:68` — "A griefer who pre-deposits payment-token to this contract
simply donates to the next caller"). Only the doc's justification is wrong. Fix the prose, not the code.

## F-20-06 — removing the deploy-time collision guard is not equivalent to the on-chain check

The script now says the old guard is gone because "that collision is now checked **ON-CHAIN**, per
call". The on-chain check reverts the **caller**; it does not warn the **operator**. If
`DISPATCHER_INDEX` is repointed to a dispatcher whose `primeToken()` equals the token it donates to
`batchMinter`, the nudge becomes structurally dead — every claim reverts
`BatchMint__RewardTokenIsPaymentToken` — and the accumulated pot leaks instead to whoever next runs a
1-mint batch (F-20-05).

Not hypothetical: `yield-claim-nft/src/dispatchers/PromotionUniV2_Eth.sol` has
`primeToken() == USDC` (`:189`) **and** donates USDC to `batchMinter` (`:340`); `NudgeRatchet.sol`
likewise forwards USDC to `batchMinter`. Only the currently-pinned `BalancerPoolerV2` (USDS prime,
USDC donation) is safe — and the script's own NatSpec flags `DISPATCHER_INDEX = 4` as
"ASSUMED … the operator MUST confirm", i.e. a repoint is an expected operation.

Law-3 test: would a competent, non-malicious operator be surprised? Yes → footgun → in scope.

**Fix:** restore an operator-facing deploy assertion resolving
`configs(DISPATCHER_INDEX).dispatcher.primeToken()` and comparing it against the intended reward asset.
