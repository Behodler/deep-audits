# [M-01] Understated registered `decimals` fails OPEN, arming a permissionless free mint

**Ledger fingerprint:** `a1c81428a47ad295`
**Severity:** Medium (top of band)
**Location:** `lib/antimatter/src/Antimatter.sol:250`, `:254`, `:256` (function body `:246-257`)
**Root cause class:** `UnvalidatedRegisteredDecimalsFailsOpen`

## Finding description and impact

### Summary

`toStableAmount` computes how much stablecoin pairs with a given quantity of antimatter using a `decimals` value read verbatim from `PhusdStableMinter.stablecoinConfigs` (`Antimatter.sol:250`). Antimatter holds the token address and never cross-checks it against `IERC20Metadata(stable).decimals()`. If the registered value is **understated**, the pairing collapses by the corresponding power of ten and nothing reverts — the misconfiguration fails **open**, at full phUSD issuance.

### Vulnerability details

```solidity
(address yieldStrategy,, uint8 decimals,,,,) = minter.stablecoinConfigs(stable);   // :250 trusted verbatim
if (yieldStrategy == address(0)) revert StablecoinNotRegistered(stable);
if (decimals > 18) revert UnsupportedDecimals(decimals);

uint256 scale = 10 ** (18 - decimals);                                            // :254
uint256 stableAmount = amount / scale;
if (stableAmount * scale != amount) revert AmountNotRepresentable(amount, decimals); // :256
```

Register an 18-decimal stablecoin with `decimals = 6` and `scale` becomes `1e12`, so the stablecoin pulled at `:222` is 1e12 times too small. Crucially, **both contracts make the identical error**, so it cancels inside `PhusdStableMinter.calculateMintAmount`: the residue check at `:230` passes (the stablecoin genuinely left Antimatter), the non-zero receipt check at `:233` passes (phUSD genuinely arrived), and the exactness guard at `:256` passes. There is no revert, no anomalous event, and no on-chain signal of any kind.

Post-arming, exploitation is **permissionless, deterministic and unbounded**: any antimatter holder mints ~2x phUSD while surrendering ~1e-12 of the intended stablecoin, repeatable up to the entire outstanding antimatter supply.

### The asymmetry is what makes this a footgun, not an obvious misconfiguration

This is assessed under Law 3 (the owner is trusted for *knowing* actions; non-obvious footguns are in scope). The test is whether a competent, non-malicious owner would be **surprised**.

The same mistake in the **other** direction *usually* reverts: with `decimals` overstated, the computed pull is orders of magnitude too large and `safeTransferFrom` reverts. **This must be stated precisely, because it is not a guard.** Nothing in Antimatter or the minter validates the direction; the revert traces to `ERC20InsufficientBalance` raised by the token's own `transferFrom`, i.e. it is an accident of the caller's balance, not a check. A caller who *is* sufficiently funded is **silently over-charged by ~1e12x** — no revert at all — so the overstated direction is better described as *incidentally noisy for ordinary balances* than as failing closed.

The asymmetry that makes this a footgun therefore survives, but on a narrower basis: an owner who mis-types `decimals` will, in the overwhelmingly common case, see a loud balance revert in one direction and **complete silence at full phUSD issuance** in the other, giving positive but false reason to believe the parameter is self-checking. Surprise means footgun, which is in scope at honest severity. Severity is unchanged at Medium — only the strength of the "fails closed" evidence is corrected. This finding therefore explicitly overrides the faithfulness tier's Law-3 suppression of the same item as "the minter owner's obvious single-step act" — it is not obvious precisely because it is silent.

No malicious-owner vector is claimed anywhere in this report.

### Impact

While armed: any antimatter holder mints ~2x phUSD while surrendering dust. The stable leg — the half that is supposed to be fully collateralised — becomes backed by ~1e-12 of the intended amount. The exposure is unbounded in size (up to the entire antimatter supply) and unbounded in time, since nothing signals the condition. The loss lands on phUSD holders as collateral dilution.

### Severity justification

**Medium**, and the reason it is not High is stated plainly rather than hedged. The post-arming exploit is permissionless, deterministic and unbounded — genuinely High-shaped — which is why this sits at the **top** of the Medium band. It stays Medium because the path is not free of external requirements: it needs a registration misconfiguration that no observed deployment has. C4 Medium covers exactly "a hypothetical attack path with stated assumptions, but external requirements". It is not Low: the consequence is neither dust nor cosmetic, but an unbounded permissionless free mint against the collateral base.

It is also **not** a "weird ERC20" finding — the token is entirely standard. The defect is unvalidated trust in a registered configuration value.

**Re-weigh trigger:** escalate to **High** on evidence that any live or staged registration carries a `decimals` value differing from `IERC20Metadata(stable).decimals()`. At that point the external requirement is satisfied and the remaining path is permissionless.

**Assumptions:** a registered stablecoin's configured `decimals` is understated relative to its true ERC20 decimals; antimatter emission is live enough that some holder holds antimatter.

**External requirement:** the owner misconfiguration occurs in `PhusdStableMinter.registerStablecoin`, a nested-submodule contract. It is filed against Antimatter because Antimatter acts on the value, doubles the blast radius by adding a second uncollateralised leg, and can defend itself in one line.

The intentional control provides no protection here.

## Recommended mitigation

Cross-check the registered value in `toStableAmount`, so the dangerous direction fails closed like the safe one already does:

```solidity
(address yieldStrategy,, uint8 decimals,,,,) = minter.stablecoinConfigs(stable);
if (yieldStrategy == address(0)) revert StablecoinNotRegistered(stable);
if (decimals > 18) revert UnsupportedDecimals(decimals);

try IERC20Metadata(stable).decimals() returns (uint8 actual) {
    if (actual != decimals) revert DecimalsMismatch(stable, decimals, actual);
} catch {
    revert DecimalsUnavailable(stable);   // a token with no decimals() must not be annihilatable
}
```

One `staticcall` on a token address the contract already holds. Reverting (rather than preferring the token's own value) is the correct choice: a disagreement between the registry and the token is a configuration fault that a human must resolve, not one the contract should paper over.

Secondarily, validate `decimals` against `IERC20Metadata` at registration time in `PhusdStableMinter.registerStablecoin` as well, so the fault is caught before it is ever armed rather than at first use.
