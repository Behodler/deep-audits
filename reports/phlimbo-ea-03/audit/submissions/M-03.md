## Finding description and impact

### Summary

`PhlimboEA._claimRewards` settles a user's accrued phUSD reward by calling `phUSD.mint(user, pendingPhUSDAmount)` directly, with no `try/catch`, no fallback path, and no per-user accounting of un-mintable balances. The sibling phUSD contract is a Phoenix-ecosystem token that exposes `revokeAllMintPrivileges()` as a documented, intentional kill-switch — it is a protocol-design lever, not an operational accident. Once that lever is pulled (or minting is otherwise made unavailable, e.g. paused or supply-capped), every user-facing entrypoint that funnels through `_claimRewards` — `claim`, `stake`, `withdraw` — reverts for any staker with non-zero accrued phUSD. The only remaining exit is `pauseWithdraw`, which is gated behind the pauser role and forfeits all accrued rewards (stable and phUSD), since it does not pass through `_claimRewards`.

### Vulnerability details

`_claimRewards` (Phlimbo.sol, L432-L455):

```solidity
function _claimRewards(address user) internal {
    UserInfo storage userDetails = userInfo[user];

    if (userDetails.amount == 0) {
        return;
    }

    // Calculate pending phUSD
    uint256 pendingPhUSDAmount =
        (userDetails.amount * accPhUSDPerShare) / PRECISION - userDetails.phUSDDebt;
    if (pendingPhUSDAmount > 0) {
        phUSD.mint(user, pendingPhUSDAmount);              // <-- L442: unconditional external call
    }

    // Calculate pending reward tokens (stable)
    uint256 pendingRewardAmount =
        (userDetails.amount * accStablePerShare) / PRECISION - userDetails.stableDebt;
    if (pendingRewardAmount > 0) {
        rewardToken.safeTransfer(user, pendingRewardAmount); // <-- never reached on mint revert
    }
    ...
}
```

Because the call at L442 is unguarded, any revert from `phUSD.mint` reverts the entire transaction, regardless of which outer entrypoint invoked `_claimRewards`. Three entrypoints route through it:

- `claim()` (L374-L381) — calls `_claimRewards(msg.sender)` directly.
- `withdraw(uint256)` (L334-L369) — calls `_claimRewards(msg.sender)` at L341 *before* transferring principal back to the user.
- `stake(uint256, address)` (L295-L328) — calls `_claimRewards(recipient)` at L309 whenever the recipient already has a non-zero position.

The trigger we focus on, `phUSD.revokeAllMintPrivileges()`, is part of the published phUSD interface. It is a sibling-contract, protocol-level governance action — *not* an action by Phlimbo's own owner. The C4 "reckless admin mistake" exclusion therefore does not apply: the mint authority is a defensive lever Phoenix exposes deliberately (e.g. to contain a downstream incident), and any consuming staking contract is required to remain composable with it. Phlimbo currently treats `phUSD.mint` as if it were infallible.

Once revocation occurs, the only remaining exit is `pauseWithdraw`. That path has two asymmetric costs that make it an incomplete recovery:

1. It requires the pauser role to first pause the contract — users cannot self-rescue.
2. It deliberately bypasses `_claimRewards`, so it returns principal but **forfeits all accrued rewards** — both the phUSD that could not be minted *and* the stable rewards which are sitting unblocked on the contract and would otherwise transfer cleanly via `rewardToken.safeTransfer` at L448.

The stable reward leg is independent of the mint authority and would succeed on its own. The current code couples it to the phUSD leg by ordering and by lack of `try/catch`, so a single revocation forfeits value that is otherwise fully recoverable.

### Why this is not "owner mistake" / out-of-scope

- The trigger is an action by **phUSD's governance**, a sibling protocol that Phlimbo depends on. It is not under Phlimbo's owner's control.
- `revokeAllMintPrivileges()` is a documented, deliberate primitive in phUSD's interface — not a misconfiguration. Consumers of phUSD are expected to handle it gracefully.
- The same code path also reverts under unrelated mint-failure modes (mint paused, supply cap reached, role revoked under any future role-model change), so the bug is not contingent on the kill-switch being pulled — it is contingent on *any* `phUSD.mint` revert, of which the documented kill-switch is just the most concrete instance.

### Impact

- **Severity: Medium.** Direct theft is not possible; the issue is a protocol-availability and value-leak failure conditional on a sibling-contract action.
- **Availability:** All three user-facing entrypoints (`claim`, `stake`, `withdraw`) become unusable for every staker with non-zero accrued phUSD for the duration of the mint outage.
- **Value leak:** Principal is recoverable via `pauseWithdraw`, but accrued rewards are forfeited even though the stable component is fully transferable and the phUSD component could be deferred to a later mint.
- **Operational:** Users cannot self-rescue; recovery requires pauser cooperation and silently zeroes their reward debt, so even a later restoration of mint authority does not retroactively make stakers whole.

### Proof of Concept

The PoC at `workspace/phlimbo-ea/test/poc-M-03-mint-revocation-bricks.t.sol` deploys a `MintRevokableMockFlax` that mirrors phUSD's documented `revokeAllMintPrivileges()` kill-switch and exercises the failure mode against the audited commit. Five tests demonstrate the bricking and the asymmetric escape:

- **Baseline** — with mint authority intact, `claim()` succeeds and the staker receives phUSD as expected.
- **`claim()` bricked** — after the sibling calls `revokeAllMintPrivileges()`, `claim()` reverts; accrued rewards become unclaimable.
- **`withdraw()` bricked** — `withdraw(amount)` reverts on the same path; the staker's full principal remains stuck in Phlimbo's `userInfo` mapping.
- **`stake()` bricked on top-up** — a follow-up `stake(...)` to an existing position reverts, because `stake` routes through `_claimRewards` when the recipient already has a non-zero balance.
- **`pauseWithdraw` is an asymmetric escape** — once the pauser pauses the contract, the staker's `pauseWithdraw` returns principal in full, but the independently-transferable stable rewards (`usdc.balanceOf(staker) == 0` post-exit) are forfeited despite never having depended on the phUSD mint authority.

Note: the revert string asserted in the PoC, `"Flax: mint privileges revoked"`, is the PoC mock's emulated revert message used to model the documented kill-switch — it is not the literal production phUSD revert string. The kill-switch behaviour itself (any revert from `phUSD.mint` propagating up through `_claimRewards` and bricking the three entrypoints) is the documented behaviour the PoC validates; the exact revert message is harness-specific.

## Recommended mitigation steps

Wrap the `phUSD.mint` call in `try/catch` and decouple it from the (independent and unaffected) stable-reward `safeTransfer` leg. Two equivalent shapes both fix the core failure mode; option (a) is the minimal change and option (b) preserves full value for users:

**(a) Skip the phUSD leg on failure, still settle stable rewards, and log.**

```solidity
function _claimRewards(address user) internal {
    UserInfo storage userDetails = userInfo[user];
    if (userDetails.amount == 0) return;

    uint256 pendingPhUSDAmount =
        (userDetails.amount * accPhUSDPerShare) / PRECISION - userDetails.phUSDDebt;
    uint256 mintedPhUSD = 0;
    if (pendingPhUSDAmount > 0) {
        try phUSD.mint(user, pendingPhUSDAmount) {
            mintedPhUSD = pendingPhUSDAmount;
        } catch {
            emit PhUSDMintFailed(user, pendingPhUSDAmount);
            // Intentionally do not revert: stable rewards and the outer
            // claim / stake / withdraw entrypoint must remain operational.
        }
    }

    uint256 pendingRewardAmount =
        (userDetails.amount * accStablePerShare) / PRECISION - userDetails.stableDebt;
    if (pendingRewardAmount > 0) {
        rewardToken.safeTransfer(user, pendingRewardAmount);
    }

    if (mintedPhUSD > 0 || pendingRewardAmount > 0) {
        emit RewardsClaimed(user, mintedPhUSD, pendingRewardAmount);
    }
}
```

**(b) Same as (a), but also credit the un-mintable phUSD to a per-user `owedPhUSD` ledger so users can be made whole once mint authority is restored.**

```solidity
mapping(address => uint256) public owedPhUSD;

// inside the catch:
owedPhUSD[user] += pendingPhUSDAmount;
emit PhUSDMintDeferred(user, pendingPhUSDAmount);

// new entrypoint:
function settleOwedPhUSD(address user) external whenNotPaused {
    uint256 owed = owedPhUSD[user];
    require(owed > 0, "Nothing owed");
    owedPhUSD[user] = 0;
    phUSD.mint(user, owed); // reverts if still revoked, which is fine — owed is restored on revert
}
```

In both options, the `phUSDDebt` accumulator should only be advanced for amounts actually credited (either minted or recorded as owed). The stable-reward `safeTransfer` path is independent of phUSD's mint authority and must remain reachable when `phUSD.mint` fails — that is the core invariant the fix preserves.

A secondary recommendation: revisit `pauseWithdraw` so that, when invoked, it at minimum settles the stable-reward leg (and, under option (b), the deferred phUSD ledger). Today it silently zeroes a position whose rewards are recoverable, which is an avoidable value leak even in the non-revocation paused state.
