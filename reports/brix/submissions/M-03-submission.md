# [M-03] Vesting Amount Update Race Condition Prevents Timely Yield Distribution

## Severity
Medium

## Location
[StakediTry.sol#L280-L285](https://github.com/code-423n4/2025-11-brix-money-c4-audit/blob/68bf3dc/src/token/wiTRY/StakediTry.sol#L280-L285)

## Summary
The `_updateVestingAmount()` function in StakediTry.sol reverts with `StillVesting()` if any unvested amount remains from the previous distribution. This creates a race condition where yield distributions are artificially constrained to occur no more frequently than the vesting period duration (minimum 1 hour, maximum 30 days), even when new yield becomes available.

## Vulnerability Details
The vulnerable code pattern enforces that all previous yield must be fully vested before accepting new yield:

```solidity
function _updateVestingAmount(uint256 newVestingAmount) internal {
    if (getUnvestedAmount() > 0) revert StillVesting();

    vestingAmount = newVestingAmount;
    lastDistributionTimestamp = block.timestamp;
}
```

This function is called by two critical operations:
1. `transferInRewards()` - when the REWARDER_ROLE distributes new yield to stakers (line 114)
2. `redistributeLockedAmount()` - when locked shares are burned and redistributed (line 176)

The vesting check uses a linear time-based calculation:

```solidity
function getUnvestedAmount() public view returns (uint256) {
    uint256 timeSinceLastDistribution = block.timestamp - lastDistributionTimestamp;

    if (timeSinceLastDistribution >= vestingPeriod) {
        return 0;
    }

    uint256 deltaT;
    unchecked {
        deltaT = (vestingPeriod - timeSinceLastDistribution);
    }
    return (deltaT * vestingAmount) / vestingPeriod;
}
```

With vesting periods configured between 1 hour and 30 days (constants `MIN_VESTING_PERIOD` and `MAX_VESTING_PERIOD` on lines 34-36), this creates a hard constraint on distribution frequency.

**Attack/Failure Scenario:**
1. Admin distributes 100 ETH yield via `transferInRewards()` at T=0
2. Vesting period is set to 7 days (604,800 seconds)
3. At T=6.9 days, another 50 ETH becomes available for distribution
4. Admin attempts to call `transferInRewards(50 ether)` but transaction reverts with `StillVesting()`
5. Admin must wait until T=7 days for the previous vesting to complete
6. During this waiting period, stakers are deprived of their rightful yield

## Impact
The race condition creates several operational issues:

1. **Yield Distribution Delays**: Stakers cannot receive new yield promptly when it becomes available, forcing them to wait for the entire vesting period to complete first.

2. **Reduced Distribution Frequency**: The protocol is artificially limited to one distribution per vesting period, regardless of how frequently yield is generated by the underlying protocol.

3. **Gas Inefficiency**: The REWARDER_ROLE must either wait for perfect timing (exactly when vesting completes) or retry transactions multiple times, wasting gas on failed attempts.

4. **Compounding Effects**: With longer vesting periods (up to 30 days), the delay between distributions can be significant. If yield is generated weekly but vesting is set to 30 days, 3-4 yield distributions will be queued and delayed.

5. **Locked Amount Redistribution Failures**: When burning locked positions via `redistributeLockedAmount()`, the operation will fail if any vesting is active, preventing timely cleanup of restricted staker positions.

While this does not result in direct loss of funds (the yield is eventually distributed), it represents a functional impairment of the protocol's core feature - timely yield distribution to stakers.

## Recommended Mitigation
Accumulate new vesting amounts instead of blocking them. Replace the revert with additive vesting:

```solidity
function _updateVestingAmount(uint256 newVestingAmount) internal {
    // Calculate any remaining unvested amount
    uint256 unvested = getUnvestedAmount();

    // Add new vesting to unvested amount
    vestingAmount = unvested + newVestingAmount;

    // Reset vesting timer
    lastDistributionTimestamp = block.timestamp;
}
```

This allows the contract to:
1. Accept new yield at any time
2. Preserve the vesting mechanism for stakers
3. Accumulate multiple distributions smoothly
4. Avoid artificial timing constraints

**Example with fix:**
- T=0: Distribute 100 ETH (vesting 100 over 1 hour)
- T=30min: 50 ETH vested, 50 ETH unvested
- T=30min: Distribute 50 ETH (now vesting 100 total: 50 unvested + 50 new)
- T=60min: 50 ETH vested, 50 ETH unvested
- T=90min: All 150 ETH fully vested

This maintains the vesting timeline for stakers while removing the artificial distribution frequency limit.

Alternative mitigation: Allow admin to configure whether to accumulate or reject during vesting, providing operational flexibility based on the protocol's yield generation patterns.
