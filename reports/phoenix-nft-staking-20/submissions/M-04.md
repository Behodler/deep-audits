## Finding description and impact

### Summary

An in-place migration necessarily drains the staking pool to zero — `finalizeAndReset` requires
`totalStaked == 0` — and then refills it one operator-chosen slice at a time via
`InPlaceNFTStakerMigrator.migrateIn`. Emissions resume the instant slice 1 lands, but slice-N users are
still in the migrator's custody earning nothing. Because the reward budget is shared, what slice-1
users collect is drawn from the same `rewardBudget` that funds every later user's runway.

Time-in-pool — and therefore payout — is decided entirely by which slice the operator puts a user in: a
variable no user controls and none can observe in advance.

### Vulnerability details

`migrateIn` re-injects an operator-chosen `[start, end)` slice of the parked-user set
([`InPlaceNFTStakerMigrator.sol#L186-L200`](https://github.com/Behodler/phoenix-nft-staking/blob/main/src/InPlaceNFTStakerMigrator.sol#L186-L200)):

```solidity
function migrateIn(uint256 start, uint256 end) external onlyOwner nonReentrant {
    uint256 len = _parkedUsers.length;
    if (end > len) { end = len; }
    require(start <= end, "InPlace: bad range");
    ...
}
```

The target staker must already be back in `Active` for `depositFor` to succeed, and `finalizeAndReset`
is gated on a fully-drained pool
([`NFTStakerPriceScaledMigrateReady.sol#L925-L929`](https://github.com/Behodler/phoenix-nft-staking/blob/main/src/NFTStakerPriceScaledMigrateReady.sol#L925-L929)):

```solidity
function finalizeAndReset() external onlyOwner {
    ...
    require(totalStaked == 0, "NFTStaker: stake outstanding");
    ...
    poolState = PoolState.Active;
}
```

So the ordering is forced: drain → reset to `Active` (emissions live) → refill slice by slice.
Every second between slice 1 landing and slice N landing is a second in which slice-1 users accrue
against a near-empty pool, out of a budget shared with users who are not yet in it.

### Impact

Value transfer between users from a shared `rewardBudget`. Measured in
`PoC_EconMigrateReady.t.sol::test_ECON_A_migrateInOrderingIsAValueTransfer`:

| Cohort | Received | Wall-clock exposure |
|---|---|---|
| Alice (slice 1) | 40.685 phUSD | identical |
| Bob (slice 2) | 36.986 phUSD | identical |

**1000 bps** edge with a 3-day operational lag. Scaled to the configured ceiling — `MAX_TARGET_APY`
(50%) with a 7-day staggered migration — the transfer reaches **~0.96% of migrated notional**.

**Protocol solvency is unaffected** (asserted directly in the PoC). The harm is redistribution between
users, not a loss to the protocol, and no value leaves the system.

### Honest bounds

- **Likelihood:** certain on any multi-slice migration. Magnitude scales linearly with `targetAPY` and
  with the gap between the first and last slice; at `targetAPY == 0` it is exactly zero.
- **Assumptions:** `targetAPY` non-zero during the staggered window, and the migration spans more than
  one transaction.
- **External requirements:** none — purely internal operational sequencing.
- **Not centralization, and not a malicious-owner finding.** "You are not staked, you do not earn" is a
  defensible rule. What makes this reportable is that the *operator*, not the user, chose the un-staked
  interval, via a migrate-on-behalf primitive the user cannot opt out of or observe in advance. It is
  an operational hazard (footgun) with a clean remedy.
- **Severity dispute, disclosed.** The scanner proposed **Low** with a Medium ceiling; classification
  raised it to **Medium** under DECISION-LOG D-10. The Low reading rests entirely on the availability
  of the clean operator remedy. The Medium reading rests on the harmed party having **zero agency**:
  a slice-N user can neither observe nor influence their assignment. The dedup record pre-authorised a
  `medium` ceiling, so this is within band.

- **Different actor** — operator slice assignment (M-04) vs. a user advancing themselves (M-08).

**Do not treat a fix for one as closing the other.** Each requires its own verification.

## Recommended mitigation steps

**Primary (free, immediate).** Set `targetAPY` to `0` immediately after `finalizeAndReset` and restore
it only after the final `migrateIn` slice has landed. Emissions are zero across the whole staggered
window, so slice order carries no economic weight.

**Alternative.** Re-inject every parked user in a single `migrateIn` transaction where the population
allows: `test_ECON_C` measures ~426 users per 30M-gas block, so single-transaction re-injection is
viable for most realistic cohorts.

Whichever is chosen, **document it as a MANDATORY runbook step**. The finding is that it is not one
today; the code offers no guard rail if the operator forgets.

**Structural (optional, removes the reliance on operator discipline).** Introduce an explicit
"re-injection in progress" state in which emissions do not accrue, exited only by an owner call once
the last slice has landed. This removes the window entirely rather than relying on the operator
remembering to zero the APY.

**Do not** address this by removing `userMigrate`'s permissionlessness — that is a load-bearing
frozen-state escape hatch, and it belongs to M-08's surface, not this one.
