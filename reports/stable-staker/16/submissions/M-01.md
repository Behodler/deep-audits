## Why the mitigation is rejected, and why the same reasoning collapses the severity

The owner rejects the recommended mitigation — *book to `unclaimedReward` instead of minting inline in
`_exitPosition`* — on the grounds that **fail-loud is the correct behaviour on this path**. That is not
a concession about the mechanics; it is a different reading of what the mechanics mean.

1. **The fix does not deliver the Antimatter.** `claim` (`StableStakerV2.sol:385`) is **itself a mint
   site**, so a booked `unclaimedReward` balance is still unmintable while the minter is revoked.
   Booking does not give users their AM — it lets them exit *without* it, moving the failure from
   **loud-and-now** to **silent-and-later**, landing on the user with no recourse.
2. **The fix manufactures more of a class this same run already filed.** `L-07` (`ss16l7`) and `F-03`
   are the **backlog-stranding class**: a settled `unclaimedReward` on a staker later paused, retired,
   or de-approved is permanently stranded. Routing the migration exit into `unclaimedReward` feeds
   exactly that channel.
3. **The operation is attended and permissioned.** `initiateMigration`, `batchMigrate` and
   `userMigrate` are all `onlyMigrator` (`:178-181`), the migrator being a thin owner-only forwarder.
   An operator is present, and the revert `Antimatter.NotApprovedMinter` (selector **`0x6830132b`**) is
   an **immediate, named alarm** that something important was disabled — a working signal, not a defect.
4. **Story-022 already decoupled the paths that matter.** `withdraw` **books** rather than mints
   (`:361-363`), so ordinary principal return never depends on Antimatter. The migration exit is the
   **deliberate exception**, and it is the one path with an operator watching.

**Net impact.** An attended, permissioned migration **halts loudly** and resumes after a single
`setApprovedMinter(staker, true)`. The permanent branch requires `renounceOwnership`, whose
irreversibility is **obvious on its face** → Law 3 says that is the owner's own affair, not a finding.

## Finding description and impact

### Summary

While a pool is `Migrating`, `_exitPosition` is the **sole** path by which principal can leave the contract — and it mints Antimatter **inline**, before releasing the principal. If that mint reverts, that user's exit reverts, and there is no hatch of any kind.

**The precise scope of the freeze — stated with its gate, not rounded up.** The mint is guarded by `if (owed > 0)` at `:619`, so the trap bites **per user, on any user with a non-zero `owed`** (accrued pending plus `unclaimedReward` backlog). A user with `owed == 0` — no rewards accrued and no backlog — exits cleanly. In practice that gate is satisfied for every user who has accrued anything, which is every user of an armed pool that has run for any length of time, and it is the condition the PoC demonstrates. Two amplifiers make the practical result the whole pool rather than a subset: `batchMigrate` reverts the **entire batch** when any one member trips the mint, and `finalizeAndReset` requires an empty staker set, so a single un-exitable user blocks the pool's terminal state. **So: 100% of a migrating pool's principal is frozen whenever any staker in it has `owed > 0` — the ordinary case, and the case measured below — rather than unconditionally.**

### Vulnerability details

`src/StableStakerV2.sol:613-622` (root cause at `:619-620`):

```solidity
613:        info.amount = 0;
614:        info.rewardDebt = 0;
615:        unclaimedReward[token][account] = 0;
616:        pool.totalStaked -= amt;
617:        _stakers[token].remove(account);
618:
619:        if (owed > 0) {
620:            antimatter.mint(account, owed);
621:        }
622:        emit MigratedOut(token, account, credit, owed);
```

`owed` is non-zero for any user who accrued while `antimatterPerSecond > 0`, i.e. for essentially every staker in a live pool. The mint is unconditional on success — no `try/catch`, no fallback to booking.

Every other door is shut while `Migrating`:

```solidity
347:        require(poolState[token] == PoolState.Active, "StableStaker: pool not active");   // withdraw
397:        require(poolState[token] == PoolState.Active, "StableStaker: pool not active");   // emergencyWithdraw
675:        require(_stakers[token].length() == 0, "StableStaker: stakers remain");           // finalizeAndReset
```

```solidity
912:        uint256 reserved = address(yieldStrategy[token]) == address(0) ? poolInfo[token].totalStaked : 0;
913:        uint256 bal = IERC20(token).balanceOf(address(this));
914:        require(bal >= reserved + amount, "StableStaker: would touch user principal");     // rescueERC20
```

With no strategy wired, `reserved == totalStaked == bal`, so `rescueERC20` is exactly tight and **not one wei is rescuable**.

The contract's own NatSpec promises the opposite in two places — `emergencyWithdraw` at `:391-392` ("Works while paused and never mints, so a broken mint path can never trap principal") and `_settle` at `:829-831` ("Never calls Antimatter, so a revoked minter role cannot brick the principal paths that reach here"). Both statements are true of `stake`/`withdraw`/`emergencyWithdraw` and **false of the terminal migration exit**, which is where the principal actually has to leave.

**Trigger sequence:**

1. Owner calls `initiateMigration(token)` — pool enters `Migrating`; `withdraw` and `emergencyWithdraw` now revert `"StableStaker: pool not active"`.
2. Independently, `Antimatter.setApprovedMinter(staker, false)` — ordinary decommissioning or incident response, with no attacker involvement.
3. Every path through `_exitPosition` now reverts `Antimatter.NotApprovedMinter(staker)`: `batchMigrate` (full batch **and** any single-user batch — the migrator cannot page around it), `userMigrate`, and `claim`.
4. `finalizeAndReset` reverts `"StableStaker: stakers remain"`; `rescueERC20` reverts at 1 wei; `pause()` opens nothing.
5. Recovery: `setApprovedMinter(staker, true)` — one call, fully restores the exit.

|---|---|
| Exact revert | `Antimatter.NotApprovedMinter(staker)`, selector **`0x6830132b`** |

The impact is **availability of a migrating pool's principal — 100% of it in the ordinary case where any staker has `owed > 0` (see the gate discussion above)**, not theft: nothing is extracted, no external attacker exists anywhere in the path. In the compound branch — revoke, then `renounceOwnership` — it becomes **permanent loss** of that principal.

### Severity justification (C4) — **SUPERSEDED (argues Medium; the finding is LOW)**

**Medium.** This is precisely C4's Medium text: *"assets are not at direct risk, but the function of the protocol or its availability could be impacted."* One hundred percent of a migrating pool's principal is unreachable, and the trigger is an ordinary operator action whose consequence is invisible from both contracts involved and contradicted by the project's own documentation.

**The High case, argued and rejected.** `renounceOwnership` after revocation makes the trap permanent, and permanent loss of a migrating pool's principal is on its face "assets lost". It is rejected because (a) the loss leg needs a **second, independent discretionary act** taken *after* the freeze has already occurred — a conjunction of two operator decisions is not an attack path free of hypotheticals; (b) `renounceOwnership` is universally understood to be irreversible, so making it the load-bearing step would rest a High on an *obvious*-consequence admin action, which both the C4 known-invalid filter and owner-trust policy exclude; and (c) the base case the PoC actually demonstrates is recoverable in a single call, and the same PoC demonstrates that recovery. **That recoverability is what bounds this below High** — and it is exactly why the permanence branch is stated here prominently rather than buried, because it is one `renounceOwnership` away.

**This sits at the top of Medium** because `CLAUDE.md:12-13` asserts the safety property this finding falsifies, unconditionally and with no migration carve-out. A false exhaustive safety claim in operator-facing documentation is what turns a knowable hazard into a footgun.

## Recommended mitigation steps — **WITHDRAWN 2026-08-31 (steps 1-2 REJECTED; only step 4, the doc correction, survives)**

> **Do not action steps 1 or 2.** Booking to `unclaimedReward` is rejected: `claim` (`:385`) is itself
> a mint site, so booking does not deliver the AM — it converts a loud, attended, one-call-recoverable
> halt into a silent deferral, and feeds the `L-07`/`F-03` backlog-stranding class. **Fail-loud is the
> intended and preferred behaviour on this path.** See the revision header for the full reasoning.

**1. Structural fix — remove the class.** Mirror the shape `stake`/`withdraw` already use since story-022: book the amount instead of minting inline, so principal leaves **unconditionally**.

```solidity
// src/StableStakerV2.sol, _exitPosition
-        if (owed > 0) {
-            antimatter.mint(account, owed);
-        }
+        if (owed > 0) {
+            // Book it; `claim` pays it out once the mint path is healthy. Principal must never
+            // depend on the reward token.
+            unclaimedReward[token][account] = owed;
+        }
```

Note this requires re-ordering against `:615` (`unclaimedReward[token][account] = 0;`), and that a booked balance is claimable only after minter rights are restored — which is the correct trade: **reward availability may depend on the mint path; principal availability must not.**

**2. Minimal fix — make the mint non-fatal.** If the inline mint must stay, wrap it so a revert cannot block the exit:

```solidity
if (owed > 0) {
    try antimatter.mint(account, owed) {
        // paid
    } catch {
        unclaimedReward[token][account] = owed;   // fall back to booking
    }
}
```

This one change is the difference between **recoverable-by-one-call** and **unrecoverable-by-anyone**, because it removes the mint from the principal path entirely.

**3. Delete the permanence branch (either alone is sufficient).**
   - Give `Antimatter` `Ownable2Step` **and override `renounceOwnership` to revert**. As shipped, `Antimatter` is plain `Ownable` with `renounceOwnership` inherited and un-overridden; a single call to it makes minter re-approval impossible forever, and `StableStakerV2.antimatter` is `immutable` at `:60` with no setter, so there is no way to point the staker at a replacement.
   - **Or** give `StableStakerV2` an owner-settable `antimatter` pointer, so a dead token contract can be replaced.

**4. Correct the documentation, now.** `CLAUDE.md:12-13` and `docs/deferred-reward-accrual-plan.md:35-38` ("The principal paths now never call the reward token at all, so its availability can neither trap nor degrade principal handling") state the mint-free-principal-path property **unconditionally**. Until fix (1) or (2) lands, both must carry an explicit migration carve-out, and the same carve-out belongs in the `emergencyWithdraw` and `_settle` NatSpec, which make the same claim in-source.

**5. Operational guard in the meantime.** Never revoke a staker's Antimatter minter approval while any of its pools is `Migrating`; sweep every pool to `Active` (or fully drained) first. Add a test covering "migration exit with the minter revoked" — no such test exists today.
