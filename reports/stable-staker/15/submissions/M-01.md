## Finding description and impact

### Summary

While a pool is `Active` and its yield strategy is below par, `StableStakerV2._routeExit` pays an exiting
staker **at par** out of the contract's idle token balance (the on-contract set-aside buffer, "B2").
Since story-020, `initiateMigration` snapshots `R = IERC20(token).balanceOf(address(this))` — i.e. **the same
B2** — and divides it **pro rata** among the remaining cohort.

Two different allocation rules therefore claim one pot: par/FCFS while `Active`, pro-rata while `Migrating`.
A staker who lands a `withdraw` in the block **before** the migrator's `initiateMigration` moves themselves
from the second rule to the first, and the cushion they consume is subtracted from everyone else's credit.
The transfer is exact, permissionless, and costs one transaction.

### Vulnerability details

**The par-exit branch** — `src/StableStakerV2.sol#L834-L854` ([link](https://github.com/Behodler/stable-staker/blob/master/src/StableStakerV2.sol#L834-L854)):

```solidity
834:    function _routeExit(address token, uint256 amount, bool guardUnderwater) internal returns (uint256 payout) {
835:        IYieldStrategy strategy = yieldStrategy[token];
...
840:        if (guardUnderwater && _isUnderwater(token, strategy)) {
841:            // Underwater: try to satisfy the entire withdraw from the on-contract buffer.
842:            // Caller forwards the returned amount via safeTransfer, so we just signal
843:            // "use the buffer" by returning `amount` without touching the strategy.
844:            if (t.balanceOf(address(this)) >= amount) {
845:                emit BufferWithdrawn(token, msg.sender, amount);
846:                strategy.relinquishPrincipal(token, amount);
847:                return amount;
848:            }
849:            revert("StableStaker: strategy underwater");
850:        }
851:        uint256 balanceBefore = t.balanceOf(address(this));
852:        strategy.withdraw(token, amount, address(this));
853:        return t.balanceOf(address(this)) - balanceBefore;
854:    }
```

The contrast is the whole finding: the healthy branch at `#L851-L853` returns the *actual* balance delta the
strategy delivered — the exiting user eats the impairment — while the underwater branch above returns `amount`
in full out of tokens that are already sitting on the contract.

The withdrawer is paid `amount` in full from the idle balance, and `relinquishPrincipal` writes the strategy
claim down **without moving shares** — so the impairment that would have been shared is left entirely behind.

**The pot the branch spends** — `src/StableStakerV2.sol#L512-L527` ([link](https://github.com/Behodler/stable-staker/blob/master/src/StableStakerV2.sol#L512-L527)):

```solidity
512:        // R is the whole liquid position this contract can pay migration credits from, capped at par.
513:        // Measuring it from the balance (rather than from _routeExit's delta) counts the set-aside
514:        // buffer, dust and donations already sitting here, so a below-par exit is softened before any
515:        // user is haircut — audit-14 ss14l8. All liquid value up to par is paid to users; anything
...
521:        uint256 R = IERC20(token).balanceOf(address(this));
522:        if (R > P) {
523:            R = P;
524:        }
525:
526:        migrationInfo[token] = MigrationInfo({realized: R, principalSnapshot: P});
527:        emit MigrationInitiated(token, R, P);
```

and the credit each remaining staker then receives — `src/StableStakerV2.sol#L584-L587`
([link](https://github.com/Behodler/stable-staker/blob/master/src/StableStakerV2.sol#L584-L587)):

```solidity
584:        MigrationInfo storage mig = migrationInfo[token];
585:        uint256 P = mig.principalSnapshot;
586:        uint256 S = mig.realized < P ? mig.realized : P; // min(R, P): caps credits at par
587:        credit = (amt * S) / P;
```

**Why the window exists.** `withdraw` is `whenNotPaused` and stays open for the whole time the pool is
`Active` — `src/StableStakerV2.sol#L334-L338`
([link](https://github.com/Behodler/stable-staker/blob/master/src/StableStakerV2.sol#L334-L338)):

```solidity
334:    function withdraw(address token, uint256 amount) external nonReentrant whenNotPaused poolExists(token) {
335:        require(amount > 0, "StableStaker: amount=0");
336:        // Frozen once terminal migration is engaged: exits go through {userMigrate}, which honours the
337:        // fixed (R, P) snapshot. A live withdraw would change `P`. See TERMINAL MIGRATION.
338:        require(poolState[token] == PoolState.Active, "StableStaker: pool not active");
```

`initiateMigration` is the single transaction that ends that state — `#L449-L450` and `#L510`
([link](https://github.com/Behodler/stable-staker/blob/master/src/StableStakerV2.sol#L449-L450)):

```solidity
449:    function initiateMigration(address token) external override nonReentrant onlyMigrator poolExists(token) {
450:        require(poolState[token] == PoolState.Active, "StableStaker: pool not active");
...
510:        poolState[token] = PoolState.Migrating;
```

Note what `#L449` does **not** carry: it is `nonReentrant onlyMigrator poolExists`, with **no
`whenNotPaused`**. That asymmetry is both what leaves the window open — the pool's own `Active` gate is the
only thing closing `withdraw`, and it does not flip until `#L510` executes — and, precisely because
`initiateMigration` is exempt from the pause, what makes the mitigation in the next section work.

Between the migrator broadcasting that transaction and it being mined, `withdraw` is still open. Any staker
watching the mempool can take the par branch first.

**Attack path.**
1. The strategy goes below par (depeg, vault impairment) — `withdrawDisabled(token)` is `true`, the pool is
   still `Active`, and B2 is non-zero.
2. The operator broadcasts `initiateMigration(token)`.
3. A staker whose position fits within B2 front-runs with `withdraw(token, fullPosition)`.
4. `_routeExit`'s underwater branch pays them at par out of B2 and relinquishes the claim.
5. `initiateMigration` is mined against a B2 reduced by exactly that payout; `R` falls by the same amount and
   every remaining staker's pro-rata credit falls with it.

### Impact — measured, not estimated

Validated in `Run15_M01_ParExitFrontRun.t.sol` against the **real** `reflax-yield-vault`
`ERC4626YieldStrategy` on the real `AYieldStrategy` base (no `MockYieldStrategy` on any path).
`P = 1,000.000000` USDC (Alice 100, Bob 500, Carol 400), vault 20% impaired (full exit delivers 800.000000),
`B2 = 150.000000`. All figures in USDC (6 decimals).

| | ARM 1 — honest baseline | ARM 2 — Alice front-runs | ARM 3 — mitigation |
|---|---|---|---|
| B2 at snapshot | 150.000000 | 50.000000 | 150.000000 |
| `P` | 1000.000000 | 900.000000 | 1000.000000 |
| `R` | 950.000000 | 850.000000 | 950.000000 |
| Alice receives | 95.000000 | **100.000000** (par) | 95.000000 |
| Cohort (Bob + Carol) | 855.000000 | **849.999999** | 855.000000 |
| Cohort retention | 95.0000% | 94.4444% | 95.0000% |

- **Front-runner gain: exactly 5.000000 USDC.**
- **Cohort loss: exactly 5.000001 USDC** — 5e6 plus 1 wei of floor-division dust that rounds to the protocol.
- **Cost to the attacker: one `withdraw` call.** No capital, no flash loan, no privileged role, no second
  contract.

The front-runner's gain is `position × (P − R)/P`, evaluated at the `P` and `R` that **would have obtained
absent the front-run** — i.e. ARM 1's `P = 1000.000000` and `R = 950.000000`, so 5% of the position here
(Alice: `100.000000 × 50.000000 / 1000.000000 = 5.000000`, exactly the measured delta). Evaluating the same
ratio on ARM 2's own post-attack snapshot gives 5.56%, which is the *cohort's worsened haircut*, not the
attacker's gain — the two must not be conflated. Since the trade needs no capital and one transaction, it is
profitable wherever 5% of the position exceeds gas.

### What this is *not* — the honest bound

This finding is deliberately bounded, and the bounds are load-bearing for its severity:

- **Nothing is stolen from the protocol.** Totals are conserved: 950.000000 distributed in ARM 1,
  949.999999 in ARM 2, the 1 wei difference rounding *to* the protocol. The protocol's balance sheet is
  identical either way — B2 is spent in both branches.
- **The front-runner takes only their own principal**, through a path the protocol *deliberately offers*
  while `Active`. The harm is the delta between two legitimate allocation rules applied to one pot, not an
  extraction from anybody's balance.
- **Hard-bounded by B2**, which is working capital, not a solvency reserve. The exploit needs
  `B2 ≥ attacker's position`; below that, `_routeExit` reverts `"StableStaker: strategy underwater"`
  (`#L849`). Exposure is therefore rationed FCFS by the buffer's size — a race for a fixed pot, never an
  unbounded drain.
- **Two external preconditions the attacker does not control**: the strategy must be below par *and* a
  migration must actually be broadcast.
- **No in-`Migrating` leg exists.** Tier-3 `INV-3` (5,000 fuzz runs) proved that once `Migrating` is latched,
  allocation is pro-rata and bit-identical under any batch composition or ordering, and `INV-B` (256,000
  stateful calls) that the idle balance always covers the remaining snapshot credits. Exposure is *strictly*
  the pre-`Migrating` window — which is exactly why the mitigation below is a window-closing runbook step
  rather than a change to the allocation maths.

### Why Medium and not High

C4 High requires assets stolen, lost or compromised. Here no asset leaves the protocol, no victim's balance
is touched, and the mover withdraws their own principal through an offered path. What remains is a concrete,
quantified value leak between user cohorts that depends on stated assumptions (below-par strategy, non-zero
B2) and external requirements (an impairment and a broadcast migration) — the textbook C4 Medium prong.
Rating this High would overstate it; rating it Low would understate a permissionless, essentially free,
exactly-quantified transfer between users.

## Recommended mitigation steps

### 1. Zero-code-change runbook fix (adopt immediately)

Wrap the irreversible step in a pause:

```
pause()  →  initiateMigration(token)  →  unpause()
```

`withdraw` is `whenNotPaused` (`#L334`); `initiateMigration` deliberately is **not** (`#L449`). The window
therefore closes with no Solidity change at all. ARM 3 of the PoC executes exactly this sequence: the
front-run reverts with **`0xd93c0665` (`EnforcedPause()`)**, and the arm lands **bit-identical to the honest
baseline** — `B2 = 150.000000`, `R = 950.000000`, `P = 1000.000000`, would-be front-runner 95.000000
(not 100.000000), cohort 855.000000.

**Caveat the runbook must carry — the two calls have different roles.**

```solidity
166:    modifier onlyPauser() {
167:        require(msg.sender == pauser, "StableStaker: only pauser");
168:        _;
169:    }
170:
171:    modifier onlyMigrator() {
172:        require(msg.sender == migrator, "StableStaker: only migrator");
173:        _;
174:    }
```

`pause()` is `onlyPauser` (`#L300`) while `initiateMigration` is `onlyMigrator` (`#L449`). If `pauser` and
`migrator` are **distinct addresses in production**, the fix is two coordinated transactions from two
different signers, and the gap between them is its own window. The runbook must therefore state explicitly
either:

- that the **same operator address holds both roles** and issues both transactions; or
- that the **pauser's `pause()` transaction is confirmed before the migrator broadcasts**
  `initiateMigration` — never the reverse, and never concurrently.

(`unpause()` is callable by owner *or* pauser (`#L305`), so recovery is not the constrained leg.)

### 2. Optional code-level hardening

If the operational dependency above is unwelcome, reserve the migration cushion from the par branch rather
than blocking it — e.g. permit the par exit at `#L844` only against the portion of the idle balance above a
configured reserve, so a par exit can never consume cushion the cohort is relying on:

```solidity
uint256 spendable = t.balanceOf(address(this));
uint256 reserved  = migrationReserve[token];          // 0 by default; preserves today's behaviour
if (spendable > reserved && spendable - reserved >= amount) {
    emit BufferWithdrawn(token, msg.sender, amount);
    strategy.relinquishPrincipal(token, amount);
    return amount;
}
revert("StableStaker: strategy underwater");
```

This keeps the design intent the owner defended in the 2026-06-01 triage — transient-dip withdrawals are
still paid at par, and no user is forced to realise a loss — while capping how much of the cohort's cushion a
single fast exiter can take.

**Not recommended:** blocking the buffer branch outright, or haircutting it pro rata. Both were considered
and rejected by the owner in the prior triage, and this finding does not disturb the reasoning that rejected
them.

## TRIAGE OUTCOME — closed `wont-fix` (owner decision, 2026-08-29)

This finding is **closed `wont-fix`**. It is **not** closed because it is wrong and **not** because the
severity is overstated: the finding is **valid** and its severity **stays Medium**. It is closed because the
mitigation is **operational rather than a code change, and out of scope for this repository**. The
`pause() → initiateMigration() → unpause()` sequence belongs in the deployment script that performs the
migration, and that script lives in **`phoenix-phase-2-staging`**. Nothing in `stable-staker` can fix it.

**The obligation is routed, not dropped.** It is recorded on this project's ledger as cross-repo route
**`SS15M1-PHSTAGING`**, to be applied by **`/audit-script`** as a check on any `phoenix-phase-2-staging`
entry point touching terminal migration: any script calling `StableStakerV2.initiateMigration` must
`pause()` first and `unpause()` after. Note the roles differ — `pause()` is `onlyPauser`
(`src/StableStakerV2.sol:300`) while `initiateMigration` is `onlyMigrator` (`:449`) — so either one operator
holds both roles, or the pauser's transaction must confirm before the migrator's is broadcast, a
two-transaction sequence that opens its own window between them. The route carries the measured exposure
(front-runner **+5.000000 USDC**, cohort **−5.000001 USDC**) and points at **ARM 3** of
`workspace/stable-staker/test/poc/Run15_M01_ParExitFrontRun.t.sol`, which proves the wrapper closes the
window (revert `0xd93c0665`). The owner expects the issue to surface again when that script is written and
audited, and will note the pause requirement there.

**Reopen trigger (`REOPEN-ss15m1`, ARMED).** `wont-fix` suppresses this finding from future `stable-staker`
scans, and the closure rests on the pause step **actually being carried out**. If a migration executes
**without** the pause wrapper, or a script calls `initiateMigration` with `withdraw` left open, the premise
fails and this finding must be reopened: `/ledger stable-staker reopen 2b9a89d2`.

*Nothing above alters the finding's substance, figures, PoC output, or the prior-triage disclosure.*
