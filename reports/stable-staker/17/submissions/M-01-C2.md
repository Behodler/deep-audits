## Terminology: three different quantities are all called "buffer"

**This report never writes "buffer" unqualified, because three distinct quantities in this system share
the name and confusing them inverts the conclusion.** All figures verified first-hand at block
**25,851,231**.

| # | Name used in this report | Definition | DOLA | USDC | USDe |
|---|--------------------------|------------|------|------|------|
| 1 | **set-aside buffer** | idle ERC-20 balance held **by the staker contract** | 6.663469 | 9.941647 | **48.506672** |
| 2 | **principal desync** — ***this finding's quantity*** | `strategy.principalOf(token, staker)` − `poolInfo.totalStaked` | **+26.898456** | **+27.043385** | **0** |
| 3 | **accrued yield** | `totalBalanceOf` − `principalOf` | 0.362341 | 0.953472 | 0.519649 |

(Quantity 3 accrues per block, so its figures drift slightly between blocks; 1 and 2 were stable across
the two blocks sampled.)

**(1) The set-aside buffer** is the protocol's intended concept: a liquidity cushion sized for daily
withdrawal flow, and — per the protocol owner — deliberately **not** a claim-satisfying reserve. The
owner's analogy is fractional-reserve banking: enough in the vault for day-to-day chequing, not enough
to satisfy all deposit claims at once. USDe's is the largest because that strategy books conservatively
against worst-case slippage, so everything delivered above that worst case lands as set-aside buffer.

**(2) The principal desync is this finding's quantity.** It lives **inside the strategy** and never
touches the staker's idle float. These are different pools of value in different contracts.

> **Note on the deployment tooling's vocabulary.** `PostMigrationCleanup.s.sol` logs quantity (2) as
> `"DOLA buffer (principal - totalStaked)"`. So the deployment scripts use the word "buffer" for
> **sense (2)**, while the protocol uses it for **sense (1)**. Wherever this report quotes a script
> saying "buffer", it means the **principal desync**, not the protocol's set-aside buffer. That
> collision is part of why the consequence went unspotted.

### The set-aside buffer is INVERSELY correlated with the failure — it can be ruled out

This is the cleanest discriminating evidence in the report, so it is stated up front:

| Pool | set-aside buffer (1) | principal desync (2) | `initiateMigration` |
|------|---------------------|----------------------|---------------------|
| USDe | **48.506672 (largest, ~5x the others)** | **0** | **succeeds** |
| USDC | 9.941647 | +27.043385 | **REVERTS** |
| DOLA | 6.663469 (smallest) | +26.898456 | **REVERTS** |

The pool with by far the **largest** set-aside buffer is the one that **works**; the two with the
**smallest** both **fail**. **The set-aside buffer neither causes the condition nor protects against
it** — it is inversely correlated, so anyone reaching for it as an explanation can be ruled out on the
data. The principal desync, by contrast, correlates **perfectly**: non-zero ⇔ reverts.

## Finding description and impact

### Summary

`StableStaker.setYieldStrategy` sweeps the contract's entire **raw** `IERC20.balanceOf(address(this))`
into the newly wired strategy with **no matching `totalStaked` increment**. Because the function is
gated on an empty pool, `totalStaked` is pinned at zero while the sweep is bounded by the raw balance,
so any surplus present at that moment is booked as strategy principal the staker does not account for.

`initiateMigration` later requests exactly `P = totalStaked`, under-drains by the surplus, and reverts
its completeness post-check with `"StableStaker: incomplete exit"`. Terminal migration — the protocol's
only order-independent exit — is unavailable for that pool until the strategy owner writes the surplus
down.

**This is not a hypothesis. It is the current state of two live mainnet pools.**

### The code

Empty-pool gate, `src/StableStaker.sol:236`:

```solidity
236:        require(poolInfo[token].totalStaked == 0, "StableStaker: pool not empty");
```

Unmatched sweep, `src/StableStaker.sol:272-274`:

```solidity
270:            // Sweep any idle balance already sitting in the contract into the new strategy so that
271:            // accounting is consistent immediately (at first adoption this equals staked principal).
272:            uint256 idleBalance = IERC20(token).balanceOf(address(this));
273:            if (idleBalance > 0) {
274:                strategy.deposit(token, idleBalance, address(this));
275:            }
```

Exit request and the post-check that fails, `src/StableStaker.sol:442` / `:456-459`:

```solidity
442:        uint256 P = poolInfo[token].totalStaked;
...
451:        uint256 R = _routeExit(token, P, false);
...
456:        require(
457:            address(strategy) == address(0) || strategy.principalOf(token, address(this)) == 0,
458:            "StableStaker: incomplete exit"
459:        );
```

than the pool accounts for, not less. Solvency checks ask whether principal is sufficient; the desync
makes it look better than expected.

**Likelihood is not an estimate. It is 1.0 — already realized.**

## How it happened

> **Provenance:** the causation below comes from **delegated research**. It is **corroborated** by my
> first-hand state verification above and by the receipts and source lines I read directly (quoted
> below), but I did not independently re-derive the narrative. It is labelled as such deliberately.

- **`ResetAndRewire.s.sol` was written but never broadcast**, superseded by the InPlaceMigrator route —
  consistent with story-018 recording the ys-swap saga as **abandoned**. I confirmed there is no
  `broadcast/ResetAndRewire.s.sol/` directory.
- **The script that actually ran is `script/MigrateSaga2Migrate.s.sol`**, broadcast to chainId 1
  (`broadcast/MigrateSaga2Migrate.s.sol/1/run-1781586598731.json`, commit `10b4aca`). I read the receipts:
  - DOLA `0x3719c54e09f823ce0e725f0419573bfbb10335477ee1db80dc3468f4bbf918d9`, block **25327882**

  - **Both transactions are `setYieldStrategy(address,address)` calls** — the exact function at issue.

### The script's header claims the sweep was avoided. The chain disagrees.

`script/MigrateSaga2Migrate.s.sol:29-30`:

```
  8. Transfer the skimmed DOLA/USDC surplus to the staker as a set-aside buffer (AFTER the rewire,
     so setYieldStrategy never sweeps it into the YS).
```

(Here the script does mean the **set-aside buffer**, sense (1) — its stated plan was to place the skim
into the staker's idle float *after* wiring so the sweep could not reach it.)

The receipts contradict it. Both transactions emit a `Deposited` event from the staker into the **new**

| Pool | Swept at rewire (from receipt) | Principal desync today (block 25,851,201) | Drift |
|------|-------------------------------|--------------------------------|-------|

The swept amounts match today's principal desyncs within rounding drift. **The gap between the script's stated
intent and what the chain records is the heart of this finding**: the operator believed the ordering
avoided the sweep, and the sweep happened anyway.

## Aggravator: the verification tooling blesses the condition

This is why it went unnoticed for seven months. The sibling scripts' own gates are **designed never to
flag it** — I read both.

`script/PostMigrationCleanup.s.sol:218-225` — **note the script's "buffer" here is the principal desync,
sense (2), not the protocol's set-aside buffer**:

```
// The "buffer" (principalOf - totalStaked) is a pure DIAGNOSTIC, logged but NOT bounded. There
// is deliberately NO sanity band: the buffer is EXPECTED to far exceed the recorded skim.
// leg-1 initiateMigration realizes the old strategy's whole position into idle, which exceeds
// credited principal by the strategy's accrued yield; ResetAndRewire's setYieldStrategy
// idle-sweep then folds that entire excess into V2 principal. So buffer = skim +
// realize-over-credit surplus, with the surplus dominating (on fork the USDC buffer was ~51x
// the skim). The earlier [skim/2, skim*2] band was built on the false premise buffer ≈ skim and
// would revert valid migrated state before the minter-revocation mutation could run.
```

The gate is then a deliberate `>=` **floor**, not an equality (`:229-230`):

```solidity
require(dolaP >= dolaTotalStaked, "Verify 4b FAILED: ysDolaV2 principal < totalStaked (insolvent)");
require(usdcP >= usdcTotalStaked, "Verify 5b FAILED: ysUsdcV2 principal < totalStaked (insolvent)");
```

`script/SkimAndLeg1Migration.s.sol:478-481` repeats the reasoning (again "buffer" = principal desync):

```
///      That gate is a `>=` FLOOR, NOT an equality assert: the unattributed skim buffer folded
///      into V2 by setYieldStrategy makes realized >= booked by construction, so an `==` check
///      would wrongly revert (surplus stays with the protocol, never socialized into a per-user
///      credit).
```

So the principal desync was **observed, reasoned about, explicitly expected, and deliberately exempted
from bounding** — while nobody connected it to `initiateMigration`'s equality post-check. An earlier band
that *would* have caught it was removed as a false premise.

**A detail worth noting:** the comment attributes the sweep to *`ResetAndRewire`'s* `setYieldStrategy` —
but `ResetAndRewire` was never broadcast. The tooling's causal attribution is itself wrong, which is
part of why the live consequence was never traced.

### Nothing reconciles it afterwards

`AYieldStrategy._withdrawInternal` caps **downward only** (`:673-674`, mirrored at `:741`), so a request
of `P` debits exactly `P` and leaves the principal desync untouched. Nothing sweeps it back.

And the `initiateMigration` comment reads as safe precisely because it assumes the invariant
`setYieldStrategy` breaks — `src/StableStaker.sol:449-450`:

```
// so the funds would never land here. withdraw caps the request to available principal, draining
// the client fully. When no strategy is set, _routeExit returns P (principal already idle ⇒ R = P).
```

"Draining the client fully" holds **only when `P == principalOf`**. That is exactly the equality the
sweep destroys. The code reads correct to a reviewer who does not question the premise.

## The owner remedy — real, available, and unchanged

**This finding is Medium and not High precisely because a clear exists, and it must stay prominent.**

`lib/reflax-yield-vault/src/AYieldStrategy.sol:654`:

```solidity
654:    function relinquishPrincipalAsOwner(address client, uint256 amount) external override onlyOwner nonReentrant {
655:        _relinquishInternal(address(underlyingToken), client, amount);
656:    }
```

`_relinquishInternal` decrements exactly the slot `principalOf` reads (`:679` vs `:523-525`), and the
source says at the write itself that it is lossless (`:678`):

```solidity
678:        // Write down recorded principal ONLY — vault shares are deliberately untouched.
679:        clientBalances[token][balanceHolder] -= amount;
```

I verified the losslessness rather than trusting the comment: the PoC asserts the strategy's vault share
balance is byte-identical across the clear.

**The remedy is available in the live configuration.** Verified at block 25,851,201: the staker owner
and **all three** strategy owners are the same address —

```
staker  0xbce8ABC0…  owner -> 0xCad1a7864a108DBFF67F4b8af71fAB0C7A86D0B6
DOLA ys 0x1760E053…  owner -> 0xCad1a7864a108DBFF67F4b8af71fAB0C7A86D0B6
USDC ys 0xaFDf8DeA…  owner -> 0xCad1a7864a108DBFF67F4b8af71fAB0C7A86D0B6
USDe ys 0xaC2e5936…  owner -> 0xCad1a7864a108DBFF67F4b8af71fAB0C7A86D0B6
```

Recovery is **2 non-atomic transactions per token** (`relinquishPrincipalAsOwner`, then
`initiateMigration`), and because they are not atomic the write-down should be run **immediately before**
`initiateMigration` to minimise the window in which fresh drift reopens the gap.

*No action has been taken on any live contract, and none will be. Remediation is the owner's decision.*

### The discoverability gap remains the reason this is a finding

The remedy is documented **nowhere** in `stable-staker`. No `docs/` directory exists in this repository,
and grepping `src/` plus `CLAUDE.md` for `relinquish` returns exactly one hit:

```
src/StableStaker.sol:796:                strategy.relinquishPrincipal(token, amount);
```

That is the *client*-initiated `relinquishPrincipal`, called for an unrelated purpose inside `_routeExit`
(the underwater set-aside-buffer path). The string `relinquishPrincipalAsOwner` does not appear in `stable-staker`
at all. An operator hitting this sees a revert naming `StableStaker`, while the fix lives behind an
owner-only function in a **different repository's base contract**. Seven months of it going untraced —
by tooling that measured the principal desync and blessed it — is the empirical demonstration.

## Impact

**Terminal migration is the protocol's only order-independent exit.** The fixed `(R, P)` snapshot pays
every user an identical proportional credit `p_i * min(R,P) / P` regardless of the order in which they
exit. That property is the whole point of the machinery.

With it unavailable, if a strategy goes underwater:

- `withdraw` is blocked by the underwater guard (`"StableStaker: strategy underwater"`, `:799`);
- `userMigrate` is unreachable — it requires `PoolState.Migrating` (`:565`), and `initiateMigration`
  never succeeds, so the pool never leaves `Active`;
- only FCFS `emergencyWithdraw` (`:363-378`) remains, which ledger entries `0dca43f315` and
  `69c7666eee` already record as concentrating loss on late exiters.

**The defect does not create a new loss mechanism. It removes the protocol's only fair one.** The loss
in that scenario originates in the strategy's impairment; what this defect changes is that the loss can
no longer be socialized proportionally, only raced for.

**The set-aside buffer will not cover the gap, by design.** Per the protocol owner, the set-aside buffer
is sized for **daily withdrawal flow** and is explicitly **not** intended to make all users whole — the
owner's own analogy is fractional-reserve banking: enough for day-to-day chequing, not enough to satisfy
all deposit claims at once. So in a genuine underwater episode the set-aside buffer will **not** protect
late withdrawers; it is not a reserve and was never meant to be one.

That is precisely why the ordered terminal migration matters. The fixed `(R, P)` snapshot is the one
mechanism that pays every user an identical proportional credit **regardless of exit order**, and it is
the mechanism currently unavailable on DOLA and USDC. Note the design intent here **sharpens** the
impact rather than softening it: the cushion that might look like a mitigation is, by the owner's own
description, not one.

Today, on the two affected pools: no value is lost, no value leaks, users stake/withdraw/claim normally,
and 21 users are exposed to the loss of that guarantee without any indication.

## Severity: Medium

**C4 Medium — "assets are not at direct risk, but the function of the protocol or its availability could
be impacted."** That is met squarely and, unusually, **already realized**:

- **Availability of a first-class protocol function is impacted on live, funded mainnet pools, today** —
  two of three, 21 staked users, verified by direct call at block 25,851,201.
- **Likelihood is 1.0.** Not modelled, not estimated: observed. The natural control (USDe, never rewired,
  zero principal desync, migration succeeds) rules out coincidence.
- **The condition is invisible** to pool state, `withdrawDisabled`, pause state and every solvency check,
  and the operational tooling that measures the principal desync explicitly declines to bound it.

**Explicitly NOT High.** High requires assets to be stolen, lost, or compromised. Here:

- nothing is stolen and no attacker profits;
- no value is lost or leaked — the principal desync is protocol-owned value sitting in the strategy;
- users retain normal stake, withdraw and claim;
- the condition is **recoverable**, by an owner who holds the required key in the live configuration
  (verified above), in two transactions per token.

Rating this High would be the overstatement this pipeline rejects. Rating it Low would now understate a
realized production condition — which is what the step-2 Low did, correctly on the evidence available at
the time, and incorrectly in light of the chain.

### ⚠ CONDITIONAL REOPEN — a third-party-owned strategy warrants HIGH consideration

If a strategy whose owner is **not** the staker's operator is ever wired, this finding should be
re-evaluated for **High**, not merely Medium. In that configuration **no clear exists at all**
(`relinquishPrincipalAsOwner` and `withdrawAsOwner` are both `onlyOwner` on the strategy) **and** the
condition is already demonstrated to arise in practice. Unrecoverable plus realized is a materially
different finding from recoverable plus realized.

The prerequisite is textually contemplated by the protocol's own documentation —
`src/StableStaker.sol:224-225` ("the strategy owner must authorize this contract as a client") and
`CLAUDE.md:68-70` ("done by the *strategy's* owner, not `StableStaker`") both phrase the strategy owner
as a possibly-distinct party, and `AYieldStrategy`'s owner is a plain constructor argument. Today all
four addresses coincide (verified above), so the current rating is Medium; the trigger is recorded so a
future wiring change re-opens it rather than silently inheriting this rating.

## RESOLVED — the owner has answered the open question

An earlier revision of this report left open whether the defect lay in the sweep or in
`initiateMigration`'s post-check, and presented two framings as a live choice. **The protocol owner has
now stated the intent, and it resolves the question. Neither framing as written is what the owner
wants.**

### The owner's stated intent

> - All yield **and** the set-aside buffer should be swept into principal during a migration.
> - If the yield strategies credit the staker with **more** than `StableStaker` is claiming, the excess
>   should be **relinquished** — it returns to the protocol through the yield accumulator.
> - Priority order: **safe migrations over precise ones**; **err toward the user** where possible; but
>   **never break protocol functionality or open an exploit vector**.

### What that rules out

- **Framing A (bound the sweep, destroy the surplus) is rejected.** The owner wants the sweep to happen.
  The prior revision's "bound the sweep" proposal is withdrawn (not to be confused with the *new*
  mitigation 1 below, which is a different fix).
- **Framing B's disposition is rejected too.** The owner does not want the principal desync *preserved
  and tolerated*; they want it **written down**. The `protocolPrincipal` accumulator (2a) and the
  `principalOf`-based exit request (2b) both keep the desync alive as a permanent feature, which is not
  the stated intent. Both are withdrawn as primary proposals.

The prior A/B analysis is retained below as **history**, because the reasoning is what surfaced the
question the owner has now answered — not because either option is still on the table.

## Recommended mitigation steps

> **Mitigation 1 is now the primary fix and follows directly from the owner's stated intent.**
> Mitigations 2 and 3 are unchanged and apply regardless. The withdrawn Framing A/B proposals are
> recorded as history at the end of this section.

### 1. (PRIMARY) Relinquish the excess in-contract, inside `initiateMigration`

This implements the owner's second stated rule exactly: where the strategy has credited the staker more
than `StableStaker` claims, the excess is **relinquished** and returns to the protocol through the yield
accumulator.

**This is already-wired plumbing, not a new dependency.** Verified at `8856781`:

`lib/reflax-yield-vault/src/AYieldStrategy.sol:649` — the client-callable variant, **`onlyAuthorizedClient`,
not `onlyOwner`**, so the staker can call it on its own behalf:

```solidity
649:    function relinquishPrincipal(address token, uint256 amount) external override onlyAuthorizedClient nonReentrant {
650:        _relinquishInternal(token, msg.sender, amount);
651:    }
```

`StableStaker` **already calls it** today, in `_routeExit`'s underwater branch —
`src/StableStaker.sol:796`:

```solidity
796:                strategy.relinquishPrincipal(token, amount);
```

And `_relinquishInternal` (`:667-683`) caps to available, writes down `clientBalances` **and**
`totalDeposited`, and leaves vault shares untouched (`:678`), so the excess stays in the strategy as
protocol-owned value and flows back via the yield accumulator — **exactly the owner's stated
disposition**:

```solidity
678:        // Write down recorded principal ONLY — vault shares are deliberately untouched.
679:        clientBalances[token][balanceHolder] -= amount;
680:        totalDeposited[token] -= amount;
```

**The edit.** Realize `P`, then relinquish whatever remains booked, *then* assert the drain — instead of
reverting on a non-zero remainder. Replacing the post-check at `src/StableStaker.sol:456-459`:

```solidity
uint256 R = _routeExit(token, P, false);                       // :451, unchanged

// NEW: write down any principal the strategy still books to us. The idle sweep in
// setYieldStrategy can leave principalOf > totalStaked; that excess is protocol-owned and is
// relinquished here rather than blocking the migration.
if (address(strategy) != address(0)) {
    uint256 remaining = strategy.principalOf(token, address(this));
    if (remaining > 0) {                                        // REQUIRED: see guard note below
        strategy.relinquishPrincipal(token, remaining);
    }
}

// Post-check retained, and now satisfiable by construction.
require(
    address(strategy) == address(0) || strategy.principalOf(token, address(this)) == 0,
    "StableStaker: incomplete exit"
);
```

**Two mechanical requirements, both load-bearing:**

1. **The `address(strategy) == address(0)` case must be handled.** When no strategy is wired,
   `_routeExit` returns `P` (principal already idle) and there is nothing to relinquish; calling into a
   zero address would revert. The guard above preserves the existing `strategy == address(0)` short-circuit
   in the post-check.
2. **The call must be guarded on `principalOf > 0`.** `_relinquishInternal` reverts on a zero amount —
   twice, at `:669` (`"AYieldStrategy: amount must be greater than zero"`) and again at `:676` after
   capping (`"AYieldStrategy: no principal to relinquish"`). An unguarded call on an already-clean exit
   would turn a working migration into a reverting one, which is precisely the failure mode this
   finding is about.

**Why this beats every prior option, on the owner's own safety criterion.** The owner's first priority
is *safe migrations over precise ones*, and their overriding constraint is *never break protocol
functionality*. This fix **removes the operator from the loop entirely.** The live condition on DOLA and
USDC currently requires someone to know about an undocumented, owner-only function in a *different
repository* and to invoke it at the worst possible moment — mid-incident, under time pressure, with the
revert string pointing at the wrong contract. With this change `initiateMigration` **self-heals**: both
pools become migratable with no intervention, no cross-repo knowledge, and no operator in the critical
path. It also makes the mainnet condition documented in this report resolve itself on upgrade, rather
than requiring a remediation transaction per token.

It is also strictly narrower than the alternatives: no new storage, no change to the sweep, no change to
`P` as the credit denominator, and no change to what users are paid.

### 2. Name the clear in the `"incomplete exit"` NatSpec

An operator mid-incident should not be decoding a foreign repository. At `src/StableStaker.sol:453-459`:

```solidity
// RECOVERY: if this reverts, the strategy holds client principal this contract never accounted for
// (see setYieldStrategy's idle sweep). The strategy's OWNER clears it in one call —
// AYieldStrategy.relinquishPrincipalAsOwner(address(this), surplus) — which writes down recorded
// principal only and moves no vault shares. `surplus` is strategy.principalOf(token, address(this)).
// Note: owner-only, on the STRATEGY, in reflax-yield-vault — not on this contract.
```

### 3. Fix the operational gates that bless the condition

`PostMigrationCleanup.s.sol:218-230` and `SkimAndLeg1Migration.s.sol:478-481` should assert that a
non-zero principal desync is **reconciled before the pool is left in service**, or at minimum warn that
a non-zero desync disables `initiateMigration`. The current `>=` floor is correct for solvency and silent on
migration liveness — which is exactly the blind spot that let this run for seven months.

### 4. Operational note

`test_mitigation_rescueIdleBeforeWiring` shows idle balance can be rescued **before** wiring (at that
moment `reserved == totalStaked == 0`, so the full balance is rescuable). To survive a 1-wei front-run
this must be atomic with the wiring, and it does nothing for the already-affected pools — the owner
clear is the remedy there.

## Trigger analysis

Both triggers below are proven in the PoC. **Neither is now the primary evidence** — the primary evidence

because they show the mechanism is general, not specific to one script.

### Permissionless 1-wei donation, on ANY pool, at first strategy wiring

No preconditions: no impaired strategy, no prior migration, no runbook. Any pool, at the moment its owner
first wires a strategy, for 1 wei plus gas. The empty-pool gate still passes (a raw donation does not move
`totalStaked`), and the condition is set **before the first user stakes**.

warp. Also demonstrated against the real `ERC4626YieldStrategy` (`test_realERC4626Strategy_sameBrick`).

### Revival runbook (no attacker), only against an impaired strategy

`initiateMigration -> batchMigrate/userMigrate -> finalizeAndReset -> setYieldStrategy`. A completed

requires the prior migration to have run against an impaired (`R < P`) strategy, since dust exists only
because `S = min(R,P) < P` makes the credit truncate. Probed directly:


Demonstrated against `MockYieldStrategy`; the real-strategy test covers the donation leg only.
