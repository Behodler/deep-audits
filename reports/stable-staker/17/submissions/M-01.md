# [M-01] story-025's claim gate creates a reward-forfeiture trap: while the strategy is underwater and the idle buffer is short, the only path that returns principal irreversibly destroys the accrued Antimatter backlog

**Severity:** Medium
**Contract:** `src/StableStakerV2.sol` (audited at `96d39ed`, branch `master`)
**Functions:** `claim` / `withdraw` / `autoAnnihilate` / `emergencyWithdraw`
**Link to root cause:** [`src/StableStakerV2.sol#L624-L634`](https://github.com/Behodler/stable-staker/blob/master/src/StableStakerV2.sol#L624-L634)

## Finding description and impact

### Summary

story-025 placed `claim` behind a `claimEnabled` flag that is `false` on deployment. In the state
where the wired yield strategy is below par and the shared idle buffer cannot cover the caller's
request, three paths close at the same instant. The only path that still returns principal is
`emergencyWithdraw`, and taking it zeroes the caller's `unclaimedReward` backlog with nothing
minted.

The claim proved here is deliberately narrow: **while the strategy is below par and the buffer is
short, the only path that returns principal is `emergencyWithdraw`, and taking it irreversibly
destroys 100% of the accrued Antimatter.** It is not a claim that the backlog is destroyed on a
timer. A probe confirmed the opposite — an untouched backlog keeps accruing (`4166666666666666550000`
wei grew to `18254166666666666644249879` wei over a simulated year), so a staker who does not need
their principal is not losing anything by waiting. The loss is conditional on exiting, not forced.

### The three closed paths

`claim` — the story-025 gate, at `:439-440`:

```solidity
function claim(address token) external nonReentrant whenNotPaused poolExists(token) {
    require(claimEnabled, "StableStaker: claim disabled");
```

`claimEnabled` is a bare `bool` with no initializer at `:100`, so it is `false` from the first block
of the contract's life:

```solidity
bool public claimEnabled;
```

`withdraw` — the underwater guard, entered at `:423` with `guardUnderwater = true`:

```solidity
uint256 payout = _routeExit(token, amount, true);
```

`autoAnnihilate` — the same guard, entered at `:579`, again with `guardUnderwater = true`:

```solidity
uint256 received = _routeExit(token, gross, true);
```

Both land on `_routeExit`'s underwater branch at `:1184-1194`, which either satisfies the whole
request from the idle buffer or reverts:

```solidity
if (guardUnderwater && _isUnderwater(token, strategy)) {
    // Underwater: try to satisfy the entire withdraw from the on-contract buffer.
    // Caller forwards the returned amount via safeTransfer, so we just signal
    // "use the buffer" by returning `amount` without touching the strategy.
    if (t.balanceOf(address(this)) >= amount) {
        emit BufferWithdrawn(token, msg.sender, amount);
        strategy.relinquishPrincipal(token, amount);
        return amount;
    }
    revert("StableStaker: strategy underwater");
}
```

`_isUnderwater` at `:1131-1133` is an ordinary market condition, not an operator action:

```solidity
function _isUnderwater(address token, IYieldStrategy strategy) internal view returns (bool) {
    return strategy.totalBalanceOf(token, address(this)) < strategy.principalOf(token, address(this));
}
```

### The surviving path destroys the backlog

`emergencyWithdraw` is the only exit left, and at `:629-630` it zeroes the backlog and never mints:

```solidity
// Forfeit the backlog too: the hatch stays the single rule "no reward, principal out".
unclaimedReward[token][msg.sender] = 0;
```

It then routes the exit with the guard **off** at `:633-634`, which is precisely why it is the one
path that still works below par:

```solidity
// No underwater guard: the escape hatch must always work, accepting a haircut if below par.
uint256 payout = _routeExit(token, amount, false);
```

### The buffer condition is the default state of a fresh pool

The second condition — an idle buffer smaller than the request — is not an unusual configuration. It
is the shipped default. `stake` forwards the entire received amount into the strategy at `:388-389`
and retains no fraction:

```solidity
uint256 received = _pullToken(token, msg.sender, amount);
uint256 credited = _routeDeposit(token, received);
```

A non-zero idle balance therefore arises only from exit residue, a donation, or a deliberate owner
set-aside. The PoC's own log records `idle buffer held by StableStakerV2: 0` after a 150,000-token
stake into the real strategy. Reachability of the trap consequently collapses to a single condition:
**the strategy goes below par.**

### Impact

The staker's accrued `unclaimedReward` is destroyed — irreversibly, on-chain, with nothing minted.
The PoC pins the destroyed quantity at exactly `4166666666666666550000` wei of Antimatter for a
150,000-token position accruing for two hours at 50,000 Antimatter/day. Under V2 that Antimatter is
redeemable into phUSD via the permissionless `Antimatter.annihilate`, so this is real user value, not
opportunity cost; the project-wide minter-cushion and externally-derived-yield suppressions are void
for V2 and are not available to soften it. Principal is unaffected — `142500000000000000000000` wei
came back in the PoC, correctly haircut by the 5% drawdown.

Irreversibility is asserted, not assumed. After the hatch, opening the gate does not recover
anything: the PoC reopens `setClaimEnabled(true)` and `claim` then reverts `"StableStaker: nothing to
claim"` at `:446`:

```solidity
require(owed > 0, "StableStaker: nothing to claim");
```

Four post-state assertions corroborate it — `unclaimedReward == 0`, `claimableReward == 0`, the
caller's Antimatter balance `== 0`, and their phUSD balance `== 0`.

A secondary dynamic worth stating: the idle buffer is first-come-first-served at `:1188`, and
story-025 adds reward-seeking callers to a queue that previously held only principal-seeking ones, so
the buffer exhausts sooner and the trap closes on later stakers first.

### Why this is new to this diff range

Before story-025, `claim` was ungated: a trapped staker could claim first and hatch out second. The
gate is what converts a recoverable situation into a forfeiture on exit. Control 2 in the PoC
demonstrates that recovery, and its result should be read for what it is — it implements
"pre-story-025" by calling `setClaimEnabled(true)` earlier rather than by compiling pre-story-025
source, so it is Control 1's mechanism run at a different time, **not independent corroboration of
historical behaviour**. The historical claim rests on the diff, not on Control 2.

### Assumptions and external requirements

Stated plainly. These are **not** four independent conjuncts — three of the four are the shipped deployment defaults, so reachability collapses to a single condition: **the strategy goes below par.**

1. the wired strategy is below par (driven by external market state);
2. the idle buffer is less than the caller's gross request — **the deployment default, not a second
   condition.** `_routeDeposit:1139-1144` forwards 100% of every deposit to the strategy and retains
   nothing; `setYieldStrategy:349-354` sweeps any idle balance *into* the strategy; and no donate,
   target-buffer or reserve mechanism exists anywhere in `src/` (`donateBuffer` is harness-only). The
   PoC log records `idle buffer held by StableStakerV2: 0`. A non-zero idle balance can arise only
   from exit residue or an unmodelled owner set-aside;
3. `claimEnabled` is `false` (the deployment default at `:100`);
4. the staker's need for principal is time-sensitive enough that waiting out the dip, or waiting for
   owner intervention, is not acceptable.

No attacker is required at any step.

### Severity justification

**Not High.** There is no attacker and no theft; no protocol funds move to a third party; principal
is untouched and still exits; the staker retains a wait-option (the backlog keeps accruing rather
than decaying); and one owner transaction, `setClaimEnabled(true)`, defuses the trap entirely.

**Not Low.** The destruction is irreversible once the transaction lands, it needs no adversary, and
it is *created* by story-025 — the very conditions that reach it (a transient, mean-reverting
underwater dip) are the conditions the buffer was built for.

**Top of the Medium band.** Because the buffer condition is the deployment default rather than a
second conjunct, reachability rests on one condition — the strategy going below par — which is the
owner's own stated normal case for this buffer. That places this finding at the **top of the Medium
band**. It still does not cross into High, for the reasons stated immediately above: no attacker, no
theft, principal untouched, a surviving wait-option, and one owner transaction that defuses it.

**Open triage item SA-17-01 (may broaden this finding).** The "shared idle buffer" that known-issue
N19, this finding, `[L-05]` and the owner's own `69c7666eee` triage reason (*"sized for daily-volume
withdrawals"*) all treat as a tunable operational parameter has **no funding mechanism in the
contract**. If that premise is retracted rather than implemented, then while a strategy is below par
`withdraw` is dead for **every** staker, not only for one whose request exceeds a partly-funded
buffer — i.e. the availability limb of this finding is **broader** than stated here. Routed to human
triage; deliberately not used to escalate this rating in-pipeline.

The obvious downgrade — "the owner can just open the gate, so it is Low" — is not taken. The gate
ships `false` and nothing on-chain reopens it.

**Law-3 footgun.** `CLAUDE.md` anticipates exactly this lockout class for the *antimatter pause*
("the owner flips `claimEnabled` to true for the duration of any antimatter pause") but not for the
*underwater* case, which is by far the more likely trigger. The operational obligation the design
depends on is written down for the rarer trigger and unwritten for the common one, so an owner who
has read the two-pause note reasonably believes they have enumerated the lockout conditions. They
have not. This is filed on the impact it unlocks, not as a centralization item — the owner does
nothing wrong.

### Evidence quality

- The three revert strings in the PoC are captured as literal text and verified against production
  source at `:440`, `:423`→`:1193` and `:579`→`:1193` (quoted above).
- **Mutation test.** Inserting `setClaimEnabled(true)` and changing nothing else makes the headline
  test fail. The test therefore measures the gate and nothing else.
- **Falsifiability.** Controls 3a (fund the buffer) and 3b (hold the strategy at par) each
  individually defuse the trap, so the conjunction is genuine rather than an artifact of one blocked
  path masking another.
- **Fixture discipline.** The rig uses the real `StableStakerV2`, the real
  `ERC4626YieldStrategy`, and OpenZeppelin's real `ERC4626`. The underwater condition is induced by a
  genuine 5% asset departure from the vault — assets leave, shares are unchanged, share price falls,
  and production `_isUnderwater` flips on its own — with no value knob anywhere. `MockYieldStrategy`
  is deliberately **not** used: it carries a value-factor knob that fabricates the underwater
  condition, and its `relinquishPrincipalAsOwner` is a known empty stub on this project.
- Tier-3 independently measured `4166666666666666650000` wei destroyed on the same emission
  parameters in a three-actor rig; the `1e5`-wei difference from the PoC figure is per-user
  `rewardDebt` flooring across a different staker split, not a different mechanism.

## Recommended mitigation steps

**Do not** make `emergencyWithdraw` preserve the backlog. Known issue N4 documents the forfeiture as
the deliberate single rule of the escape hatch ("no reward, principal out", and it never mints), and
recommending its removal would be a recommendation against documented intent. What N4 does not reach,
and what this finding is, is the coercion: N4's wording presupposes `emergencyWithdraw` is an escape
hatch *among* options, and an escape hatch that is the only exit is not an escape hatch. The remedies
below leave `:630` exactly as it is.

**(a) Preferred — exempt the reward-only leg from the underwater guard.** A caller whose `netWanted`
resolves to zero principal moves no principal and has no reason to be blocked by a principal-solvency
guard. Concretely, in `autoAnnihilate`, when the computed `gross` is zero (or when the call is a
reward-only settlement), do not route through `_routeExit(..., true)` at `:579`. This restores a
non-forfeiting reward path in exactly the state where every other one is shut, and leaves the
`withdraw` guard at `:423` untouched — that guard is correct and is not disputed here.

**(b) Alternative — settle the backlog before the hatch zeroes it.** Have `emergencyWithdraw` mint or
otherwise settle `unclaimedReward` to the caller ahead of `:630`, so the line still zeroes a mapping
that has already been paid out. This keeps the hatch's "principal out, immediately, always"
behaviour and its no-underwater-guard exit intact; it changes only whether already-accrued reward is
discarded on the way past. If the project prefers the hatch to remain literally mint-free, (a) is the
better fit.

**(c) Operational, and required whichever of the above is chosen.** The obligation currently written
in `CLAUDE.md` for the antimatter-pause case should be extended to the underwater case — for example:
*"the owner flips `claimEnabled` to true for the duration of any antimatter pause **or any period in
which a wired strategy is underwater**"* — and an alarm should be wired on `_isUnderwater`, since
nothing on-chain enforces the obligation. This is a mitigation, not a fix: it depends on an operator
reacting inside the window, and the window is exactly when a staker is most likely to want out.
