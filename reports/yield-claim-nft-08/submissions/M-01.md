## Finding description and impact

### Summary

`NFTMigrator.migrate()` mints V2 NFTs to the caller using an inner loop that performs one external `mintFor` call per NFT *unit* held at each V1 dispatcher index. Gas consumption therefore scales linearly with the caller's single-index ERC1155 balance. Because the function processes the caller's entire balance in one transaction and exposes no paginated or partial migration path, a holder whose balance at a single index is large enough that the per-unit work exceeds the block gas limit can never successfully call `migrate()` — it reverts out-of-gas on every attempt. Migration is permanently unavailable for that holder.

There is no direct asset loss: the burn-then-mint is atomic, so a reverting `migrate()` leaves the holder's V1 NFTs intact and fully usable. The impact is loss of the migration function for affected holders, which is an availability/protocol-function impact -> Medium.

### Vulnerability details

The vulnerable code is in `migrate()` ([src/V2/NFTMigrator.sol#L62-L76](https://github.com/Behodler/yield-claim-nft/blob/master/src/V2/NFTMigrator.sol#L62-L76)):

```solidity
function migrate() external {
    require(initialized, "NFTMigrator: not initialized");
    uint256 upperBound = v1.nextIndex();
    for (uint256 i = 1; i < upperBound; i++) {
        uint256 balance = IERC1155(address(v1)).balanceOf(msg.sender, i);
        if (balance > 0) {
            v1.burn(msg.sender, i, balance);
            uint256 v2Index = indexMapping[i];
            for (uint256 j = 0; j < balance; j++) {
                v2.mintFor(v2Index, msg.sender);          // one external _mint per UNIT
            }
            emit Migrated(msg.sender, i, balance, v2Index);
        }
    }
}
```

The inner loop at [L70-L72](https://github.com/Behodler/yield-claim-nft/blob/master/src/V2/NFTMigrator.sol#L70-L72) issues `balance` sequential external calls to `v2.mintFor`, each of which performs an ERC1155 `_mint`. The V1 side burns the whole balance in a single `v1.burn` call (L68), but the V2 side mints one unit at a time. There is no batch `mintFor` and no `maxCount`/cursor parameter, so:

1. A user accumulates a large balance of a single V1 index through normal, permissionless minting (`balance` is read at L66 from the caller's own ERC1155 balance — it is not owner-controlled).
2. The user calls `migrate()`.
3. The inner loop runs `balance` external mints in one transaction.
4. For a sufficiently large `balance`, cumulative gas exceeds the block gas limit and the transaction always reverts out-of-gas.
5. With no partial-migration path, that holder can never migrate.

### Impact

`migrate()` becomes permanently unavailable to any holder whose single-index V1 balance is large enough that `balance` sequential mints exceed the block gas limit, with no in-contract workaround. The PoC measures a marginal cost of ~9,865 gas per unit, which places the brick threshold at roughly 3,041 NFTs at one index under a 30M gas limit (see PoC). This is not direct theft or loss — the atomic revert preserves the holder's V1 NFTs and their utility — so the issue caps at Medium per C4 (protocol function/availability impacted, assets not at risk). It is not High: no funds are lost or stolen, and V1 utility is retained.

### Severity assumption (stated honestly)

This finding's Medium rating depends on whether a single holder realistically accumulates ~3,000+ NFT units at one V1 dispatcher index. That is config-dependent. The `migrate()` balance is permissionless and not capped by the contract, and a cheap or popular dispatcher (low constant mint price, no per-holder cap) makes a multi-thousand single-index balance plausible — under those conditions Medium is firm. If, in the deployed configuration, realistic per-holder single-index balances stay well below the threshold (e.g. high mint price, supply caps, or steep price growth that economically bounds accumulation), the issue degrades toward Low/QA — merely an expensive migration rather than a brick. The root cause (unbounded per-unit loop with no pagination) is present regardless of configuration.

## Proof of Concept

A runnable Foundry PoC is provided at `workspace/yield-claim-nft/test/poc-M01-migrate-gas-dos.t.sol`. It uses the real `NFTMinter`, `NFTMinterV2`, `Gather`/`GatherV2` dispatchers and `NFTMigrator` with correct role wiring, and grants V1 balances only through the legitimate paid mint path (no privileged shortcut). Dispatchers are configured with `growthBasisPoints = 0` so the mint price is constant — a realistic configuration that lets a holder accumulate a large single-index balance.

`test_M01_gasScalesLinearlyWithBalance` measures `migrate()` for two balances and derives the marginal per-unit cost:

```solidity
_mintV1(smallHolder, 50);
vm.prank(smallHolder);
uint256 gBefore = gasleft();
migrator.migrate();
uint256 gasLow = gBefore - gasleft();   // 50-unit migration

_mintV1(whale, 250);
vm.prank(whale);
gBefore = gasleft();
migrator.migrate();
uint256 gasHigh = gBefore - gasleft();  // 250-unit migration

uint256 perUnitGas = (gasHigh - gasLow) / (250 - 50);
uint256 dosBalance = 30_000_000 / perUnitGas; // balance that crosses a 30M block
```

Measured results:

| Single-index balance | `migrate()` gas |
|----------------------|-----------------|
| 50 units             | 612,188         |
| 250 units            | 2,585,188       |

- Marginal cost: `(2,585,188 - 612,188) / (250 - 50)` = **~9,865 gas per unit**.
- Brick threshold: `30,000,000 / 9,865` = **~3,041 NFTs** at a single index to exceed a 30M block gas limit. This is a plausible single-index balance, not an astronomical one.

`test_M01_migrateRevertsUnderBlockGasLimit` then demonstrates the concrete denial of service. It calibrates the per-unit cost, gives a whale a single-index balance whose `migrate()` cost comfortably exceeds 30M (the PoC selects a ~5,349-unit balance with headroom over the threshold), and invokes `migrate()` while forwarding exactly a full block's worth of gas:

```solidity
vm.prank(whale);
(bool ok,) = address(migrator).call{gas: 30_000_000}(
    abi.encodeWithSelector(NFTMigrator.migrate.selector)
);

assertFalse(ok, "migrate() must FAIL when forwarded a full block of gas");
assertEq(v1.balanceOf(whale, 1), whaleQty, "V1 balance unchanged after failed migrate");
assertEq(v2.balanceOf(whale, 1), 0, "no V2 minted -> migration permanently bricked");
```

The whale's call reverts (out-of-gas) under the 30M cap while small balances (50/100/250 units) migrate successfully under the same cap. After the failed call the whale's V1 balance is unchanged and no V2 was minted — the holder is stuck, unable to ever migrate, with no partial path to drain the balance across multiple transactions.

Run with:

```
forge test --match-path test/poc-M01-migrate-gas-dos.t.sol -vv
```

## Recommended mitigation steps

The root cause is minting one unit per external call. Two complementary fixes:

1. **Batch the V2 mint (preferred).** Replace the per-unit inner loop with a single batched mint of the full `balance`. Since V2 NFTs are ERC1155, expose a batch entry point on `NFTMinterV2` that performs one `_mint(to, id, balance, "")` (or `_mintBatch`) instead of `balance` separate `mintFor` calls. Per-unit overhead then collapses to roughly the cost of updating a single balance slot, removing the linear scaling:

```solidity
// instead of:
for (uint256 j = 0; j < balance; j++) {
    v2.mintFor(v2Index, msg.sender);
}
// mint all units in one ERC1155 _mint:
v2.mintForBatch(v2Index, msg.sender, balance); // performs a single _mint(to, id, balance, "")
```

2. **Paginate migration as a defense in depth.** Add a bounded/partial migration path so a holder can always make progress even if total work is large — e.g. `migrate(uint256 v1Index, uint256 maxUnits)` that burns and re-mints only `maxUnits` of a given index per call and can be resumed. Ensure the burn is correspondingly partial so a large balance can be drained across multiple transactions.

Implementing the batch mint (1) addresses the underlying gas-scaling defect directly; adding pagination (2) guarantees migration remains available even for arbitrarily large or multi-index balances.
