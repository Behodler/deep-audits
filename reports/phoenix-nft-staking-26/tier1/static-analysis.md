## Non-noise first-party findings

### S-01 — `calls-loop`: unbounded external `pullPendingStream` loop over the whole nudge whitelist can brick `batchMint`
- **Location:** `src/BatchNFTMinterMultiToken.sol:533` (loop at 532-534, inside `batchMint` 464-727)
- **Sources:** Slither `calls-loop` (Low/Medium)
- **Assessment: LOOKS REAL — hand to code-scanner/econ-scanner, do not cull.** `batchMint` loops `INudgeStreamer(_nudgeStreamer).pullPendingStream(_nudgeTokens[i])` over every whitelisted token in one tx. Any single token whose settle reverts takes the entire `batchMint` down. This is not speculative: `NudgeStreamer.sol:168-174` **names this exact brick path in its own NatSpec** as the consequence of `Σ buffer_i` exceeding pooled custody ("a sibling pair's `pullPendingStream` reverts — which bricks `batchMint`, since it loops `pullPendingStream` over the whole whitelist in one tx"). The contract defends the *cause* it anticipated (balance-delta credit at `collectNudge`), but the loop remains a single-point-of-failure amplifier for any *other* revert source on any one whitelisted token (blacklisting/pausable token, custody shortfall from a path not covered by the delta credit, or an owner-grown whitelist hitting gas limits). Severity is for the classifier; the availability surface is genuine.

### S-02 — `missing-inheritance`: `BatchNFTMinterMultiToken` does not formally implement `IMultiTokenNudgeWhitelist`, which `registerStream` relies on as a structural type-check
- **Location:** `src/BatchNFTMinterMultiToken.sol:159` vs `src/NudgeStreamer.sol:15-17`
- **Sources:** Slither `missing-inheritance` (Informational/High)
- **Assessment: LOOKS REAL as QA/Low — keep.** Normally pure noise, but here the duck-typed `isNudgeToken` call is **load-bearing by design**: `NudgeStreamer.registerStream` (`:127`) uses it as the one check that simultaneously proves whitelist membership *and* that the target is a MultiToken batchMinter (documented at `NudgeStreamer.sol:10-17`). Because the coupling is by convention rather than by inheritance, a future signature change on either side compiles fine and fails only at runtime as an unexplained `registerStream` revert. Declaring the interface would make the compiler enforce the guard the design already depends on. Owner-facing config hazard, not an exploit.

### S-03 — `unused-return`: `nftMinter.mint()` return value discarded in the mint loop
- **Location:** `src/BatchNFTMinterMultiToken.sol:650` (also legacy `src/BatchNFTMinter.sol:287`)
- **Sources:** Slither `unused-return` (Medium/Medium), Aderyn `Unchecked Return` (Low) — **corroborated by 2 tools**
- **Assessment: probably benign, but keep for one check.** The batcher mints straight to `recipient` and never needs the returned id, and budget accounting is driven by the re-read `configs()` price (`:646`), not the return. Worth one confirmation that `ITokenMinterV2.mint` genuinely cannot signal partial/no-op success via its return rather than reverting — if it can, a silent no-op mint would still decrement `budget` at `:649`. Downgrade to noise once that is confirmed.

### S-04 — no `ReentrancyGuard` at all on legacy `BatchNFTMinter`, while its MultiToken successor has one
- **Location:** `src/BatchNFTMinter.sol:62` (`contract BatchNFTMinter is Ownable, Pausable, IPausable`), `batchMint` at `:238-312`; contrast `src/BatchNFTMinterMultiToken.sol:159`
- **Sources:** Slither `reentrancy-events` on `BatchNFTMinter.batchMint`; corroborated by direct inspection (`grep -c nonReentrant src/BatchNFTMinter.sol` = **0**, every other non-interface contract has 4-9)
- **Assessment: REAL asymmetry, pre-existing and out of regression focus — surface, do not silently carry.** V1 is the frozen/deployed contract and prior runs may already have dispositioned this; the sanitizer/ledger should reconcile it rather than this agent culling it. Flagged because it is the only first-party non-interface contract with zero reentrancy protection, and its successor's NatSpec (`:154`) explicitly says the guard "is retained" — implying V1's absence was noticed but never backfilled.

### S-05 — `timestamp` comparisons in `NudgeStreamer` (KEPT per instruction — this suite is time-driven)
- **Locations:** `src/NudgeStreamer.sol:241` (`settled > 0` in `_settle`), `src/NudgeStreamer.sol:270` (`accrued > buffer` in `_accrued`); plus 65 further `timestamp` instances across the staker family
- **Sources:** Slither `timestamp` (Low/Medium) x67
- **Assessment: these two specific instances are Slither mis-attribution, but the detector class stays in the report.** Slither labels `settled > 0` and `accrued > buffer` as timestamp comparisons because both operands derive transitively from `block.timestamp - s.lastUpdate` (`:267`); neither is an actual timestamp threshold. However, the surrounding math **is** the load-bearing Linear-Depletion logic this suite has produced real findings from before (rate-drift class), so per the standing instruction the class is kept intact and forwarded rather than filtered — the dedup/severity stages decide, not this one. The remaining 65 instances sit in the unchanged staker family (`windowEnd`/`lastRewardTime` window arithmetic) and are pre-existing.
