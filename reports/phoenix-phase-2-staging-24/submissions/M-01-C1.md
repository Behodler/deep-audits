## Finding description and impact

### Severity

**Medium.**

Assets are not at direct risk, but protocol function and availability can be impacted: a half-applied one-shot cutover leaves mint paths reverting with no automated and no procedural detection, because every assertion in the script evaluates before dispatch and the story's designated post-broadcast human confirmation (story-072 checklist line 1195) is unticked. The assumptions (broadcast-time divergence) and external requirements (mainnet drift or a failed transaction during the session; an operator who does not self-verify) are stated, not hidden.

**Not High.** C4 High requires assets stolen, lost or compromised via a valid attack path. There is no attacker, no theft path and no demonstrated route to unrecoverable loss — every affected contract stays owner-controlled, `migrate` and `:resume` are re-runnable, and the fork run showed zero unintended state writes. Escalating an assurance-and-availability defect to High would be overstatement.

**Not Low.** Three facts jointly clear the Medium bar and none is hypothetical:

1. The undetected end state is a real availability impact — mint indices reverting `OnlyDispatcher` past the intended fail-closed window — not merely "we would not have a report".
2. The compensating control is not weak, it is **absent** on the broadcast path: the only outcome check the design defines (line 1195) is unticked at the time of this audit.
3. This defect is the enabling condition that converts three sibling Lows from theoretical to undetectable — L-01's stated backstop `require(old.totalStaked() == 0)` at `:1394`, L-05's trailing `require(balanceOf(OLD_BATCH_MINTER) == 0)` at `:1148`, and L-02's BPT conservation all evaluate in the same local pass.

The one-shot weight is applied deliberately. On a redeployable contract, "no post-deployment verification entry point" would be routine hardening. Here the operation cannot be re-run cleanly, the operator gets one Ledger session, and the designated human backstop is unticked — that is what moves it over the line rather than merely up the Low ordering.

#### Narrowed basis — and the limb that was rejected

This severity rests on a **narrowed** basis, and the exclusion is material enough to state up front.

The limb *"a 60+-transaction one-shot cutover can exit 0 while half-applied"* — i.e. forge returning exit code 0 while a dispatched transaction reverted on-chain — is **EXCLUDED FROM THE SEVERITY BASIS**. The fork run was a **PREVIEW** run (`PREVIEW_MODE=true`, no broadcast attempted), so forge's receipt-handling and exit-code behaviour under `--broadcast --skip-simulation --slow` on a reverted on-chain transaction was **never observed by this audit**. That limb is **reasoned, not evidenced**, and an unverified limb must not carry a severity.

The Medium therefore rests **only** on structural facts read directly from source and from the story:

- Phase 7 and every in-phase post-condition evaluate before dispatch (`run():400-411`, plus forge's local-pass execution model).
- Phase 8 is gated off entirely under broadcast (`run():402-408`).
- Story-072 checklist line 1195 is unticked (read verbatim from the story document).

Those three hold regardless of what forge's exit code does. The exit-code question is carried into the report as an **open operational question for the operator to confirm before the session**, not as a claim of this finding.

### Description

`promotion-ready:broadcast` runs `DeployMainnetPromotionReady.s.sol` — a 2,171-line, one-shot mainnet cutover signed on a Ledger — with `--broadcast --skip-simulation --slow`.

`forge script` executes the **entire Solidity body once, locally**, collecting calldata; the resulting ~60 transactions are then signed and dispatched afterwards. `--skip-simulation` does not change this: it removes the pre-send sanity check that each queued transaction would succeed against current chain state; it does **not** skip the local execution pass.

The consequence is that **every safety assertion in the script has already evaluated, against local pre-broadcast state, before transaction #1 leaves the machine.** That includes:

- Phase 0's 17-target ownership and drift preconditions;
- every in-phase post-condition — BPT conservation at `:892-895`, `newBM` balance unchanged at `:728-731`, `old.paused()` at `:1134`, `V1 totalStaked == 0` at `:1394`;
- the whole of `_phase7_wiringAssertions()`, the script's designated read-back gate.

They assert that the **plan** is internally consistent. They never assert that the **chain** matches it.

Phase 8 — which holds the BLOCKING probes, including the Kendu fee-on-transfer round trip and the positive `BatchDonatedViaPSM` donor-path checks — is guarded by `isPreview` and **does not execute under `--broadcast` at all** (`run():402-408`).

The design's compensating control is therefore entirely procedural: story-072 checklist line 1195, marked *"(Post-broadcast, HUMAN step)"*, which specifies a thorough on-chain confirmation — dispatcher configs 1/2/3/4/7 resolving to the new dispatchers with price and growth preserved, the retiring contracts drained and paused, the rescued ~349 USDC sitting in the streamer's buffer rather than on `newBM`, the ratchet hook's 70 phUSD `mintDebt` pulled, all five hooks reading their new dispatcher with ratio and recipient intact, **phUSD's minter set byte-identical to its pre-cutover state**, the new pooler holding the full 16,338.8190 BPT, each V1 staker drained and Pauser-deregistered with its V2 counterpart funded, every donor's `nudgeStreamer()` returning the new streamer, and `streams(newBM, USDC/phUSD/KENDU).duration` reading 10/30/30 days.

**Line 1195 is unticked.** So is its sibling, line 1197 (*"trigger one index-4 mint and assert `BatchDonatedViaPSM` fired — a green transaction is **not** evidence for the pooler"*).

This is compounded by a documented cascade. Commit `5ae94bd` exists to fix comment drift found in review. Post-review correction #1 removed a script comment that falsely claimed Phase 7 asserts mint-authority invariance, and **reassigned that check to "the post-broadcast HUMAN item at the end of this checklist"** — i.e. to line 1195. Because line 1195 is unticked, the correction transferred the obligation to a control that has not been discharged, and **no verification of mint-authority invariance now exists on any path.** The story's own remedy for the first drift created the second.

(The underlying "zero `phUSD.setMinter` calls, so mint authority is byte-identical by construction" argument was independently checked and found **sound** by this audit: all three `setMinter` call sites at `:799`, `:951` and `:1073` are `dispatcher.setMinter(NFTMinterV2)`. But a sound argument is not a control.)

**Net: on the broadcast path there is no outcome verification of any kind.**

### Impact

No assets are stolen, lost or made unrecoverable. The impact is on **protocol function and availability**.

A half-applied cutover leaves one or more of the five dispatcher indices in the fail-closed intermediate state the story itself documents (`hook.setDispatcher(new)` landed, `replaceDispatcher(idx, new)` not), so mints on that index revert `OnlyDispatcher` **indefinitely** rather than intermittently for the duration of the session as intended — and nothing in the tooling raises a signal.

Secondary exposures, each of which can be left one-sided by the same mechanism: donor → streamer routing, batch-minter whitelisting and stream registration, and staker migration across the three `NFTStakerDepletion` → `NFTStakerDepletionV2` legs.

**Likelihood: medium.** No adversary and no special conditions are required — only that something diverges during a multi-hour, 60+-transaction manual Ledger session over live mainnet state. The fork dry run is evidence that the **happy** path is sound; it is not evidence about the divergent path, because the run was PREVIEW and Phase 7 there ran against a state the same process had just produced locally.

**Recoverability:** recoverable by owner action — every mutation target remains owner-controlled and `migrate` / `:resume` are re-runnable by design. But recovery is gated on someone **noticing**, which is precisely what this finding says is absent.

### Proof of Concept

**No coded PoC is provided, and none is obtainable.** This is stated as a limitation, not as a formality.

Demonstrating the failure directly would require executing `npm run promotion-ready:broadcast` — an irreversible, Ledger-signed, one-shot mainnet cutover moving 16,338.8190 BPT, ~348.81 USDC and three staker populations — and arranging for a transaction within it to diverge. That is out of the question, and a fork cannot substitute: the defect is precisely that the local pass and the broadcast pass are different execution phases, and a fork PREVIEW run only ever exercises the local pass.

The finding does not depend on a PoC, because it rests on structural facts that are read rather than executed:

1. **Phase 7 and every in-phase assertion run before dispatch.** Read from `run():400-411` and from forge's documented local-pass execution model. `--skip-simulation` removes the pre-send simulation, not the local pass.
2. **Phase 8 never runs under broadcast.** `run():402-408` — `isPreview = vm.envOr("PREVIEW_MODE", false)` at `:368`; when false the script writes the progress file and skips `_phase8_previewSmokeTests()` entirely.
3. **Story-072 checklist line 1195 is unticked**, and line 1197 with it. Read verbatim from the story document.

Supporting evidence from the run-22 mainnet-fork PREVIEW execution of `promotion-ready:dry` at block **25659373** (exit 0, no revert, no progress file written) is recorded in the script-audit artifacts under `reports/phoenix-phase-2-staging-22/script-audits/promotion-ready-broadcast/` — in particular `side-effects.json`, whose `postconditionResults` record the two checks that returned `null` rather than pass: *"phUSD minter set byte-identical — NOT ASSERTED ANYWHERE"* and *"rescueERC20 still works on the paused old batch minter — NOT PROVEN"*.

## Recommended mitigation steps

**PRIMARY (from the auditor, endorsed by the classifier).** Add a read-only verification entry point — e.g. `promotion-ready:verify` — that re-runs `_phase7_wiringAssertions()` as a standalone `forge script --rpc-url $RPC_MAINNET` invocation against live **post-broadcast** state, and append it to the `:broadcast` and `:resume` npm chains after the patch script:

```
… && node scripts/patch-mainnet-addresses-promotion-ready.js && forge script script/…:VerifyPromotionReady --rpc-url $RPC_MAINNET
```

The refactor is mechanical: Phase 7 is already `internal view` and self-contained apart from the deployment addresses, which the progress file supplies. Until it exists, tick checklist line 1195 as a hard gate rather than an optional sweep.

**Conditions on the fix — both are conditions, not alternatives.**

**(1) BLOCKING FIX-ORDER DEPENDENCY — implement L-02 FIRST.** Relocating Phase 7 to a standalone post-broadcast run re-reads `bptAtPhase0` from an already-emptied `OLD_POOLER`, which makes the 16,338.8190 BPT conservation assertion **vacuous on the FRESH path too**, not just on resume. Shipping this fix without L-02's persisted-baseline fix would widen a sibling bug while appearing to close this one. **The verification entry point must consume a persisted `bptAtCutover` from the progress file, never a freshly-read Phase 0 value.**

**(2) ZERO-CODE INTERIM CONTROL, available for this session.** Tick story-072 checklist lines **1195 and 1197** as mandatory, blocking, signed-off steps in the runbook before the Ledger key is disconnected. This requires no change to the script and **discharges most of the impact on its own.**

**(3) OPEN OPERATIONAL QUESTION — confirm before the session.** Establish forge's actual behaviour under `--broadcast --skip-simulation --slow` when a dispatched transaction reverts on-chain: does it halt the sequence, and what exit code does it return? **This audit did not verify it and this finding does not depend on it** — but the answer determines how much of the gap the interim control in (2) must cover.
