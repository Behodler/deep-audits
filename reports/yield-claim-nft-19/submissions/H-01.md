### Severity label: CONDITIONAL High

The severity is deliberately labelled **CONDITIONAL High**, not High. The conditionality is part of the label because it is unresolved *in this report*, not merely hedged in prose:

**This report makes no claim about the live on-chain configuration.** `dispatcherIndex` is runtime storage on a *deployed* `BatchNFTMinterMultiToken`; it is not fixed by source, and this repository contains no `addresses.json`, deploy record, or broadcast artefact from which the live value could be read. In the deployment topology modelled by the PoC the batch path is pinned to an 18-decimal PAY-prime dispatcher, and under *that* modelled configuration the collision is dormant.

**Required before acting — verify against chain state:** read `dispatcherIndex`, resolve that index's dispatcher `primeToken()`, and test it with `isNudgeToken(...)`.

- Returns a nudge-whitelisted prime (e.g. USDC-prime while USDC is whitelisted) ⇒ **the pot is drainable now**; this is an unconditional live High requiring immediate action.
- Returns a non-whitelisted prime ⇒ the finding is dormant and the label stands at CONDITIONAL High: one ordinary owner transaction arms it.

The state is reached by a single ordinary owner transaction — `setDispatcherIndex(i)` selecting a dispatcher whose `primeToken()` is already on the nudge whitelist.

### The Law-3 footgun: a one-sided guard, documented as two-sided

The protocol demonstrably intends `paymentToken ∈ nudgeWhitelist` to be impossible, guards exactly one of the two directions that can produce it, and **tells the owner in NatSpec that the guarantee is structural**.

Guarded direction — `setNudgeTokenWhitelist` (`:250-256`) re-derives the payment path and refuses the add:

```solidity
(,, IERC20 paymentToken) = _resolvePaymentPath();
if (token == address(paymentToken)) {
    revert BatchMint__RewardTokenIsPaymentToken(token);
}
```

Its NatSpec (`:238-241`) describes that check as one **half** of a two-part exclusion:

> *"Adding (`allowed == true`) derives the payment token EXACTLY as `batchMint` does (via `_resolvePaymentPath`) and rejects the dispatcher's prime token — **the admin-time half of the §4.1 payment-token exclusion**."*

And `_resolvePaymentPath`'s own NatSpec (`:490-493`) states the guarantee in the strongest available terms:

> *"Used by both `batchMint` (step 2) and `setNudgeTokenWhitelist`'s add branch, so the admin-time payment-token exclusion is checked against exactly the token `batchMint` would derive — **by construction, not by convention**."*

Unguarded direction — `setDispatcherIndex` (`:198-201`) is a bare two-line setter with no reciprocal check:

```solidity
function setDispatcherIndex(uint256 newIndex) external onlyOwner {
    dispatcherIndex = newIndex;
    emit DispatcherIndexSet(newIndex);
}
```

This is the footgun in its sharpest form: an owner reading the source has been told the exclusion is enforced *by construction*, while the other half of the derivation — the input the payment token is derived **from** — is settable with no check at all. Repointing the index re-derives the payment token and silently produces exactly the state the guarded setter exists to reject.

**The authors did contemplate the repoint — and the property they concluded was safe is the one that fails.** The `_snapshotRewards` NatSpec (`:532-541`) reasons:

> *"The admin-time check in `setNudgeTokenWhitelist` prevents this at write time, but the owner can later repoint `tokenMinter`/`dispatcherIndex` and change the derived payment token out from under an existing entry; skipping keeps `batchMint` live instead of bricking it, **while the payment-token balance stays out of the payout**."*

The balance does stay out of the *payout*. It then leaves via step 10 to `msg.sender`, ungated. The documented safety property is exactly what does not hold.

The *caller* of the drain is unprivileged. The *setup* is an owner action, but not a malicious one: nothing on-chain warns that the selection has this consequence — no guard, no event, no view — and the NatSpec affirmatively tells the owner the opposite. Reported as a non-obvious owner footgun classified by the impact it unlocks, **not** as a centralization finding: the value is taken by an arbitrary third party, not by the owner.

### The denominator — four of five donor dispatchers

Stating it explicitly, since it decides whether the repoint is a corner case: `src/dispatchers/` in this repository holds **seven** concrete dispatchers (`ATokenDispatcherV2` is the abstract base). Two of them (`BurnerV2`, `GatherV2`) are not donor paths. Of the remaining five donor dispatchers, **four can be USDC-prime and are registerable as the batch index**: `PromotionUniV2_Eth`, whose `primeToken()` is a hard-coded `pure` USDC and therefore always collides; and `NudgeRatchet`, `Uniboost` and `NudgeRatchetDelayRelease`, whose prime token is a constructor argument and is USDC in this deployment topology. Only `BalancerPoolerV2` is structurally excluded — its prime is USDS (`IERC4626(sUSDS_).asset()`). The hazardous selection is therefore **four of the five donor dispatchers**, and `NudgeRatchetDelayRelease` in particular must not be overlooked when auditing candidate indices.

### Mechanism — the colliding token is skipped on payout but swept on exit

`_snapshotRewards` (`:549-566`) skips the colliding entry, so it is never paid through the reward path and its snapshot stays zero:

```solidity
if (rewardToken == paymentToken) continue;
uint256 available = qualifies ? IERC20(rewardToken).balanceOf(address(this)) : 0;
```

Value instead leaves through step 10, the residual-payment-token sweep (`:479-482`), which transfers the **full** balance to `msg.sender` and is **not gated on `qualifies`**:

```solidity
// --- 10. Dust sweep of residual payment token back to msg.sender. ---
uint256 remaining = paymentToken.balanceOf(address(this));
if (remaining / DUST_THRESHOLD != 0) {
    paymentToken.safeTransfer(msg.sender, remaining);
```

Consequently `count = 1` bypasses the `nudgeSize` gate entirely: `count(1) < nudgeSize(5)` makes `qualifies == false`, `_payRewards` pays nothing, and the whole pot exits via the ungated sweep. The mint itself is funded **out of the pot**, because step 6 (`:459`) grants the pinned `nftMinter` an unbounded allowance over the batch-minter's balance — the un-landed cap discussed above — so `paymentAmount` need not cover the mint price and the caller needs no capital. Net extraction is exactly `pot − mintPrice`, with no upper bound.

### Impact

The entire standing nudge pot — real USDC donated by prior minters and aggregated by the shared streamer — is transferable to whoever calls `batchMint` next, for a nominal payment, with no role, allowlist, or budget. The loss is total, permissionless, first-come, and repeatable on every refill. Measured in the PoC: **190.0 USDC extracted from a 200 USDC pot for a 1 wei payment**, plus a further **100 USDC** after the pot refilled.

Severity is CONDITIONAL High because the attack step itself contains no hypotheticals — no collusion, no price manipulation, no unusual market state — and the consequence is complete loss of user-funded value to an unprivileged party. The conditionality lies entirely in the enabling configuration: one routine owner transaction whose consequence is unsignalled on-chain and mis-signalled in NatSpec, plus the unverified live value of `dispatcherIndex`.

## Recommended mitigation steps

Both changes below are in `src/BatchNFTMinterMultiToken.sol` (`phoenix-nft-staking`). Nothing in `yield-claim-nft` requires modification.

Before either: **verify live chain state** — read `dispatcherIndex`, resolve its dispatcher's `primeToken()`, test against `isNudgeToken(...)`. A whitelisted result means the pot is drainable now and operational action (do not fund the instance; set a non-zero `pauser` per still-open ledger `919b71fd…`) precedes any code change.

### Primary — gate the step-10 sweep on `qualifies`

This is the recommended fix: it is one token, it closes the drain at the exit rather than at one of several entrances, and it introduces no new configuration-ordering constraint.

```solidity
uint256 remaining = paymentToken.balanceOf(address(this));
if (qualifies && remaining / DUST_THRESHOLD != 0) {
```

A non-qualifying batch can then never carry pot-sized value out, regardless of how the dispatcher index came to be set. Note the `else` branch must still assign `totalPaid` correctly for the non-qualifying case.

**This is deliberately not the change the 2026-07-21 closure deferred.** That closure set aside `refund <= paymentAmount` as *"a separate, larger change"* requiring the property to be *"established and tested"* first — a judgement this submission accepts. The `qualifies &&` conjunct establishes no accounting relationship between refund and contribution; it only prevents a batch that pays out nothing from carrying out everything. It can ship independently of, and ahead of, the deferred property.

### Secondary — the reciprocal setter guard, with a caveat

This is the remedy for open ledger Medium `fb17fc6d07…`, and it does **not** substitute for the primary fix (nor the primary for it).

The invariant `paymentToken ∉ nudgeWhitelist` is enforced today only on `setNudgeTokenWhitelist`. Enforcing it on `setDispatcherIndex` as well is desirable, **but the obvious implementation regresses an intentional property** and must not be shipped naively.

`_resolvePaymentPath` (`:494-510`) reverts `BatchMint__MinterNotConfigured` when `tokenMinter == 0`, and `BatchMint__DispatcherNotConfigured` when the resolved dispatcher config is empty. A guard that calls it unconditionally would make `setDispatcherIndex(non-zero)` uncallable before the minter is wired — breaking the deployment ordering the authors explicitly rely on. Their intent is on the record in the NatSpec at `:247-249`, which notes that whitelist *removal* "deliberately performs no payment-token derivation, so the owner can always shrink the whitelist even while the minter/dispatcher are unconfigured."

If the guard is added, the derivation must be guarded too — derive only when the path is already resolvable, and let the unconfigured case through unchecked (it cannot be exploited, since `batchMint` itself reverts on the same unresolvable path):

```solidity
function setDispatcherIndex(uint256 newIndex) external onlyOwner {
    uint256 prev = dispatcherIndex;
    dispatcherIndex = newIndex;
    if (newIndex != 0 && address(tokenMinter) != address(0)) {
        (address dispatcher,,,) = INFTMinterV2(address(tokenMinter)).configs(newIndex);
        if (dispatcher != address(0)) {
            address pay = ITokenDispatcherV2(dispatcher).primeToken();
            if (_nudgeTokenIndex[pay] != 0) {
                dispatcherIndex = prev;
                revert BatchMint__RewardTokenIsPaymentToken(pay);
            }
        }
    }
    emit DispatcherIndexSet(newIndex);
}
```

`setTokenMinter` should carry the same guarded check, since it too feeds `_resolvePaymentPath`.

Either change alone removes the drain. The sweep gate is sufficient on its own and is the safer single change; the setter guard additionally makes the hazardous configuration unreachable on-chain, which collapses this finding's precondition entirely and is the standing remedy for `fb17fc6d07…`.
