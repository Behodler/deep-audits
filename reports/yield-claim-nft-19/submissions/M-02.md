## Finding description and impact

### Summary

Story-046 made the `NudgeStreamer` the **only** delivery path out of `NudgeRatchet`. What is unique to `NudgeRatchet` is the **combination**, not each clause: it has no `try/catch` around the streamer call, no `donationSplit` or donation-disable switch, a `batchMinter` that cannot be zeroed, **and** no `rescueERC20`. No other donor dispatcher has all four.

Per clause, precisely: the absence of `try/catch` is shared — `BalancerPoolerV2` is the only donor dispatcher that has one (its `try this._psmDonate{} catch` failure-isolation envelope); `Uniboost`, `PromotionUniV2_Eth` and `NudgeRatchetDelayRelease` have none either. The absence of `rescueERC20` **is** individually unique among the donor dispatchers: `BalancerPoolerV2`, `Uniboost`, `PromotionUniV2_Eth` and `NudgeRatchetDelayRelease` each define one; `NudgeRatchet` does not. It is that last absence, combined with the newly-mandatory external delivery leg, that removes the last recovery route.

There is therefore no degraded mode: if the streamer call cannot succeed, every user mint at that dispatcher index reverts, and any USDC resident on the contract is unreachable by any actor, including the owner.

The whole delivery leg is `src/dispatchers/NudgeRatchet.sol:156-161`:

```solidity
if (bal > 0) {
    address streamer = nudgeStreamer;
    require(streamer != address(0), "NudgeRatchet: nudgeStreamer unset");
    IERC20(_token).forceApprove(streamer, bal);
    INudgeStreamer(streamer).collectNudge(batchMinter, _token, bal);
}
```

A revert here propagates through `ATokenDispatcherV2.dispatch` into `NFTMinterV2._executeMint` (`src/NFTMinterV2.sol:191`) and reverts the user's entire mint.

Trigger B's *deploy-ordering* sub-case is excluded on the same ground as A, and for the same reason: pre-declared in NatSpec, loud, pre-traffic. Only the **live repoint** sub-case is load-bearing.

**Trigger C is a low-probability tail, and the finding does not rest on it.** Blacklisting requires the USDC issuer to act against the streamer contract specifically — entirely out-of-protocol, historically rare, and not something an attacker can induce. It is included because it is the trigger that did not exist before story-046 and is therefore the *qualitative* change in the risk surface: it is uncontrollable by the protocol and uniquely irreversible. Because the streamer is **shared**, blacklisting it bricks every donor routed through it (verified for `NudgeRatchet` and `Uniboost` simultaneously) and **permanently strands the already-buffered pooled funds** — `pullPendingStream` reverts on `_settle`'s outbound transfer, and `NudgeStreamer` has no owner rescue of its own.

To be explicit about what carries the severity: **the Medium stands on the live-repoint sub-case of trigger B plus the invalidated-recovery-rationale half, and on nothing else.** Both are true without any external actor and without the excluded deploy-ordering case. Trigger A is not counted, because the finding's own Law-3 analysis excludes it. Trigger C escalates the worst case (irreversible, cross-donor, pooled-buffer loss) but is likewise not load-bearing. If a reviewer strikes both A and C, the Medium is unaffected — which is the point of stating it this way.

### Value is unreachable, and that is verified rather than assumed

With 500 USDC resident on the ratchet, an owner raw call to `rescueERC20(address,address,uint256)` returns `false` — the selector does not exist on the contract. The PoC pairs this negative with a **positive control**: the identical raw call against a freshly deployed sibling `NudgeRatchetDelayRelease` returns `true`. The absence is a real absence, not a mis-encoded call. The only forwarding path (`dispatch`) is the one that is reverting.

### This is an expired closure of ledger entry L-08 — the sweep is intact, do not restore it

Persistent ledger entry **L-08** (`0b97f155…`, *"NudgeRatchet has no rescueERC20; out-of-band USDC is permanently stranded"*) is marked `fixed` via story-038, on the owner's chosen alternative: a full-balance sweep inside `_dispatch`.

**That sweep is intact in source at `d4cc563`** (`src/dispatchers/NudgeRatchet.sol:142-162`). Nothing regressed and nothing was partially fixed, and **no part of this submission asks for the story-038 patch to be re-applied** — it is already present and correct. What changed is the *rationale the closure rested on*: ledger entry L-08 was closed explicitly *"on whether out-of-band USDC becomes recoverable, NOT on literal `rescueERC20` presence"*, and story-046 turned the sweep's only delivery leg into an external, cross-repository call that can revert. The self-cleaning property that made the missing escape hatch acceptable no longer holds.

The correct remedy is therefore a **new** escape hatch and/or a degraded mode.

### Vulnerability details — what the shipped NatSpec declaration does and does not cover

The contract's NatSpec (`src/dispatchers/NudgeRatchet.sol:33-35`) pre-declares trigger B: *"If the streamer is set but ops forgot `registerStream(...)`, every dispatch reverts `NudgeStreamer__NotRegistered()`. This is the accepted consequence of the mandatory-streamer decision, NOT an audit finding."*

That declaration is **correct and accepted for the deploy-ordering case**, and this submission does not contest it: a fresh deployment fails loudly on its first dispatch, before any user traffic exists, and a competent operator would not be surprised. That sub-case is excluded from the finding entirely.

The finding is confined to two states the declaration does not reach:

1. **The live repoint.** `setBatchMinter(new)` on an *already-live* dispatcher succeeds silently and arms the same revert on every subsequent user mint — after user traffic exists, with no local view or guard surfacing the missing registration, and with the cure (`registerStream`) living in a different repository that may not share the owner key. A loud first-dispatch failure at deploy time and a silent arming of a wedge under live traffic are different hazards; only the first is pre-accepted.
2. **The invalidated recovery rationale.** The declaration addresses the deliberate liveness coupling. It says nothing about the escape hatch having been omitted on a self-cleaning argument that story-046 subsequently invalidated. This is the load-bearing half of the finding: it is a second-order consequence of a later story, which the declaration's author had no occasion to consider when it was written.

Under Law 3 this is the footgun test rather than a centralization claim — the owner acts non-maliciously in both states, and would be surprised by the consequence in each.

### Impact and severity

**The Medium rests on stranded value.** With the live-repoint sub-case of trigger B arming the revert, `dispatch` — the sole forwarding path — is the thing that is reverting, so every USDC already resident on `NudgeRatchet` is unreachable by any actor including the owner, and there is no `rescueERC20` to reach it with. That is a standing property at `d4cc563`, not a hypothetical: the recovery rationale ledger entry L-08 was closed on has been invalidated by story-046, and nothing replaced it. Availability impairment travels with it (while the path is broken, mints at that index revert with no degraded mode), but availability alone is **not** what carries this to Medium — see the split note below.

Under trigger C the same stranding extends irreversibly to the pooled streamer buffer across every donor sharing the streamer. That escalates the ceiling; it is not needed to reach Medium.

Assets are not stolen and no third party gains what the protocol loses, so this is not High. Value is stranded with no escape hatch for any actor, which is squarely the C4 Medium band.

Severity is raised **on its own merits at `d4cc563`**, not inherited: ledger entry L-08 was Low on the strength of a self-cleaning sweep that made the missing escape hatch tolerable; at `d4cc563` that sweep's only delivery leg can revert, so the same code now produces unrecoverable resident value — materially worse than what L-08 described.

### Relationship to this run's QA `L-01` — do not merge

Run-scoped QA `L-01` ("Repointing a live dispatcher silently arms `NudgeStreamer__NotRegistered` on every subsequent mint", ledger `L-16` / `b0aa0f58`) covers the **same owner repoint on the same contract**, and a reader will reasonably ask why both exist. They are split on **consequence**, and each is complete without the other:

- **QA `L-01` is the AVAILABILITY finding.** It spans all three repointable dispatchers (`NudgeRatchet`, `Uniboost`, `PromotionUniV2_Eth`), and it says so explicitly: *"Impact: availability only. No value is at risk."* The revert is transaction-atomic, the failure is loud on the first mint after the repoint, and `NFTMinterV2`'s `config.disabled` is an owner backstop. That is correctly a Low.
- **M-02 is the STRANDING finding.** It is specific to `NudgeRatchet`, the only donor dispatcher lacking `rescueERC20`, and it concerns value **already resident** on the contract when the path breaks — which no amount of taking the index out of service recovers. This half does not exist on `Uniboost` or `PromotionUniV2_Eth` at all, because they each have a rescue.

Merging them would force one severity onto two different impacts: fold M-02 into `L-01` and the unrecoverable-value half is filed as "no value is at risk", which is false; fold `L-01` into M-02 and a Low availability issue on two contracts that *do* have a rescue is filed at Medium, which overstates it. The remediations differ accordingly — `L-01` wants an atomic repoint guard on all three dispatchers, M-02 wants an escape hatch and a degraded mode on `NudgeRatchet`. Neither fix closes the other.

## Recommended mitigation steps

The story-038 sweep is already in place and must be left alone. Three additions, in order of importance:

**1. Give `NudgeRatchet` an escape hatch.** This restores the recoverability property ledger entry L-08 was closed on, which the sweep alone no longer provides:

```solidity
function rescueERC20(address token, address to, uint256 amount) external onlyOwner {
    require(to != address(0), "NudgeRatchet: zero recipient");
    IERC20(token).safeTransfer(to, amount);
}
```

Mirror the NatSpec caveat already present on `NudgeRatchetDelayRelease.rescueERC20` regarding withdrawing backing for accrued mint-debt.

**2. Add a degraded mode so a broken streamer cannot brick user mints.** Either a `donationEnabled` switch matching `BalancerPoolerV2`, or wrapping the streamer call so a failed donation parks the balance instead of reverting the mint:

```solidity
if (bal > 0 && donationEnabled) {
    address streamer = nudgeStreamer;
    if (streamer != address(0)) {
        IERC20(_token).forceApprove(streamer, bal);
        try INudgeStreamer(streamer).collectNudge(batchMinter, _token, bal) {
            // delivered
        } catch {
            IERC20(_token).forceApprove(streamer, 0);
            emit DonationSkipped(_token, bal);
        }
    }
}
```

Parked USDC is then swept on the next successful dispatch exactly as story-038 intended, and is recoverable via (1) in the meantime.

**3. Add an owner rescue to `NudgeStreamer`.** Without it, a blacklist or any other outbound-transfer failure on the shared streamer strands the pooled buffer of every donor permanently, and no change confined to the dispatchers can recover it.

Additionally, amend the NatSpec declaration to scope it to the deploy-ordering case it correctly covers, and document the safe repoint ordering (`setNudgeTokenWhitelist` on the new batch-minter, then `registerStream` on the streamer, then `setBatchMinter`).
