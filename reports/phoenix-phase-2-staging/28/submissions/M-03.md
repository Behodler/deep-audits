## Severity

**Medium.**

Not High: there is no asset path and no attacker. The harm is loss of assurance and recovery capability, not loss of funds.

Not Low: the protocol's ability to **detect and recover from a bad mainnet cutover** is materially degraded, and a human-accepted remediation for a still-open fix-pending Medium was removed by an untagged sweep. Stranding 81 live findings with no verification path is a recall hazard in its own right. This finding escapes the local-chain ceiling that bounds the rest of the `dev` cluster outright: the code it concerns is **live on mainnet**.

Likelihood: certain. The state already exists at HEAD and the mainnet cutover has already broadcast. The external requirement is a future incident, audit, or resume attempt on that live cutover, which is what converts a latent loss into concrete harm.

## Description

At the diff base `1d8a3a7`, `promotion-ready:snapshot`, `:dry`, `:broadcast`, `:resume` and `:verify` all existed. At HEAD `f929b5b`, **only `:snapshot` survives**, at `package.json:45`:

```json
"promotion-ready:snapshot": "RPC_MAINNET=$RPC_MAINNET node scripts/snapshot-depletion-stakers.js && RPC_MAINNET=$RPC_MAINNET node scripts/snapshot-phlimbo-v2-stakers.js",
```

Four doc comments survive alongside it and still instruct operators to run the deleted keys — most explicitly `//order-of-execution:human-readable` on the very next line, `package.json:46`:

```json
"//order-of-execution:human-readable": "promotion-ready:snapshot then  promotion-ready:dry then promotion-ready:broadcast. After success, mint an LSP NFT and check that it truly pools on balancer. If the cutover fails, consult Claude on how to resume."
```

`:snapshot` is a pure JS snapshot step; the two keys the runbook names after it — the ones that actually broadcast and that the operator is told to resume from — are gone.

The underlying scripts were moved under `script/archives/`, which `foundry.toml:32` excludes:

```toml
skip = ["script/archives/**"]
```

They therefore cannot be run even by explicit path:

```
$ forge script script/archives/VerifyPromotionReady.s.sol:VerifyPromotionReady --rpc-url $RPC_MAINNET
Error: Could not find target contract
EXIT=1
```

Two facts aggravate this beyond ordinary tidying.

**First, `promotion-ready:verify` was the accepted fix for a live finding.** It was created by story 075 specifically to remediate fix-pending Medium `2c53e944caee…` — *"a broadcast run performs ZERO on-chain verification of its own outcome"*. Deleting it removes the remediation for a finding a human marked `fix-pending`, and **no story authorises the removal**: the purge of 246 `package.json` keys has no story anywhere in the enumerated 81-file story tree, while story 075 *adds* `:verify` and nothing anywhere removes it. (`2c53e944caee2e74a1a351c9b30b9e92cd8feac28203e8d5c1c9b7d9e8b4102f` lives on a different entry point, `promotion-ready:*`; because `entryPoint` is folded into the fingerprint, findings on different entry points never collapse. It is **cited here, not merged, and its status is not changed by this submission.**)

**Second, the cutover has already broadcast to mainnet.** Commit `4e5cca1` landed live addresses and `broadcast/DeployMainnetPromotionReady.s.sol/1/run-latest.json` is tracked in git. `:verify` and `:resume` are therefore not hypothetical future tooling — they are the post-hoc verification and recovery path for a migration that is **live**.

**The wider stranding is quantified.** 246 keys were deleted in this delta (287 → 41) and 108 files swept into `script/archives/`. An `entryPoint` tally against `reports/phoenix-phase-2-staging/ledger.json` shows **81 live (open or `fix-pending`) ledger findings had their entry point deleted by this delta** — including **23 open + 2 fix-pending on `promotion-ready:broadcast`** (the largest cluster, 25), 3 on `:verify`, 4 on `:resume`, 1 on `:dry`, plus the entire ys-swap and migration-saga families. An independent pass over the same ledger counted 90 live findings with no surviving entry-point key, of which 9 already had none at the diff base — leaving the same 81 attributable here. Their code survives under `script/archives/` but is **uncompilable**, so neither PoC replay nor `/recheck` has any path to re-prove or retire any of them.

## Impact

An operator following the surviving in-repo runbook is told to run three commands, two of which no longer exist and cannot be reinstated by path. The verification step for a migration **already executed on mainnet** is gone, reopening the exposure story 075 closed, and the resume path for a failed cutover is gone with it.

Separately, 81 live findings are frozen in an unresolvable state — not fixed, not abandoned, simply unreachable by the verification tooling. `abandoned` explicitly does **not** apply: the code is on master and merged, and nobody chose to live with these findings, so marking them abandoned would bury live bugs.

There is no direct on-chain loss, which is what caps this at Medium. What is degraded is the project's ability to detect or recover from a bad mainnet cutover.

## Recommended Mitigation

Restore at minimum `promotion-ready:verify` and `promotion-ready:resume` (keys **and** compilable scripts) — the cutover they cover is already live on mainnet and `:verify` is the accepted fix for fix-pending `2c53e944caee`.

For the rest, decide deliberately rather than by sweep: either keep the entry point and its script compiling, or delete the key **and** its orphaned doc comment together, and retire the corresponding ledger findings explicitly (`/ledger ... abandon`) rather than leaving them stranded.

If `script/archives/**` must stay in `skip`, add a CI check that every path referenced by a surviving `package.json` key or shell script resolves to a compilable target.
