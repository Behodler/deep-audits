# [M-01] `setRewardToken` silently re-keys the nudge stream and permanently bricks `claim()`, the sole permissionless entry point

**Severity:** Medium
**Contract:** `src/StableYieldAccumulator.sol`
**Root cause:** [`src/StableYieldAccumulator.sol#L417-L420`](https://github.com/Behodler/stable-yield-accumulator/blob/f7041304e4a71cc2325cf406974f5cc16a5b5322/src/StableYieldAccumulator.sol#L417-L420) (`setRewardToken`)
**Manifestation:** [`src/StableYieldAccumulator.sol#L595-L600`](https://github.com/Behodler/stable-yield-accumulator/blob/f7041304e4a71cc2325cf406974f5cc16a5b5322/src/StableYieldAccumulator.sol#L595-L600) (`claim`, nudge leg)

**C4 criterion satisfied:** Medium — *assets are not at direct risk, but protocol function or availability is impacted.* No value is stolen, lost or stranded on this path; the impact is a total outage of the protocol's only permissionless entry point.

---

## Finding description and impact

### Summary

`NudgeStreamer` keys every stream on the **pair** `(batchMinter, token)`. `StableYieldAccumulator` holds *both* halves of that key in mutable owner state — `nudge` and `rewardToken` — but the contract's own operational documentation treats only `setNudgeAddress` as an action that moves the key.

`setRewardToken` moves the same key, is not listed as a re-arm trigger, and emits no event. A single owner call rotating the reward denomination therefore points `claim()` at an unregistered stream slot, and every subsequent claim carrying a payable nudge share reverts `NudgeStreamer__NotRegistered()` (selector `0xd62cbfe8`) until an ordered repair is performed on two *other* contracts.

### Root cause

`setRewardToken` (`StableYieldAccumulator.sol:417-420`) is a bare assignment with a zero-address check, no rail guard, and — uniquely among the contract's load-bearing address setters — **no event**:

```solidity
function setRewardToken(address _rewardToken) external onlyOwner {
    if (_rewardToken == address(0)) revert ZeroAddress();
    rewardToken = _rewardToken;
}
```

Contrast the immediately preceding setter, `setPhlimbo` (`:405-411`), which emits `PhlimboUpdated`; `setNudgeAddress` likewise emits `NudgeUpdated`. `setPauser`, `setNudgeSplit`, `setNudgeStreamer`, `setNFTMinter`, `setTokenConfig` and `setDiscountRate` all emit as well. `setRewardToken` is the sole silent one.

The value written is consumed as half of the stream key in `claim` (`:595-600`):

```solidity
if (nudgeAmount > 0) {
    address streamer = nudgeStreamer;
    if (streamer == address(0)) revert NudgeStreamerNotConfigured();
    IERC20(rewardToken).forceApprove(streamer, nudgeAmount);
    INudgeStreamer(streamer).collectNudge(nudge, rewardToken, nudgeAmount);
}
```

On the receiving side, `NudgeStreamer.collectNudge` (`phoenix-nft-staking/src/NudgeStreamer.sol:138-143` @ `5015f1b`) rejects an unregistered pair before doing anything else:

```solidity
Stream storage s = streams[recipientBatchMinter][token];
if (s.duration == 0) revert NudgeStreamer__NotRegistered();
```

There is no `try/catch` envelope around the nudge leg — by design, per the in-source NatSpec — so the revert propagates and the whole `claim()` reverts.

### Why this is a finding and not obvious admin error

Under the repository's Law-3 test, an owner action is in scope when a competent, non-malicious owner would be **surprised** by the consequence. Here the contract itself creates the surprise. The NatSpec at `:69-79` presents a **closed enumeration**:

> "Once a nudge share is actually payable there are **three** failure modes, all deliberate and loud"
> …
> "3. Repointing the sink via `setNudgeAddress` re-arms exactly that failure mode: register the new `(sink, rewardToken)` pair on the streamer FIRST."

`setRewardToken` re-arms the identical failure mode, and appears in neither that list nor the four-step "Required ops ordering" runbook at `:81-88`. An owner who reads the documentation and follows it exactly still bricks the rail. The same NatSpec block additionally self-certifies failure mode 2 as "the accepted consequence of the mandatory-streamer decision, not an audit finding" — a statement that is factually incomplete about its own subject, and which carries no suppressive authority (no known-issues artefact backs it; see `review/validity-check.json` XC-3).

The missing event compounds the non-obviousness: the state change is invisible to off-chain monitoring, so the operator gets no signal at the moment of the mistake. (Detection still follows quickly from user-facing reverts, which is why this is an aggravator rather than an escalator.)

### Impact

- **Total outage of `claim()`**, which is the only permissionless entry point on the contract and the sole mechanism converting yield-strategy surplus into phlimbo rewards. The decentralized-conversion rail stops entirely.
- **Permanent until cured.** The outage does not heal with time; the PoC retries after +1d, +30d and +365d (396 cumulative days) and reverts identically. `_settle` never writes `s.duration`, and the only two sites that set it are `registerStream` (owner-only) and the constructor, so no ordinary activity can re-arm the key.
- **No assets at risk.** The revert occurs at the registration check *before* any transfer, and it rolls the entire `claim()` back — the claimer's payment, the skimmed surplus, the NFT burn and the streamer deposit all revert together. No partial-state value loss is reachable, and nothing is stranded.
- **Cure is not in this contract's hands.** Repair requires an ordered two-call sequence on two other contracts: `setNudgeTokenWhitelist(newToken, true)` on the batch minter **first**, then `registerStream(nudge, newToken, duration)` on the streamer. Reversing that order hits a second trap, `NudgeStreamer__NotWhitelisted` (`0x0dc85695`). The only unilateral lever the SYA owner holds, `setNudgeSplit(0)`, restores liveness by permanently abandoning the nudge rail — availability bought by deleting the feature.

### Preconditions and scope notes

- **Applies on the live-donation branch only.** The streamer requirement sits inside `if (nudgeAmount > 0)`; with `nudgeSplit == 0` the finding does not arise.
- **Deployment status, stated plainly.** `NudgeStreamer` and `BatchNFTMinterMultiToken` are **not yet deployed**. That is an input to urgency, not to validity: both exist as first-party source at a pinned commit (`phoenix-nft-staking` @ `5015f1b`), the PoC executes against the real `NudgeStreamer`, and `StableYieldAccumulator` at `f704130` already hard-depends on the streamer today — the direct `safeTransfer` nudge leg was **removed**, not retained as a fallback (`:58-64`, `:594-600`). The dependency is a property of the audited commit.
- **Ownership.** Shared ownership across the three contracts is **convention, not a code guarantee**: both curing contracts take a free `constructor(address initialOwner)`. The Medium ranking does **not** depend on ownership being split — it rests on the availability limb alone, with shared ownership assumed (the most favourable reading), in which case the cure is merely an ordering burden. **Reopen trigger:** if `NudgeStreamer` or `BatchNFTMinterMultiToken` is deployed under, or later transferred to, an owner key distinct from the SYA owner (`0xCad1a7864a108DBFF67F4b8af71fAB0C7A86D0B6`), or under a multisig/timelock that materially lengthens the repair window, this becomes a cross-party coordination outage and should be re-examined.

### What each step establishes

**Step 0 — the anti-vacuity tripwire is itself alive.** `_assertNotVacuous()` reverts on an unwritten state and stops reverting only once value has actually moved. Every negative assertion below is gated behind it, so a silently-empty harness cannot pass `0 == 0`.

**Step 1 — positive control (this is what makes the negative result non-vacuous).** A system configured by following the in-source runbook (`:81-88`) exactly and in order claims successfully and moves non-zero value on **all three** legs: **500000000** (500 USDC-shaped units) deposited into the streamer, **500000000** collected by phlimbo, and **1000000000** of yield delivered to the claimer, with zero reward-token residual stranded in the accumulator. The system provably works before the single owner call.

**Step 2 — the brick, with the exact selector.** From that working state, one call — `setRewardToken(newToken)`, with the new token otherwise fully configured (`setTokenConfig`, `approvePhlimbo`, claimer approval) — makes the very next `claim()` revert `NudgeStreamer__NotRegistered()`, asserted against the literal selector **`0xd62cbfe8`** (the test also asserts the selector has not drifted). A second independent attempt reverts identically, and the claimer's balance is unchanged, confirming the claim never landed. Nothing but the nudge rail is broken.

**Step 3 — storage proof: the key moved, nothing broke.** Reading `NudgeStreamer.streams` directly after the repoint:

| slot | `duration` | `buffer` |
|---|---|---|
| OLD `(sink, oldReward)` | **2592000** (30 days — still fully registered) | **500000000** (still holding the buffered nudge, live depletion rate intact) |
| NEW `(sink, newReward)` | **0** (unregistered — this *is* the brick) | 0 |

No state was corrupted and no value was destroyed. `StableYieldAccumulator` simply now reads an unregistered key.

**Step 4 — persistence.** Warping +1 day, +30 days and +365 days (396 cumulative) and retrying reverts with the same selector each time.

**Steps 5 and 6 — no unilateral cure.** `setNudgeSplit(0)` restores liveness, and the streamer's balance then never changes again: 100% routes to phlimbo and the nudge rail is dead. The genuine cure requires `setNudgeTokenWhitelist` **then** `registerStream`, on two other contracts; performing them in the reverse order reverts `NudgeStreamer__NotWhitelisted(sink, newReward)` (`0x0dc85695`).

## Recommended mitigation steps

**1. Gate the setter on the nudge rail's state.** Either refuse the repoint while the rail is live, or verify the destination pair is registered before committing it:

```solidity
event RewardTokenUpdated(address indexed oldToken, address indexed newToken);

function setRewardToken(address _rewardToken) external onlyOwner {
    if (_rewardToken == address(0)) revert ZeroAddress();

    // Option A (simplest): the rail must be disabled for the rotation.
    //   if (nudgeSplit != 0) revert NudgeRailActive();
    //
    // Option B (preferred): allow the rotation only into an already-armed pair.
    if (nudgeSplit != 0 && nudgeStreamer != address(0)) {
        (uint256 duration,,,) = INudgeStreamer(nudgeStreamer).streams(nudge, _rewardToken);
        if (duration == 0) revert NudgeStreamNotRegistered(nudge, _rewardToken);
    }

    address oldToken = rewardToken;
    rewardToken = _rewardToken;
    emit RewardTokenUpdated(oldToken, _rewardToken);
}
```

Option B is preferred because it enforces the required ordering (whitelist → `registerStream` → repoint) at the point of the mistake, rather than relying on the operator having read the runbook. Apply the same guard to `setNudgeAddress`, which re-keys the other half of the identical lookup.

**2. Emit an event.** `RewardTokenUpdated(old, new)` brings this setter in line with every other load-bearing address setter in the contract and gives off-chain monitoring a signal.

**3. Correct the NatSpec.** The enumeration at `:69-79` asserts "there are three failure modes" and is falsely exhaustive. Add `setRewardToken` as a fourth re-arm trigger, and extend the ops runbook at `:81-88` to cover reward-token rotation with its required ordering. The sentence "That is the accepted consequence of the mandatory-streamer decision, not an audit finding" should be removed or scoped, since it currently reads as blanket coverage for a trigger the document does not mention.

**4. Related hygiene (filed separately as L-05).** The same call strands the standing `approvePhlimbo` allowance, which remains denominated in the old token. Zero the old allowance and re-approve in the new denomination as part of the repoint.
