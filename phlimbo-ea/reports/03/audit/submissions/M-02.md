## Finding description and impact

### Summary

`PhlimboEA.collectReward` is `external nonReentrant` with no access control or minimum-amount guard. Every successful call re-runs `_updatePool()` and then re-anchors the linear-depletion clock with `rewardPerSecond = (rewardBalance * PRECISION) / depletionDuration`. Combined with the documented V1 rate-recompute behaviour, this lets *any* wallet pay 1 wei of reward token per call to perpetually reset the depletion window against a near-unchanged balance. The intended linear emission collapses into exponential decay, and material yield that the legitimate funder intended for active stakers is parked in `rewardBalance` and bled out over an indefinitely-extended tail.

This finding is deliberately scoped to the **permissionless surface**, not the inner re-anchor mechanic. The V1 rate-recompute is acknowledged by the project as a known issue inside `_updatePool`; what is new here is that `collectReward` exposes the same mechanic to arbitrary callers from the outside. Either of two unrelated fixes closes the attack: gating the function to an authorised funder, or making the re-anchor idempotent. The two fixes are independent; either alone is sufficient.

### Vulnerability details

[`Phlimbo.sol#L270-L286`](https://github.com/Behodler/phlimbo-ea/blob/1b1a32c4d1d7ec81a043f40ffe9a6d408c89d301/src/Phlimbo.sol#L270-L286):

```solidity
function collectReward(uint256 amount) external nonReentrant {
    require(amount > 0, "Amount must be greater than 0");

    // Update pool FIRST to accrue pending rewards before adding new balance
    _updatePool();

    // Pull tokens from stable-yield-accumulator
    rewardToken.safeTransferFrom(msg.sender, address(this), amount);

    // Add to reward balance
    rewardBalance += amount;

    // Recalculate rate based on new balance
    rewardPerSecond = (rewardBalance * PRECISION) / depletionDuration;

    emit RewardCollected(amount, rewardBalance, rewardPerSecond);
}
```

The function has three properties that compose into the attack:

1. **No access control.** There is no `onlyOwner` / `onlyFunder` modifier and no allowlist on `msg.sender`. The NatSpec describes the function as the entry point for the stable-yield-accumulator, but nothing on-chain enforces that role.
2. **No minimum amount.** The only floor is `amount > 0`, so a single wei of `rewardToken` clears the require.
3. **Mandatory rate re-anchor.** Each call unconditionally writes `rewardPerSecond = rewardBalance * PRECISION / depletionDuration`, re-projecting the *current* balance over a fresh `depletionDuration` window. Combined with `_updatePool()` having already drained `rewardBalance * dt / depletionDuration` for the elapsed slice `dt`, this turns the intended linear depletion into an exponential decay.

Concretely, with reward amount `R` and depletion duration `D`, a griefer that calls `collectReward(1)` every `dt` seconds across the window produces the recurrence

```
rewardBalance_{k+1} = rewardBalance_k * (1 - dt/D) + 1
```

The `+1` is dust. After `K = D/dt` calls (one full intended window), `rewardBalance ≈ R/e ≈ 0.368 R`, and the staker receives only `R * (1 - 1/e) ≈ 0.632 R` over the same horizon. The remaining ~36.8% is parked in the contract and emitted across an extended tail.

The economic cost to the griefer is `K * 1 wei` of `rewardToken` plus gas. On any L2 deployment this is negligible: 300 calls over a 1-hour-equivalent window cost 300 wei of reward token plus the gas budget — a per-block dust transaction.

### Impact

Stakers receive materially less than the funder's advertised emission schedule over the depletion window. The PoC measures the effect precisely:

| Quantity | Baseline (no grief) | Grief scenario | Delta |
|---|---|---|---|
| Staker `pendingStable` after `D = 3600s` | 99.99 e18 (≈ full `R`) | 63.27 e18 | −36.7% |
| `rewardBalance` left in contract at `T0 + D` | ~0 (dust) | 36.7 e18 (≈ `R/e`) | parked |
| Griefer cost | n/a | 300 wei of reward token + gas | trivial |

This is a value-leak Medium, not asset theft:

- **No reward tokens are stolen.** They remain in the contract.
- **Staker yield is reduced** in proportion to the suppression factor (`1 - 1/e` per full window under continuous grief).
- **Value accrues to the wrong cohort** — the parked tail leaks to whichever addresses are staked when it eventually emits, not the cohort the original funder intended to reward.
- **Affects every active staker pro rata** — the suppression is global to the pool, so the entire staker set is impacted by a single griefer.

Severity is Medium per the C4 criteria: protocol function (reward emission) is materially impaired, with a value-leak under stated assumptions (existence of a rational griefer with a 1-wei-per-call budget; V1 rate-recompute behaviour as observed in deployed code). Likelihood is bounded by whether anyone benefits from suppressing staker yield (short positions, competing protocols, social griefing), so we explicitly do not claim High.

### Proof of Concept

The full test lives at `workspace/phlimbo-ea/test/poc-M-02-collectReward-grief.t.sol` and is provided in the C4 PoC form field. It deploys two fresh instances with identical funding, runs an honest "no grief" baseline against a grief scenario in which an unauthorised wallet calls `collectReward(1 wei)` every `GRIEF_DT = 12s` for `NUM_GRIEF_CALLS = 300` iterations (one full `D = 3600s` window), and asserts the differential — strictly-lower staker `pendingStable`, ≥20% suppression, ≥25% parked tail, and exact 300 wei griefer cost. Parameters: `REWARD_AMOUNT = 100 ether`, `STAKE_AMOUNT = 1_000 ether`. The exponential-decay dynamics are scale-invariant in `dt/D`, so the 1-hour / 12-second test window is representative of, e.g., a 1-week window with ~5-minute griefer cadence on a real deployment.

Run with:

```
forge test --match-test test_M02_collectRewardGriefSuppressesYield -vv
```

Key forge log line:

```
Grief / baseline (bps)              : 6327
```

The measured suppression — staker receives 63.27% of the baseline (6327 bps) and 36.73% of `R` is parked in the contract — matches the theoretical `1 - 1/e ≈ 0.6321` ratio to three significant figures, confirming the exponential-decay model. Total griefer reward-token cost is exactly 300 wei.

## Recommended mitigation steps

Either fix below closes the attack independently. Pick one.

**Option A (preferred) — gate the surface.** Restrict `collectReward` to an authorised funder role, since the function semantically belongs to a single role (the stable-yield-accumulator) and has never been documented as a public top-up:

```solidity
address public funder;

modifier onlyFunder() {
    require(msg.sender == funder, "Not funder");
    _;
}

function collectReward(uint256 amount) external nonReentrant onlyFunder {
    require(amount > 0, "Amount must be greater than 0");
    _updatePool();
    rewardToken.safeTransferFrom(msg.sender, address(this), amount);
    rewardBalance += amount;
    rewardPerSecond = (rewardBalance * PRECISION) / depletionDuration;
    emit RewardCollected(amount, rewardBalance, rewardPerSecond);
}
```

Add an owner-only `setFunder(address)` and emit a `FunderUpdated` event. A minimum-amount threshold (e.g. `amount >= MIN_FUNDING_AMOUNT`) is a weaker variant — it raises the griefer's per-call cost but does not eliminate the attack against funders willing to spend it. Role-gating is the cleaner fix.

**Option B — make the re-anchor idempotent.** Remove the `rewardPerSecond` recompute from `collectReward` (and from `_updatePool` where the V1 KI lives) and instead derive the instantaneous rate from `(rewardBalance, depletionEndTimestamp)` set once per funding event. Under this model, an additional 1-wei top-up adds 1 wei to the in-flight schedule rather than re-projecting the entire balance over a fresh `D`. This is the design adopted in PhlimboV2 (rate-recompute removed from `_updatePool`) and removes the amplifier the permissionless surface relies on.

Either fix alone is sufficient. Applying both is safe.
