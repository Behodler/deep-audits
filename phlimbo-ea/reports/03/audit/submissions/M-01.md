## Finding description and impact

### Summary

`pauseWithdraw` decrements `user.amount` but does not update the user's `phUSDDebt` or `stableDebt` accumulator anchors. On the next user-driven entrypoint (`claim` / `withdraw` / `stake`), `_claimRewards` evaluates

```
(userDetails.amount * accPerShare) / PRECISION - userDetails.<token>Debt
```

with a minuend computed against the post-`pauseWithdraw` (smaller) amount and a subtrahend still anchored to the pre-`pauseWithdraw` (larger) amount. For any configuration in which the user has previously claimed against a non-zero accumulator, this expression underflows and Solidity 0.8 checked arithmetic raises `Panic(0x11)`, reverting the entire entrypoint.

### Lines of Code

- `src/Phlimbo.sol#L432-L455` — `_claimRewards` (subtraction site at L440 and L446)
- `src/Phlimbo.sol#L245-L261` — `pauseWithdraw` (decrements `user.amount` without rebasing debts)

### Root cause

`pauseWithdraw` (Phlimbo.sol#L245-L261) is documented as an "emergency exit" that "does NOT claim rewards or update pool". Its body executes:

```solidity
function pauseWithdraw(uint256 amount) external whenPaused {
    UserInfo storage user = userInfo[msg.sender];
    require(user.amount >= amount, "Insufficient balance");
    require(amount > 0, "Amount must be greater than 0");

    user.amount -= amount;          // <-- minuend shrinks
    totalStaked -= amount;
    IERC20(address(phUSD)).safeTransfer(msg.sender, amount);
    emit EmergencyWithdrawal(msg.sender, amount);
}
```

Note the missing updates: `user.phUSDDebt` and `user.stableDebt` are left untouched. The contract's reward-debt accounting invariant is

```
user.<token>Debt == user.amount * acc<token>PerShare / PRECISION
```

at the moment of the most recent debt write. `pauseWithdraw` breaks this invariant unilaterally by mutating only the left-hand side.

The next time `_claimRewards(user)` runs (Phlimbo.sol#L432-L455):

```solidity
uint256 pendingPhUSDAmount =
    (userDetails.amount * accPhUSDPerShare) / PRECISION - userDetails.phUSDDebt;
```

`userDetails.amount` is now strictly smaller than the amount used when `phUSDDebt` was last written, while `accPhUSDPerShare` is monotone non-decreasing. The minuend is bounded above by `pre_amount * accPhUSDPerShare / PRECISION`, which is exactly `phUSDDebt`. Any partial withdraw therefore makes the minuend strictly less than the subtrahend, and Solidity's checked subtraction reverts with `Panic(0x11)` (`Panic(uint256)` selector `0x4e487b71`, code `0x11`). The same reasoning applies verbatim to the `stableDebt` subtraction at L446.

### Who can trigger / when

Any user who:
1. has staked phUSD,
2. has been credited a positive `phUSDDebt` or `stableDebt` at any prior point (the canonical path is a prior `claim` against a grown accumulator, but `stake`/`withdraw` also write debt), and
3. partially exits via `pauseWithdraw` during a normal pause cycle.

After the pauser un-pauses, all of the user's normal-mode entrypoints (`claim`, `withdraw`, `stake`) revert. The pause cycle itself is a documented operational action and `pauseWithdraw(amount < user.amount)` is a valid input per the function signature; no privileged input, ordering trick, or unusual configuration is required.

### Impact

- **Permanent DoS** of `claim`, `withdraw`, and `stake` for the affected user. Every call routes through `_claimRewards` and reverts with `Panic(0x11)`.
- **In-motion yield loss.** Rewards accrued on the remaining stake (both phUSD emission and the stable reward token) become unclaimable through the normal path.
- **View-helper breakage.** `pendingPhUSD` and `pendingStable` share the same subtraction shape and revert with `Panic(0x11)` as well, breaking off-chain integrators, indexers, and front-ends that rely on those calls.
- **Principal is recoverable.** The user can still exit the remaining balance via another `pauseWithdraw` during a future pause, but doing so forfeits all rewards accrued on the surviving stake.

Per C4 special cases, an in-motion yield-loss DoS with principal recoverable caps at Medium even given a verified counterexample, hence the M-01 label.

### Verified evidence

- Forge invariant `INV-01` violated; the harness produced a 5-step shrunk counterexample of the same shape (`stake → warp → claim → pause → partial pauseWithdraw → unpause → claim ⇒ revert`).
- Halmos symbolic checks `SYMBOLIC-001` (static accumulator) and `SYMBOLIC-002` (100e18 canonical witness) both fail at the L440 subtraction.
- The PoC at `workspace/phlimbo-ea/test/poc-M-01-claim-underflow.t.sol` reproduces the panic deterministically and asserts the exact `Panic(0x11)` selector (not a generic `vm.expectRevert()`).

### Proof of Concept

The PoC mirrors the INV-01 shrunk counterexample. Alice stakes the canonical 100e18 phUSD witness, the reward donor seeds stable rewards, and time is warped 30 days so both accumulators grow materially. Alice then calls `claim()` (which anchors her `phUSDDebt` and `stableDebt` to the pre-pause `user.amount` of 100e18). The pauser pauses, Alice partially exits via `pauseWithdraw(60 ether)` so `user.amount` drops to 40e18 while both debts remain stale at their 100e18-anchored values, and the pauser unpauses. The test then asserts that the underflow precondition holds (`(amount * accPerShare) / PRECISION < storedDebt` for both reward tokens) and that every subsequent normal entrypoint — `claim()`, `withdraw(1 ether)`, `stake(1 ether, alice)` — and both view helpers `pendingPhUSD(alice)` and `pendingStable(alice)` revert with the exact Solidity 0.8 underflow selector `Panic(0x11)` rather than a generic revert.

## Recommended mitigation steps

Any one of the following resolves the underflow. Option A is the surgical fix and is preferred because it preserves the existing reward-debt accounting model.

**Option A — rebase debts inside `pauseWithdraw` (recommended).** After updating `user.amount`, recompute the user's debt anchors against the new amount. Call `_updatePool()` first so both accumulators are current:

```solidity
function pauseWithdraw(uint256 amount) external whenPaused {
    UserInfo storage user = userInfo[msg.sender];
    require(user.amount >= amount, "Insufficient balance");
    require(amount > 0, "Amount must be greater than 0");

    _updatePool();

    user.amount   -= amount;
    totalStaked   -= amount;

    // Re-anchor debts to the new amount so the invariant
    // debt == amount * accPerShare / PRECISION holds.
    user.phUSDDebt  = (user.amount * accPhUSDPerShare)  / PRECISION;
    user.stableDebt = (user.amount * accStablePerShare) / PRECISION;

    IERC20(address(phUSD)).safeTransfer(msg.sender, amount);
    emit EmergencyWithdrawal(msg.sender, amount);
}
```

Mirror the same accumulator rebase in `pendingPhUSD` / `pendingStable` (see L-14) so the view helpers stop underflowing for the same users.

**Option B — clamp on underflow in `_claimRewards`.** If `pauseWithdraw` must remain a strict "do nothing else" emergency path, treat the subtraction as a saturating one and zero out the pending if the minuend is below the stored debt:

```solidity
uint256 grossPhUSD = (userDetails.amount * accPhUSDPerShare) / PRECISION;
uint256 pendingPhUSDAmount = grossPhUSD > userDetails.phUSDDebt
    ? grossPhUSD - userDetails.phUSDDebt
    : 0;
```

Apply the analogous guard to the `stableDebt` subtraction and to `pendingPhUSD` / `pendingStable`. Note that Option B silently discards the rewards accrued on the surviving stake between the prior debt write and the `pauseWithdraw` — Option A preserves them.

**Option C — track absolute owed amount.** Replace the share-debt accounting with an explicit `user.pendingPhUSD` / `user.pendingStable` settled on every state change (including `pauseWithdraw`). This is the largest change and only worth considering if the share-debt model is being revisited for other reasons.
