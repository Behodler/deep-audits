## Finding description and impact

### Summary

`PhlimboV3._claimRewards` pays rewards with **reverting** transfers, and every self-service entry point calls it *before* moving the staker's principal. If a reward token's issuer blocklists a staker's address, that staker's `withdraw` reverts inside the reward leg and never reaches the principal transfer. `stake` and `claim` revert identically. The staker's phUSD principal becomes unreachable on every path they control.

The protocol already solved this exact problem — but only on the owner-driven flush path.

### Vulnerability details

**The ordering.** [`withdraw` at PhlimboV3.sol#L698](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L698) claims rewards before the principal moves at [#L723](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L723):

```solidity
_updatePool();

// Route auto-claim to msg.sender (caller) — consistent with stake/claim.
_claimRewards(user, msg.sender);          // :698  <-- reverts here
...
IERC20(address(phUSD)).safeTransfer(msg.sender, actualWithdrawAmount);   // :723  <-- never reached
```

**The reverting legs.** Inside [`_claimRewards` (PhlimboV3.sol#L844-L877)](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L844-L877), both token legs use `safeTransfer`, which bubbles the token's own revert:

```solidity
uint256 pendingRewardAmount = (userDetails.amount * accStablePerShare) / PRECISION - userDetails.stableDebt;
if (pendingRewardAmount > 0) {
    rewardToken.safeTransfer(beneficiary, pendingRewardAmount);       // :858  STABLE leg
}
...
if (address(promoToken) != address(0)) {
    uint256 pendingPromoAmount = (userDetails.amount * accPromoPerShare) / PRECISION - userDetails.promoDebt;
    if (pendingPromoAmount > 0) {
        promoToken.safeTransfer(beneficiary, pendingPromoAmount);     // :873  PROMO leg
        emit PromoClaimed(user, pendingPromoAmount);
    }
}
```

**The asymmetry.** The flush path, [`batchClaim` at #L471](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L471), handles the identical condition correctly — non-reverting `_tryTransfer` plus a per-user bank:

```solidity
if (_tryTransfer(promoToken, staker, pending)) {
    emit PromoClaimed(staker, pending);
} else {
    unclaimablePromoOf[address(promoToken)][staker] += pending;   // banked, pullable later
    ...
}
```

`_claimRewards` has no equivalent. The same staker, the same blocklist, the same protocol: handled on the rotation path, fatal on the everyday path.

### Two legs, one defect: the PoC'd promo leg (`:873`) and the conditional stable leg (`:858`)

The PoC exercises the **promo** leg, which requires an active promotion on a blocklisting partner token. The promo token is **owner-chosen** at `startPromotion`, so this leg is real on the deployed contract the moment a promotion runs on a token whose `transfer` reverts for a blocked recipient. That leg alone carries the finding.

The **stable** leg at `:858` is potentially much wider — it requires **no promotion at all**, so any period in which the protocol distributes a non-zero stable stream would expose every staker with a non-zero `pendingRewardAmount`. **This wider exposure is conditional and is not asserted here**, because it depends entirely on the deployed `rewardToken` being a *recipient*-blocklisting token (USDC-class — see the token-behaviour note below), and that cannot be established from the repository:

- `rewardToken` is an unpinned constructor argument ([PhlimboV3.sol#L210](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L210)), documented only as *"Address of the stable token for rewards"* (`:207`).
- The repo contains **no deploy scripts, no broadcast artefacts, and no hardcoded mainnet token addresses**. Every `USDC` reference in the source is confined to `MigratorV1V2`, which settles **V1** rewards — it describes neither V2's nor V3's constructor argument.

What the repo *does* establish is that a blocklisting stable is a **contemplated configuration of V3**: the project's own suite builds a full stack whose stable reward token is a blocklisting token, constructing `PhlimboV3` with it directly ([MigratorV2V3Test.t.sol#L720](https://github.com/Behodler/phlimbo-ea/blob/master/test/MigratorV2V3Test.t.sol#L720)) in a helper named `_setupBlocklistStableStack`, documented as *"Fresh V2/V3/migrator stack whose STABLE reward token is a MockBlocklistToken"*. The team therefore already treats a recipient-blocklisting `rewardToken` as a configuration V3 must survive — it simply never tests it against the self-service path.

**Open verification item for the team:** confirm the deployed V3 `rewardToken` address. If it reverts on transfer *to* a blocklisted address (USDC-class), the stable leg makes this a standing exposure of the everyday path and materially raises likelihood. If it is a plain ERC-20 with no recipient blocklist, only the promo leg applies.

The finding is Medium either way. Both legs share one root cause, one fingerprint, and one fix, and the mitigation below covers both.

### Impact

**Frozen, not stolen — and this is stated as the honest ceiling, not a hedge.** No attacker exists, no party profits, and no value is transferred. What the staker loses is *access*: every self-service path into their own position (`withdraw`, `stake`, `claim`) reverts, indefinitely, until a party they cannot compel intervenes.

The trigger requires no error by anyone in the system. A third party — the token issuer — blocklists an address for reasons unrelated to this protocol, and a staker who did nothing wrong loses access to principal the protocol is still holding for them.

**Why Medium and not High.** Recovery paths exist and the owner unilaterally controls them. [`pauseWithdraw` (#L596-L611)](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L596-L611) transfers **only** phUSD principal and never calls `_claimRewards`, so it does not touch the reverting transfer at all; and [`pause()` at #L576](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L576) is `pauser || owner()`. Once the owner pauses, each affected staker recovers their own principal via `pauseWithdraw` without any third party's cooperation. Principal is recoverable, so this does not meet the "assets stolen or lost" bar.

This ceiling is also required by this project's trust model: rating it High would mean assuming the owner **never** pauses — an owner-refusal premise the hierarchy forbids, since the owner is trusted to act non-maliciously. A finding may not borrow severity from an assumption that the trusted owner declines to use a control they hold.

**Why Medium and not Low.** **No rescue exists that is both one-action and non-protocol-wide.** Both available routes carry a real cost, and neither is a simple self-service fix:

1. **Protocol-wide pause** → `pauseWithdraw`. This halts `stake`, `withdraw` and `claim` for **every** user in order to rescue one. The remedy is itself an availability event.
2. **Migrator-routed claim** — narrower, but not free. [`claim(address user)` at #L738](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L738) is callable by `user || migrator` (`:740`) and routes `_claimRewards(user, msg.sender)` (`:755`), so a **migrator calling `claim(blockedUser)` receives the stable itself** — the blocked user is never the recipient. The debt realignment at `:757-759` then clears the pending, so the user's subsequent self-service `withdraw` no longer touches the reverting leg (`:857`/`:872` both guard on `pending > 0`). This unsticks one user without pausing. But it requires the owner to `setMigrator` to a **deployed helper contract** — repointing a live, privileged, protocol-wide role at a bespoke contract to work around one blocked address — and it **costs the affected user their rewards**, which land with the migrator rather than the staker.

So the owner's choices are: freeze the protocol for everyone, or deploy a contract and hand it the migrator role while the blocked staker forfeits rewards. Meanwhile the affected staker's access to their own principal is reduced to zero on every path they control. That is the C4 Medium clause ("the function of the protocol or its availability could be impacted"), not a reason to discount.

### This is a genuine footgun, not a reckless-admin issue

**No owner action is required at any step.** This is the cleanest statement of why the finding is in scope, and it is prior to any documentation argument. The trigger is a **third-party token issuer's blocklist decision** — an external party, acting for reasons unrelated to this protocol, on an address the protocol does not control and the staker cannot un-block. There is no misconfiguration to make, no privileged call to get wrong, and no user error. A staker who did nothing wrong loses access to principal the protocol is still holding for them, with the owner having done nothing at all. Nothing here rests on the owner behaving badly, or even acting.

**Supporting evidence — the contract's own documentation describes the case as solved.** The NatSpec at [PhlimboV3.sol#L445-L447](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L445-L447) reads:

> `Failed transfers (e.g. blocklisted recipients) are banked per-user into unclaimablePromoOf ... for later pull via claimUnclaimablePromo — the flush must never brick.`

This docblock is **scoped to `batchClaim`, and it is accurate there** — it is not a false statement, and it is not offered as the proof. Its relevance is narrower: an owner reading their own contract finds the blocklist case named, addressed, and demonstrably implemented, which makes it unlikely they would independently suspect the *other* paths handle the same condition fatally. It compounds the surprise; it does not create it.

**Corroborating evidence that the gap is real and unnoticed.** The project's own suite ships `MockBlocklistToken` ([test/Mocks.sol#L105](https://github.com/Behodler/phlimbo-ea/blob/master/test/Mocks.sol#L105)) and blocks a staker in **nine** separate tests in `PhlimboV3Test.t.sol` (L1658-L2072). Every one of them drives the owner-rotation path — `batchClaim`, then unblock, then `claimUnclaimablePromo`. In each test, every self-service call by the blocked staker occurs **only after** an unblocking `setBlocked(alice, false)`. **Not once does a staker call `withdraw`, `stake` or `claim` while blocked.** The blocklist condition is heavily tested; the self-service quadrant of it is the one quadrant never exercised. That is exactly where the defect lives.

### Token behaviour: this is a *recipient*-side blocklist (USDC-class, not USDT)

The exact semantics matter, because only one of the two major stables exhibits this:

- **USDC** (`FiatTokenV2_2.transfer`) is guarded by `notBlacklisted(msg.sender)` **and** `notBlacklisted(to)`. A transfer **to** a blacklisted address **reverts**. USDC is the token that exhibits this bug.
- **USDT** (`TetherToken.transfer`) checks only `require(!isBlackListed[msg.sender])` — **sender-side only**. A blacklisted USDT address can still *receive*. **USDT would not trigger this finding at all**, and no part of this submission relies on it.

The required property is precisely: a `transfer` that reverts because of the **recipient**. Any recipient-blocklisting token (USDC and the broad FiatToken-derived family) qualifies.

### Why the non-standard-token exclusion does not apply

C4's rule ([Severity_classifications.md:54](https://github.com/code-423n4/docs)) is: *"All non-standard/weird ERC-20 token and fee-on-transfer token findings are considered out of scope, **unless they're explicitly listed as supported tokens in the scope/documentation.** The only exception is USDT..."* — two independent escape hatches. This finding clears the **first and stronger** one, and does not need the USDT carve-out (which, per above, would not even fit).

1. **The protocol has explicitly declared this token class supported.** The NatSpec at `:445-447` names *"blocklisted recipients"* as a condition the protocol handles. The project ships `MockBlocklistToken` ([test/Mocks.sol#L105](https://github.com/Behodler/phlimbo-ea/blob/master/test/Mocks.sol#L105)) for exactly this, exercises blocklisted stakers in nine tests, and constructs a full V2/V3 stack using a blocklisting token as the **stable reward token** ([MigratorV2V3Test.t.sol#L720](https://github.com/Behodler/phlimbo-ea/blob/master/test/MigratorV2V3Test.t.sol#L720)). **You cannot ship a per-user bank for blocklisted recipients — and a test fixture that wires a blocklisting token in as V3's `rewardToken` — and then call blocklisted recipients out of scope.**

2. **The root cause is not the token.** The exclusion targets findings whose root cause *is* the token's weirdness. Here the root cause is PhlimboV3's own **ordering** (`:698` claims before `:723` moves principal) plus the **missing containment** — an internal asymmetry between two paths in the same contract handling the *same* condition, one hardened (`batchClaim`) and one not (`_claimRewards`). The token merely triggers a defect that lives entirely in first-party code. A reverting-on-recipient transfer is also standard, specified ERC-20 behaviour, not "weirdness".

3. **Prior art — the owner has already accepted this exact class.** Ledger entry `V3-M-01` (**Medium, fix-pending**) is *"MigratorV2V3 reverting/blocklisted reward recipient bricks the migration chunk (no in-contract recovery)"*, and audit-08 M-01 — the blocked-recipient brick in `batchClaim` — was **fixed** via story-027, which is where `_tryTransfer` and the bank came from. The same class, on sibling contracts, has been accepted as a fix-owed Medium and acted on. This submission reports the one remaining path.

### Assumptions and external requirements

- The reward token or promo token reverts on transfer **to** a blocklisted recipient (see above). For the promo leg this token is **owner-chosen** at `startPromotion`; for the stable leg it is the deployed `rewardToken`, which is an open verification item.
- The affected staker holds a non-zero pending on the blocked leg (`pendingRewardAmount > 0` at `:857`, or `pendingPromoAmount > 0` at `:872`). A zero pending skips the transfer and the position remains accessible.
- The token issuer must blocklist the staker. This is outside the protocol's control and outside the staker's control, and requires no error by either.

## Recommended mitigation steps

Mirror the pattern the protocol **already has**. Story-027 introduced `_tryTransfer` ([#L885](https://github.com/Behodler/phlimbo-ea/blob/master/src/PhlimboV3.sol#L885)) plus the per-user bank precisely so a blocked recipient could not brick the flush. Applying that existing, in-codebase, already-tested machinery to `_claimRewards` closes this finding. This is not new design.

Apply it to **both** legs — `:873` (promo) and `:858` (stable). Fixing only the PoC'd promo leg leaves the wider and likelier exposure live.

```solidity
     uint256 pendingRewardAmount = (userDetails.amount * accStablePerShare) / PRECISION - userDetails.stableDebt;
     if (pendingRewardAmount > 0) {
-        rewardToken.safeTransfer(beneficiary, pendingRewardAmount);
+        if (!_tryTransfer(rewardToken, beneficiary, pendingRewardAmount)) {
+            unclaimableStableOf[beneficiary] += pendingRewardAmount;
+            totalUnclaimableStable += pendingRewardAmount;
+            emit StableClaimFailed(beneficiary, pendingRewardAmount);
+        }
     }
...
     if (address(promoToken) != address(0)) {
         uint256 pendingPromoAmount = (userDetails.amount * accPromoPerShare) / PRECISION - userDetails.promoDebt;
         if (pendingPromoAmount > 0) {
-            promoToken.safeTransfer(beneficiary, pendingPromoAmount);
-            emit PromoClaimed(user, pendingPromoAmount);
+            if (_tryTransfer(promoToken, beneficiary, pendingPromoAmount)) {
+                emit PromoClaimed(user, pendingPromoAmount);
+            } else {
+                unclaimablePromoOf[address(promoToken)][beneficiary] += pendingPromoAmount;
+                totalUnclaimableOf[address(promoToken)] += pendingPromoAmount;
+                emit PromoClaimFailed(address(promoToken), beneficiary, pendingPromoAmount);
+            }
         }
     }
```

Notes for the implementer:

- The debt realignment in `withdraw`/`stake` (`:710-712`) already runs after `_claimRewards`, so banking preserves the entitlement exactly as `batchClaim`'s bank does — the pending is not erased.
- The promo bank must credit the **`beneficiary`**, matching `_claimRewards`' existing caller-routing semantics (`batchClaim` banks the `staker` because it forces the beneficiary to the user). Under self-service the two coincide; under migrator delegation the migrator is the beneficiary and is not the blocked party.
- The stable leg needs its own bank mapping and a pull, since `unclaimablePromoOf` is keyed on the promo token and is reserved by `finalizePromotion`. Any stable bank must be excluded from the distributable balance used by the cap at `:789` so a banked amount is not redistributed to other stakers.
- Reordering `_claimRewards` after the principal transfer is **not** an adequate alternative: it moves the principal out but leaves `claim` dead and still reverts the whole `withdraw` on the reward leg.

PhlimboV3::withdraw(1e21, alice)

### Caveat, stated plainly

`MockBlocklistToken` is a mock standing in for a recipient-blocklisting token. **The mock is the external token, not the code under audit.** The ordering defect the PoC proves — reward transfer before principal transfer, with no failure containment — is in real `PhlimboV3`, unmodified.

**The mock models USDC faithfully on the one property that matters.** Its `_update` override is `require(!blocked[to], "recipient blocked")` ([test/Mocks.sol#L119](https://github.com/Behodler/phlimbo-ea/blob/master/test/Mocks.sol#L119)) — it reverts on transfers **to** a blocked address, which is exactly USDC's `notBlacklisted(to)` guard. (It does **not** model USDT, whose blacklist is sender-side; as established above, USDT would not trigger this finding.) The mock is a faithful reproduction of the relevant leg, not an invented behaviour: substituting real USDC would require a mainnet fork with a live issuer blacklisting, and would exercise the identical code path. The project's own tests use this same mock for the same purpose — including as V3's stable `rewardToken`.

### Test source

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

import "forge-std/Test.sol";
import "../src/PhlimboV3.sol";
import "./Mocks.sol";

/**
 * @title PoC — promo blocklist freezes staker PRINCIPAL on the self-service path
 * @notice Story-027 hardened `batchClaim` against a blocked promo recipient
 *         (per-user bank + claimUnclaimablePromo pull). The SAME condition on the
 *         ordinary path is unhardened: `_claimRewards` (PhlimboV3.sol:873) uses a
 *         REVERTING `promoToken.safeTransfer`, and stake/withdraw/claim all run it
 *         before moving principal. A staker blocklisted on the live promo token
 *         therefore cannot withdraw their phUSD principal at all.
 */
contract PoC_PromoBlocklistPrincipalFreeze is Test {
    PhlimboV3 public phlimbo;
    MockFlax public phUSD;
    MockStable public rewardToken;
    MockBlocklistToken public blkPromo;

    address public alice = address(0x1);
    address public rewardDonor = address(0x3);

    uint256 constant STAKE_AMOUNT = 1000 ether;
    uint256 constant DEPLETION_DURATION = 604800;
    uint256 constant PROMO_AMOUNT = 1000 ether;
    uint256 constant PROMO_DURATION = 1_000_000;

    function setUp() public {
        phUSD = new MockFlax();
        rewardToken = new MockStable();
        phlimbo = new PhlimboV3(address(phUSD), address(rewardToken), DEPLETION_DURATION);
        phUSD.setMinter(address(phlimbo), true);

        phUSD.mint(alice, 10000 ether);
        vm.prank(alice);
        phUSD.approve(address(phlimbo), type(uint256).max);

        rewardToken.mint(rewardDonor, 10000 ether);
        vm.prank(rewardDonor);
        rewardToken.approve(address(phlimbo), type(uint256).max);

        // Live promo funded with a USDC-style recipient-blocklisting token.
        blkPromo = new MockBlocklistToken();
        blkPromo.mint(address(this), PROMO_AMOUNT);
        blkPromo.approve(address(phlimbo), type(uint256).max);
    }

    function test_PoC_blocklistedStakerCannotWithdrawPrincipal() public {
        // 1. Alice stakes 1000 phUSD.
        vm.prank(alice);
        phlimbo.stake(STAKE_AMOUNT, alice);
        assertEq(phUSD.balanceOf(alice), 9000 ether, "stake did not land");

        // 2. Owner starts a promotion on the blocklisting token.
        phlimbo.startPromotion(address(blkPromo), PROMO_AMOUNT, PROMO_DURATION);

        // 3. Time passes; Alice accrues promo.
        vm.warp(block.timestamp + 10_000);
        assertGt(phlimbo.pendingPromo(alice), 0, "alice should have accrued promo");

        // 4. The token issuer blocklists Alice. She did nothing wrong; the protocol
        //    has no control over this, and its own comments name it as a live threat.
        blkPromo.setBlocked(alice, true);

        // 5. Alice tries to exit. Her PRINCIPAL is now unreachable: _claimRewards'
        //    reverting promo transfer (PhlimboV3.sol:873) fires before the phUSD
        //    principal transfer at :723 and takes the whole tx down.
        vm.prank(alice);
        vm.expectRevert("recipient blocked");
        phlimbo.withdraw(STAKE_AMOUNT, alice);

        // 6. Every other self-service path is dead too.
        vm.prank(alice);
        vm.expectRevert("recipient blocked");
        phlimbo.claim(alice);

        vm.prank(alice);
        vm.expectRevert("recipient blocked");
        phlimbo.stake(1 ether, alice);

        // 7. Principal is still in the contract; Alice cannot retrieve it.
        (uint256 amt,,,) = phlimbo.userInfo(alice);
        assertEq(amt, STAKE_AMOUNT, "principal still locked in the farm");
        assertEq(phUSD.balanceOf(alice), 9000 ether, "alice never got her principal back");
    }

    /// @notice Contrast: the FLUSH path handles the identical condition gracefully.
    ///         This is the asymmetry — batchClaim was hardened, _claimRewards was not.
    function test_PoC_contrast_flushPathHandlesSameConditionFine() public {
        vm.prank(alice);
        phlimbo.stake(STAKE_AMOUNT, alice);
        phlimbo.startPromotion(address(blkPromo), PROMO_AMOUNT, PROMO_DURATION);
        vm.warp(block.timestamp + 10_000);
        blkPromo.setBlocked(alice, true);

        // The owner-driven rotation absorbs the blocked recipient by banking.
        phlimbo.beginFlush();
        phlimbo.batchClaim(10);
        assertGt(phlimbo.unclaimablePromoOf(address(blkPromo), alice), 0, "banked");

        // ...and only AFTER a full rotation (promoToken -> 0) can Alice move again.
        phlimbo.finalizePromotion(address(this));
        phlimbo.unpause();

        vm.prank(alice);
        phlimbo.withdraw(STAKE_AMOUNT, alice); // now succeeds
        assertEq(phUSD.balanceOf(alice), 10000 ether, "principal only recoverable via full rotation");
    }
}
```
