### [L-01] Migrator-leg phUSD bank is credited to an address with no pull, and is not sweepable <!-- id: pe11l1 -->

**Location**: [`src/PhlimboV3.sol#L913-L918`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol) (`_claimRewards` phUSD catch), [`src/PhlimboV3.sol#L644`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol) (`claimUnclaimablePhUSD`), [`src/MigratorV2V3.sol#L254-L268`](../../../../lib/phlimbo-ea/src/MigratorV2V3.sol)

**Description**: Under migrator delegation the `beneficiary` passed to `_claimRewards` is
MigratorV2V3, so a failed phUSD mint banks to `unclaimablePhUSDOf[migrator]`. The pull is
strictly `msg.sender`-keyed:

```solidity
function claimUnclaimablePhUSD() external nonReentrant {
    uint256 amount = unclaimablePhUSDOf[msg.sender];
    ...
}
```

There is no pull-on-behalf variant and no call-through on the migrator. MigratorV2V3's complete
external surface was enumerated (`seedUsers:144`, `migrate:172`, `migrateOne:235`,
`skipCurrent:284`, `claimUnclaimable:302`, `withdrawAll:318`, `userCount:370`) — none reaches
`PhlimboV3.claimUnclaimablePhUSD()`. Because the phUSD was **never minted**, the entry is also
invisible to `emergencyTransfer` and `withdrawAll`, which both sweep `balanceOf`.

**Impact**: No principal at risk and no balance-sheet impact — the tokens were never minted, so
nothing is locked or diluted. The loss is one straggler-pass migrant's accrued phUSD reward
entitlement, discharged on-chain (`phUSDDebt` is realigned caller-side at `:715`) but never
delivered. Triple-gated: (1) non-zero `desiredAPYBps` — **not shipped**, `:60` is uninitialized
so `if (pendingPhUSDAmount > 0)` at `:903` is never true and this path is currently dead code;
(2) an *individual* phUSD mint-authority outage (a global revoke self-heals loudly via
`UserMigrationSkipped`); (3) a second/straggler pass over a user who already holds a V3 position
(`:898-900` early-returns on a first pass).

**Why Low, and what the severity rests on**: the Low rests **entirely** on the owner's
out-of-band remedy being available — `setMinter(owner,true)` then `phUSD.mint(user,amount)`,
against an uncapped supply. That remedy was stress-tested in source rather than assumed:
`FlaxToken.mint` (`:58`) is minter-gated, not owner-callable, but `setMinter` (`:44`) is
`onlyOwner` and re-stamps the current `mintVersion`, and `revokeAllMintPrivileges` (`:88`) only
increments `mintVersion` — reversible, not a permanent supply lock. Had it been irreversible,
this would be a Medium.

> **PRESERVED MEDIUM DISSENT (`severityAdjudication.preservedDissent`) — do not drop.**
> The mechanism below was **ADOPTED as correct** by the classifier; only the severity is
> disputed (3 Low vs 1 Medium; classifier reached Low independently).
>
> story-031 converted a **loud, self-healing** failure into a **silent, permanent** one on this
> leg. *Pre-fix*: the mint reverts inline → `_claimRewards` reverts → `stake` reverts →
> `migrateOne` reverts → `migrate:204`'s `catch` catches → `UserMigrationSkipped(reason)` is
> emitted → the cursor advances → **the user's V2 position is untouched** → the owner (whose own
> docstring says they MUST read these events after every pass) restores authority, re-runs, and
> the user is made whole. *Post-fix*: the revert is swallowed → `migrateOne` **completes** → the
> balance-delta at `MigratorV2V3:260` reads 0 → `_forward:268` forwards nothing → the V2 position
> is consumed, the V3 position created, the migration **reports success**, and the reward is
> stranded. The fix introduced a new loss path that did not previously exist.
>
> **What would flip the severity to Medium**: if PhlimboV3's owner and FlaxToken's owner are
> **different parties**, the out-of-band mint is not unilaterally available, "unrecoverable"
> becomes true in practice as well as on-chain, and the dissent's Medium is correct. This is a
> deploy-time config question, not answerable from the repo, and is the highest-value open
> question in the run.

> **CRITICAL_FIX_NOTE — relationship to `V3-L-15` (166e6393, open, low).**
> L-01 **relates to but is NOT identical to** V3-L-15. V3-L-15 is scoped to the **stable and
> promo** banks and earned its Low on a token-specific rationale ("value is not lost — owner
> `emergencyTransfer` sweeps it") that provably does **not** reach the un-minted phUSD bank.
> **V3-L-15's forwarder-as-written closes the stable and promo banks and would leave the phUSD
> bank stranded — an incomplete fix that reads as done.** Fixing V3-L-15 as written does **NOT**
> fix L-01. Widen V3-L-15's recommendation to also cover `claimUnclaimablePhUSD`.

**Recommendation** (in preference order):

1. *Closes the class* — add a pull-on-behalf variant on PhlimboV3 so no address can hold an
   unreachable entry. This is the only option that survives a future integrator being wired as a
   `beneficiary`, and it also makes the `:637-643` docblock true as written (see `F-11-01`).

   ```solidity
   function claimUnclaimablePhUSDFor(address beneficiary) external nonReentrant {
       uint256 amount = unclaimablePhUSDOf[beneficiary];
       // ... credit the RECORDED beneficiary, not msg.sender
   }
   ```

2. *Closes only the known migrator* — add a call-through on MigratorV2V3 that calls
   `PhlimboV3.claimUnclaimablePhUSD()` inside a `try/catch` after `phlimboV3.stake(...)`, so a
   banked accrual is re-minted into the migrator and picked up by the existing delta + `_forward`
   accounting. A positive-control test proves this suffices for the known migrator.

3. **MANDATORY, owed to the dissent** — whichever fix is chosen must **restore loudness, not
   merely reachability**. A fix that makes the value recoverable but leaves the migration
   silently reporting success on a failed reward leg closes only half of what story-031 opened.
   `Q-01`'s reason-capture is a prerequisite.

*Rejected without a story decision*: crediting the bank to `user` rather than `beneficiary`. The
catch block's own comment ("Credits the BENEFICIARY, mirroring the stable leg below") shows the
routing was deliberate and internally consistent — this is a design decision to reverse, not a
bug to patch.

**Test blind spot**: the 5 new `PhlimboV3PhUSDMintBankTest` tests declare `address migrator =
address(0x5)` but never call `phlimbo.setMigrator(...)` — the address is used only as a funded
ordinary staker. Every new test exercises `beneficiary == msg.sender == user`, the one routing
where the pull always works. story-031 shipped with tests structurally incapable of failing on
its own new loss path. The Tier-3 green is **silent here, not exculpatory**.

**Safe config until fixed**: do not set a non-zero `desiredAPYBps` while MigratorV2V3 is the
active migrator and lacks a call-through. If phUSD mint authority must be revoked during a
migration window, pause the migration first — or prefer a *global* `revokeAllMintPrivileges`
(self-heals loudly) over an *individual* `setMinter(phlimbo,false)` (strands silently). This
inverts the usual intuition that the narrower action is the safer one and belongs in the runbook
explicitly.

### [L-02] The phUSD bank survives the terminal `emergencyTransfer` ejector seat and mints fresh supply from a paused, drained contract <!-- id: pe11l2 -->

**Location**: [`src/PhlimboV3.sol#L360-L378`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol) (`emergencyTransfer`), [`src/PhlimboV3.sol#L644-L649`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol) (`claimUnclaimablePhUSD`)

**Description**: `emergencyTransfer` is a **balance sweep** plus `_pause()`. It neutralizes the
stable and promo banks as a side effect — their tokens are gone, so their pulls revert — but it
cannot reach the phUSD bank on either axis:

- **The sweep cannot see it**: the phUSD was never minted, so there is no balance to sweep.
- **The pause cannot stop it**: `claimUnclaimablePhUSD` is deliberately not pause-gated —
  `function claimUnclaimablePhUSD() external nonReentrant` carries no `whenNotPaused` modifier,
  and mints at `:649`.

While PhlimboV3 retains mint authority, every outstanding bank entry stays pullable **after** the
ejector seat has fired, minting brand-new phUSD supply the sweep never accounted for.

**Impact**: Post-terminal double-pay. Fresh, unbacked supply is minted after wind-down against a
contract with `balanceOf == 0` and `paused == true`; the loss is dilution of phUSD holders. No
attacker and no theft — the holder is claiming exactly what the contract records as owed.
Double-gated (dormant reward stream + non-empty residual bank at sweep time).

**Why this is an in-scope Law-3 footgun**: the sweep **visibly neutralizes the other two banks**,
inviting the inference that it neutralizes all three. The asymmetry is the whole footgun. A
competent, non-malicious owner firing a terminal hatch and observing two of three banks die with
it would be genuinely surprised that the third survives and can still mint.

**Recommendation — a RUNBOOK step, not code in the hatch**:

> **Ejector-seat compliance.** On this project `emergencyTransfer`/`pauseWithdraw` are ejector
> seats **by design** (story-022, "recovery out-of-band"). **Never propose accounting inside
> them.** A prior finding (`pe7m2`) was closed **INVALID** for proposing in-hatch accounting;
> this finding does **not** re-file it and must not be closed as if it did. The hazard is a
> liability that *outlives* the terminal action and lives entirely *outside* it, so the remedy is
> correspondingly operational.

Add a mandatory step to the `emergencyTransfer` runbook: **revoke PhlimboV3's phUSD minter role**
(`FlaxToken.setMinter(phlimbo,false)`, or `revokeAllMintPrivileges()`) so the terminal action
actually terminates the mint obligation. Ordering matters — revoking *before* the sweep is
equally effective and leaves no window at all. Document in `SolvencyDetermination.md` that
`emergencyTransfer` alone does **not** extinguish the phUSD bank, **unlike** the stable/promo
banks; stating the asymmetry plainly is the fix. If a code change is ever preferred over the
runbook, the correct site is a documented note at `:644` — **not** accounting in the hatch.

*Do not collapse with L-01*: same state variable, **opposite** failure mode. L-01 is a bank
credited to an address that **cannot** pull (a strand); this is a bank that **can** pull, by the
right holder, but **after** terminal wind-down (a double-pay).

### [L-03] Read-only reentrancy on the stale `pending*` views during `_claimRewards` <!-- id: pe11l3 -->

**Location**: [`src/PhlimboV3.sol#L993`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol) (`pendingPhUSD`), `#L1014` (`pendingStable`), `#L1040` (`pendingPromo`); callback surface at `#L954` (`_tryTransfer(promoToken, ...)`)

**Description**: State-changing reentrancy is **fully blocked** — OZ `ReentrancyGuard` is a
single contract-wide lock and every value-handling external entry point carries `nonReentrant`
(`stake:694`, `withdraw:739`, `claim:789`, `batchClaim:485`, `collectReward:669`, and all three
`claimUnclaimable*` pulls). The surviving leg is read-only. Debt realignment is **caller-side**
(`:715-717`, `:761-763`, `:808-810`), so throughout `_claimRewards` all three debts are stale:
phUSD is already minted (`:913`) and stable already transferred (`:930`) while `phUSDDebt` /
`stableDebt` still hold pre-claim values. The `pending*` views read those debts directly and are
not covered by `nonReentrant` (views never are), so during a callback originating inside
`_claimRewards` they report **full pending for value already delivered**.

Reachable only via an owner-chosen hooked (ERC777-class) promo token: `startPromotion` (`:391`)
rejects only `address(0)`, phUSD and `rewardToken` — it does not exclude hooked tokens. The
promo `_tryTransfer` at `:954` is the only inbound-callback surface inside `_claimRewards` (phUSD
and the USDC-class `rewardToken` have no transfer hooks).

**Impact**: No value at risk inside PhlimboV3; its own accounting stays correct throughout. The
harm lands on a hypothetical downstream integrator consuming the `pending*` views as an
entitlement oracle, which would double-count. No such integrator exists in scope.

**Boundary note (carried honestly)**: this sits **on the Low/QA line** and is **low-confidence**;
a human could defensibly move it to QA. *Case for QA*: the impact is on an integrator that does
not exist and both preconditions are unestablished. *Case for Low (held, narrowly)*: read-only
reentrancy is a recognized C4 class with a real, verified window, and the `pending*` views **are**
the protocol's external integration surface — precisely what a future integrator reaches for.
Kept at Low because the QA bundle is where a real-but-narrow integration hazard goes to be
ignored, and this one goes live the moment anyone builds on these views. **Confidence and
severity are independent judgements**: it is surfaced despite low confidence because an
uncleared reentrancy-checklist row is a recall risk, not a pass (Law 1).

**Recommendation**: Cheapest robust fix — exclude hooked/ERC777 tokens by policy in
`startPromotion`'s NatSpec; the fee-on-transfer rejection at `:401-403` already establishes
exactly this pattern in exactly this function. If any integrator is ever wired to the `pending*`
views, document that they are **not callback-safe**.

> **Do not refactor casually**: moving debt realignment inside `_claimRewards` is structurally
> cleaner but larger and riskier — the caller-side placement is **load-bearing** for the banking
> design's correctness (it is what makes paid and banked paths settle identically, per the
> `:904-911` comment).

### [L-04] Tested bytecode is not deployable bytecode: builds pin `via_ir = false` while the deploy vehicle compiles with `via_ir = true` <!-- id: pe11l4 -->

**Location**: [`foundry.toml`](../../../../lib/phlimbo-ea/foundry.toml) (`via_ir = false`, story-031 / `f279c62`); [`lib/phoenix-phase-2-staging/foundry.toml`](../../../../lib/phoenix-phase-2-staging/foundry.toml) (`via_ir = true`, `optimizer_runs = 10000`, remaps `@phlimbo-ea/=lib/phlimbo-ea/src/`)

**Description**: story-031 sets `via_ir = false` for every build this repo performs, while
explicitly blessing deployment **with** via_ir ("Deploying with via_ir is safe"). The sibling
phoenix-phase-2-staging — the established deploy vehicle, which already deploys Phlimbo V1/V2 —
sets `via_ir = true` and compiles phlimbo-ea **from source**. The pipelines differ materially,
verified empirically at HEAD:

| Pipeline | Runtime size | EIP-170 margin |
|---|---:|---:|
| legacy + optimizer (tested) | 15,979 B | +8,597 B |
| via_ir + optimizer (deployed) | 14,529 B | +10,047 B |

A 1,450 B (~9%) codegen delta. The 365-test suite — including story-031's own new
`PhlimboV3PhUSDMintBankTest` — only ever executes legacy bytecode. PhlimboV3 has **zero test
coverage of the bytecode that would actually be deployed**.

**Impact**: An **assurance gap**, not a demonstrated bug — recorded as such, and deliberately not
overstated. The author is right on the substance and this is recorded in their favour: the
`via_ir` + `vm.warp(block.timestamp + X)` diagnosis is a real, well-known solc/cheatcode
interaction, not a contract defect, and the on-chain safety argument is **sound** —
`block.timestamp` is genuinely constant within a real transaction, so *that* divergence provably
cannot manifest on-chain. What remains is that the deployed codegen pipeline has no test
coverage, and via_ir is a distinct Yul pipeline with its own historical miscompilation record.

**Corrections carried (so they are not re-derived or mis-stated)**:

- **Prospective, not live.** PhlimboV3 is **not** wired into phStaging — zero references exist in
  that repo. This is a hazard to close *before* the V3 deploy story lands, which is also when it
  is cheapest to close.
- **EIP-170 is genuinely resolved, and is independent of via_ir.** The *optimizer* fixes the size
  problem; the via_ir build fits **better** (14,529 B vs 15,979 B). `via_ir = false` is therefore
  **not load-bearing for EIP-170** and can be revisited freely without reopening the size
  problem. This is the most useful single fact here — it materially cheapens the preferred fix.
- **CI divergence was checked and REFUTED.** `.github/workflows/test.yml` sets
  `FOUNDRY_PROFILE=ci` but no `[profile.ci]` section exists, so it inherits `[profile.default]`;
  `FOUNDRY_PROFILE=ci forge config` returns `via_ir=false`, identical to default. The real
  divergence is with phStaging, not CI. Recorded so it is not re-investigated.
- **Cross-project routing flag, not a scope exclusion.** This affects the phlimbo-ea ↔
  phoenix-phase-2-staging boundary (a sibling submodule). The next phStaging run that wires
  PhlimboV3 should treat this as a **gate**, not a note.

**Recommendation** (best fix — removes the root cause and restores test/deploy parity, and is
cheap precisely because via_ir is not load-bearing for EIP-170): refactor the affected tests off
`vm.warp(block.timestamp + X)` onto an explicit absolute-time accumulator, which is immune to the
frame-caching interaction, then re-enable via_ir so builds match the phStaging deploy pipeline.

```solidity
// Instead of: vm.warp(block.timestamp + X);  // collapses under via_ir frame caching
uint256 t = block.timestamp;
t += X;
vm.warp(t);
```

*Alternative* (keeps the workaround, closes the gap): add a `[profile.viair]` mirroring
phStaging's settings and run the suite under it in CI, excluding only the known warp-loop tests.
*Minimum*: pin the deploy pipeline explicitly and record the divergence as an accepted, documented
risk before the V3 deploy story lands.

> **Tier-3 inherits this gap.** `invariant-results.buildProvenance` independently caveats that
> all its results are evidence about the legacy-codegen build **only**. The entire Tier-3 campaign
> — 500k Foundry + 1.51M Medusa calls — inherits it. No Tier-3 evidence in this run speaks to the
> deployed bytecode.

### [Q-01] Bare `catch { }` discards the revert reason; the sibling migrator preserves it <!-- id: pe11q1 -->

**Location**: [`src/PhlimboV3.sol#L913-L918`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol)

**Description**: The phUSD mint's `catch { }` at `:914` discards the revert reason, so
`PhUSDMintFailed` records **that** the mint failed but not **why**. The sibling contract in the
same repo does this correctly, which is what makes it a defect rather than a preference:
`MigratorV2V3.migrate` uses `catch (bytes memory reason)` (`:204`) and emits the raw ABI-encoded
revert data in `UserMigrationSkipped`, with a docstring explicitly warning the owner they "MUST
read the UserMigrationSkipped events after every pass before trusting it" — precisely because the
reason distinguishes a genuinely bad position from a misconfiguration. The same argument applies
verbatim here: a bank accruing because mint authority was revoked, because a supply cap was hit,
or because the beneficiary is blocklisted are operationally very different situations demanding
different responses, and `PhUSDMintFailed` cannot tell them apart.

**Importance (not severity)**: this QA is **upgraded in importance** by L-01's adjudication and
should be read alongside it. The dissent's adopted contribution is that story-031 turned a loud,
self-healing failure into a silent one on the migrator leg — and **this bare catch is the
mechanism by which it went quiet**. Reason-capture is a **prerequisite** for L-01's mandatory
"restore loudness" requirement. Fixing it is a genuine part of closing L-01 properly, not
cosmetics.

**Time-sensitive**: this is an additive event-field change and would be an **ABI break for
existing indexers** of `PhUSDMintFailed`. **Cheap now** (story-031 is unreleased), expensive
later. The window is open and closing.

**Recommendation**: Mirror the pattern the codebase already contains — this is a consistency fix,
not a new design.

```solidity
} catch (bytes memory reason) {
    unclaimablePhUSDOf[beneficiary] += pendingPhUSDAmount;
    totalUnclaimablePhUSD += pendingPhUSDAmount;
    emit PhUSDMintFailed(beneficiary, pendingPhUSDAmount, reason);
}
```

### [Q-02] `totalUnclaimablePhUSD` is the only record of un-backed mint liability and nothing reads it <!-- id: pe11q2 -->

**Location**: [`src/PhlimboV3.sol#L181`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol) (declaration), written at `:916` and `:648`

**Description**: `totalUnclaimablePhUSD` is the protocol's **only** record of outstanding
un-backed phUSD mint liability. It is written at `:916` and `:648` and exposed via a public
getter, but **no control flow anywhere reads it** — 4 hits total, all writes or the getter,
neither in PhlimboV3 nor in MigratorV2V3 — and there is no phUSD supply cap for it to interact
with (FlaxToken has none; mint is minter-gated with no cap check). Because the banked phUSD is
un-minted, `phUSD.totalSupply()` **understates** the protocol's true outstanding phUSD obligation
by exactly `totalUnclaimablePhUSD`. Any external solvency, backing-ratio, or supply monitor
reading `totalSupply()` will under-count by that amount.

**Impact**: None on-chain today, precisely *because* the counter is not load-bearing — its
inaccuracy propagates nowhere. Surfaced rather than dropped because it is the visible-channel
record of an un-backed mint liability in a system with a documented cross-project unbacked-phUSD
theme (cf. yield-claim-nft `DEDUP-001`).

**Worth noting for L-01**: this is the natural place to **catch L-01 in monitoring**. A stranded
migrator entry inflates `totalUnclaimablePhUSD` permanently, so the figure is simultaneously
**unread** and **corruptible upward**. Wiring a monitor to this getter would make L-01's silent
strand visible to operators — a cheap partial mitigation for a Low that is otherwise invisible.

**Recommendation**: No code change required. Document in `SolvencyDetermination.md` that true
outstanding phUSD is `phUSD.totalSupply() + PhlimboV3.totalUnclaimablePhUSD()` (plus any sibling
banks), and have any external backing monitor read the getter.

### [Q-04] `phUSD` and `rewardToken` are not `immutable`: the un-keyed banks' safety rests on absence-of-setter, not the compiler <!-- id: pe11q4 -->

**Location**: [`src/PhlimboV3.sol#L51`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol) (`IFlax public phUSD`), `#L54` (`IERC20 public rewardToken`); assigned at `:243-244`; NatSpec at `:168-171`

**Description**: The NatSpec at `:168-171` justifies the un-token-keyed phUSD bank with "phUSD is
fixed at construction and never rotates". That is true today — both are constructor-only with
zero-address validation and no setter exists (verified by grep; the `immutable` keyword appears
nowhere in the file) — but they are **plain storage, not `immutable`**. The safety of both
un-keyed banks (`unclaimablePhUSDOf`, `unclaimableStableOf`) rests on the continued *absence of a
setter* rather than on a compiler guarantee. A future setter would silently strand every banked
balance under the old asset. The design is internally consistent: `promoToken` **does** rotate
(`:403` / `:559`), which is exactly why `unclaimablePromoOf` is token-keyed.

**Recommendation**: Declare `phUSD` and `rewardToken` `immutable` so the banks' keying invariant
is enforced by the compiler rather than by convention. Zero runtime cost; also saves an SLOAD per
claim. Independently corroborated by 4naly3er `GAS-10` ("State variables only set in the
constructor should be declared `immutable`"), which flags `PhlimboV3.sol:244`.

```solidity
IFlax public immutable phUSD;
IERC20 public immutable rewardToken;
```

### [Q-05] `RewardsClaimed` fires even when the value was banked rather than paid <!-- id: pe11q5 -->

**Location**: [`src/PhlimboV3.sol#L939`](../../../../lib/phlimbo-ea/src/PhlimboV3.sol)

**Description**: `RewardsClaimed(user, pendingPhUSDAmount, pendingRewardAmount)` is emitted
whenever either amount is non-zero — **including when that value was banked rather than
delivered**:

```solidity
if (pendingPhUSDAmount > 0 || pendingRewardAmount > 0) {
    emit RewardsClaimed(user, pendingPhUSDAmount, pendingRewardAmount);
}
```

An indexer therefore sees **both** `RewardsClaimed` **and** `PhUSDMintFailed` /
`StableClaimFailed` for the same value, and may double-count distributed rewards. Pre-existing for
the stable leg; story-031 extends the ambiguity to phUSD.

**Impact**: Off-chain double-count only. **On-chain accounting is correct** — the event is
indexed by `user` (whose accrued rewards were drained), matching V1 semantics, and the banked
amounts are tracked separately.

**Recommendation**: Either emit `RewardsClaimed` with the amounts actually **delivered**, or
document that `RewardsClaimed` means "settled (paid **or** banked)" and that reconciling it
requires netting off the corresponding `*Failed` events.
