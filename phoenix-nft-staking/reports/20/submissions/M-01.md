## Finding description and impact

### Summary

Step 10 of `batchMint` refunds `paymentToken.balanceOf(address(this))` — the contract's **entire**
balance — to `msg.sender`, rather than the caller's own unspent budget. There is no `qualifies` check
and no `nudgeSize` gate. Any `count == 1` caller with empty reward arrays therefore takes whatever
payment-token balance has accumulated on the contract.

`src/BatchNFTMinter.sol:380-387`:

```solidity
// --- 10. Dust sweep of residual payment token back to msg.sender. ---
uint256 remaining = paymentToken.balanceOf(address(this));           // :381
if (remaining / DUST_THRESHOLD != 0) {
    paymentToken.safeTransfer(msg.sender, remaining);                // :383
    totalPaid = paymentAmount > remaining ? paymentAmount - remaining : 0;
} else {
    totalPaid = paymentAmount;
}
```

The hazard materialises whenever a dispatcher returns its own `primeToken` to the batch minter, so that
the accumulating incentive pot and the swept payment token are the **same asset**. In that
configuration the pot can leave **only** through this door: the §4.1 reward-token guard at
`src/BatchNFTMinter.sol:426-428` (`BatchMint__RewardTokenIsPaymentToken`) makes that same asset
un-listable as a reward token, so the legitimate nudge claimer cannot take it, while the un-gated sweep
remains open to anyone. `batchMint` then returns `totalPaid == 0`, so the transaction reads as a free
batch.

### ⚠ Provenance — this is pre-existing code, not newly introduced (D-18)

**State this explicitly wherever the finding is repeated.** The step-10 sweep is **byte-identical since
`ab07199 [story-013]` (2026-05-29)**. It **predates story-022** and is unchanged by it. It is neither a
regression (it was never marked fixed) nor a carryover (it was never filed); all 22 ledger entries were
checked and none covers it, so it is filed as a new finding of a pre-existing defect.

What story-022 changed is the §4.1 guard. That guard upgrades the leak from *"dust escapes"* to
*"the pot can **only** escape this way"* — it blocks the legitimate claimer while leaving the sweep
open. **The new code did not create the sink; it closed the honest exit next to it.**

### Why Medium, not High and not Low

**Not High.** No funds are exposed right now, and none were ever lost through this path. The High
branch of the criterion — "a non-trivial balance is sitting there right now" — is refuted by direct
on-chain reads.

**Not Low.** The un-gated sweep at `:381-383` is unchanged in code; only the configuration that fed it
was corrected. `0x81896F48…` is **deliberately retained and still live**, still `dispatcherIndex == 7`,
still with USDC as its swept payment token. A single `setBatchMinter` call — or any USDC airdrop to
that address — re-arms it instantly, and the sweep is permissionless, cost-free and `count == 1`
callable. This is a textbook C4 Medium: value leak with stated assumptions and external requirements.

Compounding the exposure if it is re-armed: `pauser == address(0)` and `paused == false` on **both**
live instances, so `pause()` is unavailable, and the contract's own NatSpec
(`src/BatchNFTMinter.sol:190-205`) describes `rescueERC20` as *"a race the owner will usually lose"*
with *"pause first, then rescue"* as the only dependable sequence. With no pauser, that sequence is
inexecutable — see L-01 (`919b71fd…`), the run's only live-mainnet operator action item.

### Counter-argument, surfaced for the triager and not pressed

`src/BatchNFTMinter.sol:63-68` documents the sweep as **intended**:

> *"Any payment-token balance left after the loop and after the optional nudge transfers — unused
> budget, dispatcher-side dust, or a third-party donation — is swept back to `msg.sender`… A griefer
> who pre-deposits payment-token to this contract simply donates to the next caller."*

That is a legitimate Medium→Low argument and neither D-22 nor the classification weighed it
explicitly, so it is recorded here. The answer is that the NatSpec anticipates an *incidental*
donation, not a continuous dispatcher-fed pot that the §4.1 guard makes claimable **only** through the
sweep. The finding is filed at Medium; the strongest counter is visible to whoever triages it.

## Recommended mitigation steps

### 1. Bound the refund to the caller's own unspent budget

The refund should return what this caller did not spend, not the contract's whole balance:

```diff
-        uint256 remaining = paymentToken.balanceOf(address(this));
+        // Refund only this caller's unspent budget, never the contract's accumulated balance.
+        uint256 balance = paymentToken.balanceOf(address(this));
+        uint256 spent = paymentAmount - unspentBudget;   // track spend across the mint loop
+        uint256 remaining = unspentBudget < balance ? unspentBudget : balance;
```

Track the caller's spend explicitly across the mint loop (accumulating the per-mint charge) instead of
inferring it from a post-hoc balance read. Any residue beyond that belongs to the contract and must not
be reachable by an un-gated path.

### 2. Do not treat the config repoint as the fix

`FixRatchetBatchMinterSink.s.sol` removed the *configuration* that fed the sink. The code property is
unchanged, and `0x81896F48…` is intentionally retained as the UI entrypoint with USDC still its swept
payment token. Until `:381-383` is bounded, any future `setBatchMinter` back to that instance, or any
USDC transfer to it, re-arms the leak with no code change required.

### 3. Restore the break-glass (joint with L-01, `919b71fd…`)

Set a `pauser` on **both** live batch-minter instances (`0x81896F48…` and `0x86866e01…`). Without it,
the "pause first, then rescue" sequence that the contract's own NatSpec identifies as the only
dependable recovery is unavailable, and `rescueERC20` alone is a mempool race the owner is documented
to lose.

### 4. Related but distinct — do not collapse

This finding shares a target (the nudge pot) with M-02 (`a62fe01a…`, duplicate `rewardTokens`) and with
DEDUP-20-005, but each is a **different route with a different remedy**. Fixing one does not close the
others; they must be tracked and verified separately.

### 5. Spec correction (F-20-05)

`docs/multi-token-nudge.md` §4.1's threat-model claim is false as written — it presumes the guard makes
the pot safe, when the guard is precisely what makes the sweep the pot's only exit. Fix the prose
alongside the code so the next reader does not re-derive the same false assurance.
