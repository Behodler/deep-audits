## Finding description and impact

### Summary

`_snapshotRewards` writes the same pre-loop balance `B` into **every** duplicate slot of the
caller-supplied `rewardTokens` array, and `_payRewards` transfers `snapshot[i]` once per array element
with **no cumulative per-token cap**. The mint loop in between raises the live balance by the batch's
own donation `D`. Consequently `k` transfers of `B` all succeed whenever `k·B <= B + D`, and the caller
is paid `k` times out of a pot that was counted once.

Snapshot site — `src/BatchNFTMinter.sol:429, :434`:

```solidity
uint256 available = qualifies ? IERC20(rewardToken).balanceOf(address(this)) : 0;   // :429
uint256 minReward = minRewards[i];
if (available < minReward) {
    revert BatchMint__RewardBelowMinimum(rewardToken, minReward, available);
}
snapshot[i] = available;                                                            // :434
```

Payout site — `src/BatchNFTMinter.sol:452-461`:

```solidity
function _payRewards(address recipient, address[] calldata rewardTokens, uint256[] memory snapshot) private {
    uint256 tokenCount = snapshot.length;
    for (uint256 i; i < tokenCount; ++i) {
        uint256 amount = snapshot[i];
        if (amount == 0) continue;
        address rewardToken = rewardTokens[i];
        IERC20(rewardToken).safeTransfer(recipient, amount);   // :458 — no cumulative cap
        emit NudgePaid(recipient, rewardToken, amount);
    }
}
```

### The specification contradicts itself, and §4.5 is the false half

`docs/multi-token-nudge.md` §4.5 ("Malformed arrays are the caller's problem") justifies the absence of
a dedupe pass:

> *"**Duplicates** (`[USDC, USDC]`): both entries snapshot the same balance. The first transfer drains
> it; the second either reverts on insufficient balance or transfers into a now-empty pot. Either way
> it **fails closed and harms only the caller**. No dedupe pass — that is O(n²) gas charged to every
> honest caller to protect one careless one."*

That reasoning is only valid if the balance does not grow between snapshot and payout. §4.2 of the
**same normative document** states that it always does:

> *"The dispatcher donates reward token into this contract **on every mint**… Reading balances *before*
> the loop means the batcher is paid only the prior accumulated pot; the donations generated by their
> own batch stay behind to seed the next claimant. This is the 'donate forward' mechanic, and it is the
> only thing preventing a caller from funding their own reward within a single transaction."*

§4.5's fail-closed claim is therefore false **under §4.2's own donation premise**. The `D` that §4.2
says is always deposited is exactly the headroom that lets the duplicate's second transfer succeed. A
contradiction inside one normative document is a story-unsafe condition (filed as F-20-01), and Law 1
governs: the exploitable reading wins over the reassuring one.

This is production-live under the pinned configuration: `DISPATCHER_INDEX = 4`, `BalancerPoolerV2`,
`primeToken() == USDS`, forwarding a **USDC** cut to the batcher on every dispatch — so USDC is
simultaneously a legal reward token and a per-mint donation.

### Impact

Protocol-directed incentive funds (the StableYieldAccumulator `nudgeSplit` drip plus the
`BalancerPoolerV2` per-mint cut) leak back to the batcher that generated them, and the donate-forward
mechanic that §4.2 calls load-bearing is defeated: a batcher recaptures its own batch's donation and
can drive the next claimant's seed to zero.

**No user principal is at risk.** Nothing here touches deposits, staked positions or third-party
balances.

### ⚠ The bound that keeps this at Medium (ruling R-7) — use this one, not the weak one

**Do not argue that "the currently observed mainnet shape still fails closed."** That bound is weak and
must not appear in the writeup as the reason this is not High. The bite condition is `k·B <= B + D`,
and `D` scales with `count` — **which the attacker chooses**. The measured bite point (`count = 400`)
sits well inside the ~426-users-per-30M-gas-block ceiling measured elsewhere in this run. A
precondition the attacker can create for themselves does not cap severity, and the first reviewer to
notice that `count` is caller-supplied will read the Medium as under-argued.

**The sound bound is donate-forward defeat, not third-party theft.** An honest single claim already
takes `B` by design. The **incremental** extraction from the duplicate path is therefore capped at `D`
— the caller recapturing their **own** batch's donation. That is a genuine leak of protocol-directed
incentive funds and the defeat of a spec-load-bearing mechanic, which is Medium; it is not theft of
anyone's principal, which is what High would require.

## Recommended mitigation steps

### ⚠ FIX TRAP (D-16) — read before writing the patch

**The obvious remedy is wrong.** Re-reading `balanceOf` at payout time is **exactly** the §4.2 refactor
the specification warns against, at both the snapshot site and the payout site:

> *"This is a trap for future refactors: reading the balance immediately before the transfer looks
> obviously cleaner and is silently wrong."*

A post-loop read would refund every batch's own donations straight back to the batcher, collapsing the
incentive to a no-op round-trip — i.e. it would make the leak total rather than bounded. Do not do it.

### The correct fix

Clamp each transfer to what the contract actually holds and to what has already been paid in this pass,
or dedupe the array:

```diff
 function _payRewards(address recipient, address[] calldata rewardTokens, uint256[] memory snapshot) private {
     uint256 tokenCount = snapshot.length;
     for (uint256 i; i < tokenCount; ++i) {
         uint256 amount = snapshot[i];
         if (amount == 0) continue;
         address rewardToken = rewardTokens[i];
-        IERC20(rewardToken).safeTransfer(recipient, amount);
-        emit NudgePaid(recipient, rewardToken, amount);
+        // Clamp: never pay more than the pre-loop snapshot, and never more than
+        // the contract still holds. This does NOT re-read balanceOf as the payout
+        // basis (§4.2) — the snapshot remains the entitlement; the live balance is
+        // only a ceiling.
+        uint256 held = IERC20(rewardToken).balanceOf(address(this));
+        if (amount > held) amount = held;
+        if (amount == 0) continue;
+        IERC20(rewardToken).safeTransfer(recipient, amount);
+        emit NudgePaid(recipient, rewardToken, amount);
     }
 }
```

The clamp must be `min(snapshot[i], balanceOf(this) - paidThisPass)`, tracking `paidThisPass` per token
so that a duplicate's second entry cannot consume donation headroom. Deduping the array up front is the
alternative; §4.5 rules it out on O(n²) gas grounds, so if that reasoning is retained, the clamp is the
required path — and §4.5's fail-closed justification must be corrected either way, since it is false as
written.

### Evaluate jointly with the fee-on-transfer gap

`invariant_fotFloor` shows `delivered=95e18` against a `declared floor=100e18`, 11 census hits). **The

### Close the witness gap at the same time

runs with donations `D == 0` and **passes vacuously** (Q-01, `cabd4a3d…`). Fix the witness in the same
change: if only the code is fixed, the coverage regression disappears the moment the fix lands and
nothing pins the property afterwards.
