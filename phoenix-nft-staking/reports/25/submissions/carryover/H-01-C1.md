## Finding description and impact

### Summary

`NFTStakerDepletion.depositFor` is `onlyMigrator`, so `msg.sender` is always an orchestrator contract
and never the user being migrated. It nevertheless settles that user's accrued phUSD through
`_safePay`, which forwards to `_safePayTo(msg.sender, …)`. The user's matured reward is therefore
transferred to the migrator, while `Claimed(user, pending)` is emitted anyway — so off-chain
reconciliation reports the user as paid.

`src/NFTStakerDepletion.sol:748-760`:

```solidity
function depositFor(address user, uint256 amount) external override nonReentrant onlyMigrator {
    require(amount > 0, "NFTStaker: zero deposit");
    require(poolState == PoolState.Active, "NFTStaker: not active");
    _syncBudget();
    UserInfo storage info = users[user];
    if (info.amount > 0) {                                                    // :753
        uint256 pending = (info.amount * accRewardPerShare) / ACC_PRECISION - info.rewardDebt;
        if (pending > 0) {
            pending = _safePay(pending);                                      // :756  <-- pays msg.sender
            if (pending > 0) emit Claimed(user, pending);
        }
    }
    ...
}
```

This is a missed call site, not a missing primitive: the same contract already defines and correctly
uses `_safePayTo` in `_exitPosition` (`src/NFTStakerDepletion.sol:733`).

### Provenance — a known, named bug fixed in a clone and not back-ported

The project maintains four near-identical staker copies. story-021 added the fourth
(`src/NFTStakerPriceScaledMigrateReady.sol`) and fixed this exact defect **only there**.

- The story-021 commit body names the bug itself:

  > *"depositFor settles existing pending via `_safePayTo(user, ...)` rather than `_safePay(...)`,
  > **which would pay the migrator**"*

  and in the same message declares the older copies untouched:

  > *"`NFTStaker.sol`, `NFTStakerPriceScaled.sol`, **`NFTStakerDepletion.sol`**, both migrators,
  > `INFTStakerMigratable` and all existing tests are untouched"*

- The NatSpec ported onto the fixed copy calls the `_safePay` form categorically wrong
  (`src/NFTStakerPriceScaledMigrateReady.sol:876-877`):

  > *"…partial `InPlaceNFTStakerMigrator` round-trip, or migrating into a staker the user is already
  > in), but **wrong in every case**."*

- The fixed line in the new copy is `src/NFTStakerPriceScaledMigrateReady.sol:887`
  (`pending = _safePayTo(user, pending);`), against `src/NFTStakerDepletion.sol:756`
  (`pending = _safePay(pending);`).

The standing fork-drift watch note (WATCH-17) therefore moved from precaution to a realised defect:
the anticipated failure mode — a fix authored in a clone and never back-ported — occurred inside the
very commit that created the clone. Three independent workstreams converged on it (fork-parity
DRIFT-01, story-faithfulness F-20-03, code-scan CODE-001); the convergence is recorded as
corroboration, not as three findings.

### Why this is High

The C4 High criterion is *assets can be stolen, **lost**, or compromised*. What is lost here is
**matured, settled, owed** yield — not in-flight accrual — and on one of the two documented
orchestrators the loss is **terminal**:

| Orchestrator | Recovery primitive | Outcome |
|---|---|---|
| `InPlaceNFTStakerMigrator` | `rescueERC20` (`src/InPlaceNFTStakerMigrator.sol:268`) | Recoverable by owner, via manual hand-distribution |
| `NFTStakerMigrator` | **none** | **Permanently stranded** |

`src/NFTStakerMigrator.sol` declares exactly two functions — `initiateMigration()` (`:70`) and
`migrate(address[])` (`:81`). There is no `rescueERC20`, no `rescueERC1155`, no `receive`, and no
`fallback`. phUSD delivered to it cannot be moved by anyone, including the owner.

That same contract's own NatSpec names the buggy contract as its documented target
(`src/NFTStakerMigrator.sol:9-11`):

> *"Orchestrates a zero-user-action migration between two **`NFTStakerDepletion`** instances."*

No attacker is required. This is the ordinary, intended operational path, invoked by the owner:
`migrate(users)` → `NFTStakerDepletion.depositFor(user, …)` → misroute.

### Honest bounds on impact

These bound the finding and must be read alongside it:

1. **Loss population is narrowed by the `info.amount > 0` guard at `:753`.** Only a user who already
   holds a **non-zero position on the target staker** loses anything. On a migration into a
   freshly-deployed target, every user has `pending == 0` and nothing is misrouted. The realistic
   population is users staked in *both* pools — which permissionless `stake()` on the target makes
   ordinary rather than exotic, but it is not "every migrated user".
2. **82,191.78 phUSD is a lab magnitude.** It is the figure produced by the PoC fixture, **not** a
   predicted mainnet loss, and must not be reported as one.
3. **Neither migrator is deployed today**, so present on-chain exposure is zero. That bounds *present
   exposure*; it is a deployment-status fact, not a severity bound. Discounting for non-deployment
   would make every pre-deployment self-audit finding Low, which inverts the point of auditing before
   deployment.
4. **Protocol solvency is not broken.** The protocol stays solvent while individual users are made
   whole-less; solvency is not the asset at issue here.

If the operator confirms that `NFTStakerMigrator` will never be deployed and that every migration will
run through `InPlaceNFTStakerMigrator` (which has `rescueERC20`), the loss becomes
recoverable-with-manual-effort and Medium is the honest label. That confirmation has not been given,
and `NFTStakerMigrator` is live in the repo and in scope. **If a human does downgrade on that basis,
L-02 (`cb1b5279…`, "NFTStakerMigrator has no rescue function of any kind") becomes the sole carrier of
the permanence fact and must be re-weighed at that time rather than left at Low by inertia.**

## Recommended mitigation steps

### 1. Fix the call site

The primitive already exists and is already used correctly at `src/NFTStakerDepletion.sol:733`. The fix
is one call site:

```diff
--- a/src/NFTStakerDepletion.sol
+++ b/src/NFTStakerDepletion.sol
@@ -753,7 +753,7 @@ function depositFor(address user, uint256 amount) external override nonReentrant
         if (info.amount > 0) {
             uint256 pending = (info.amount * accRewardPerShare) / ACC_PRECISION - info.rewardDebt;
             if (pending > 0) {
-                pending = _safePay(pending);
+                pending = _safePayTo(user, pending);
                 if (pending > 0) emit Claimed(user, pending);
             }
         }
```

### 2. Sweep all four copies before closing (WATCH-17, now four-way)

The defect exists because a fix landed in one clone only. Verify the `depositFor` settlement call site
in **all four** staker copies — `NFTStaker.sol`, `NFTStakerPriceScaled.sol`, `NFTStakerDepletion.sol`,
`NFTStakerPriceScaledMigrateReady.sol` — before marking this fixed, and diff the four files as part of
the fix review rather than after it.

### 3. ⚠ TRAP-6 — do not stop at `_safePay`

**Fixing the call site alone leaves the next misroute equally permanent.** The reason this finding is
High rather than Medium is not the misroute; it is that `NFTStakerMigrator` has no way to give value
back. Any future accounting error, hostile-token interaction, or ERC-1155/ERC-20 delivered to that
address by any route is unrecoverable for the same reason.

Add a rescue primitive to `NFTStakerMigrator` alongside the call-site fix — an owner-only
`rescueERC20`/`rescueERC1155` mirroring `InPlaceNFTStakerMigrator:268` — so that the permanence
property is removed, not merely the one known path into it. Treat this as part of the same fix, not as
a separate hardening item; it should be evaluated jointly with L-02 (`cb1b5279…`) and Q-02
(`d0ed2cf4…`).
