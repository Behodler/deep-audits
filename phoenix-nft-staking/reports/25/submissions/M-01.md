# [M-01] Payment-token nudge pot is payable on a value-blind, count-only gate — and the qualifying cost is recycled in full, metered

## Severity

**Medium.**

### The Medium rests on ONE stale, unverified negative — read this before triaging

This finding is Medium rather than High for **exactly one reason**: a "zero present on-chain exposure" reading recorded in the ledger. That reading has three limitations, all of which must be stated plainly:

1. **It was taken at run-20**, mainnet block **25572875** — **five runs before story-029**, the very change this finding is about. M-01's own re-file argument (below) is that arithmetic computed before story-029 is not a statement about the code at `5015f1b`. **The identical logic applies to the exposure reading itself.** It is not evidence about `5015f1b`; it is evidence about a deployment snapshot taken against different code.
2. **It covered ONE contract instance** — `RatchetBatchNFTMinter` — not "every live instance". No claim is made here, and none should be inferred, about any other live `BatchNFTMinterMultiToken`.
3. It is an **unverified negative**: a past observation of deployment wiring, never re-confirmed at or after `5015f1b`.

**State plainly: if the collision is live anywhere, this is a High that shipped labelled Medium.**

### The settling check

It must be run against **every** live `BatchNFTMinterMultiToken` instance, with addresses resolved **from chain, not from deploy records** — this project's deploy records have previously shown `0x0` "not deployed" for live, funded instances.

For each instance:

1. `dispatcher = INFTMinterV2(batch.nftMinter()).configs(batch.dispatcherIndex()).dispatcher` → `pt = ITokenDispatcherV2(dispatcher).primeToken()` → **`batch.isNudgeToken(pt)`**. If `true`, the payment token is in the pot set.
2. **`IERC20(pt).balanceOf(address(batch))`**. If this exceeds `nudgeSize * price`, the claim below is profitable *right now*.

## Impact

### Leg 1 — the payout is released by a count, not by a value

Story-029 **deleted** the runtime line `if (rewardToken == paymentToken) continue;` from `_snapshotRewards`. Every whitelisted token — now including the token derived from the dispatcher via `ITokenDispatcherV2(dispatcher).primeToken()` — is snapshotted before the payment pull, floor-checked against `minRewards`, and paid **in full** at `:790` to a **caller-chosen `recipient`**.

The gate that releases it was not touched, and it is value-blind:

```solidity
// src/BatchNFTMinterMultiToken.sol:507-511
bool qualifies;
{
    uint256 _nudgeSize = nudgeSize;
    qualifies = _nudgeSize != 0 && count >= _nudgeSize;   // :510 — a COUNT vs a COUNT
}
```

```solidity
// src/BatchNFTMinterMultiToken.sol:749-765 (_snapshotRewards) — no payment-token exclusion remains
for (uint256 i; i < tokenCount; ++i) {
    address rewardToken = _nudgeTokens[i];
    uint256 available = qualifies ? IERC20(rewardToken).balanceOf(address(this)) : 0;
    ...
    snapshot[i] = available;
}
```

`qualifies` reads `count` and `nudgeSize` and nothing else. It never reads `paymentAmount`, `price`, `budget`, or `snapshot[i]`. **No expression anywhere in the file relates the payout to the payment.** A count is compared to a count, and a value is paid out.

The gate itself is not the change — story-029 **widened what the gate can release**, by adding one more pool (the payment token) to the set the count-only comparison drains.

Consequence, in the project's own fixture terms (`test/PoC_PaymentTokenCollision.t.sol`: USDC 6dp, `price = 10.000000`, `nudgeSize = 5`, `growthBasisPoints = 0`):

| Term | Pre-029 (the arithmetic at triage time) | Post-029 (`5015f1b`) |
|---|---|---|
| pot set entering Σ | whitelist **minus** the payment token | whitelist, **no exclusion** |
| Σ(pots) at fixture config | `0` USDC | **200.000000 USDC** |
| `C = nudgeSize × price` | `50.000000 USDC` | `50.000000 USDC` (unchanged) |
| **Σ / C** | `0` — premise **held** | **4.00× — premise INVERTED** |

Whenever the standing pot exceeds `C` plus gas, any unprivileged caller converts `C` into the whole pot in one atomic transaction and keeps the NFTs. Break-even is `P > C + gas ≈ 71.60 USDC` at fixture price — **8 ratchet mints** — or **6 mints** at the mainnet-observed `price = 70.000000`.

The loss is bounded by the pot balance, not by the caller's payment, and it is not shared: the first caller to observe `P > C + gas` takes all of it.

### Leg 2 — the qualifying cost is recycled in full, metered

*(This leg was filed separately as run-25 M-02 and is merged here. It is not an independent finding: it has no standalone impact and is fully closed by Mitigation 1 below. It matters because it turns Leg 1 from one-shot into repeatable, and because it independently falsifies the premise KI #15 rests on.)*

`batchMint` pays each mint through the minter, which forwards the price to the index's dispatcher:

```solidity
// src/BatchNFTMinterMultiToken.sol:621-627
for (uint256 i; i < count; ++i) {
    (, uint256 price,,) = INFTMinterV2(address(nftMinter)).configs(_dispatcherIndex);
    if (price > budget) revert BatchMint__PaymentBudgetExhausted(i, price, budget);
    paymentToken.forceApprove(address(nftMinter), price);
    budget -= price;
    nftMinter.mint(_dispatcherIndex, recipient);            // :626
}
```

At `d4cc563`, `NudgeRatchet._dispatch` **no longer performs a leaf `safeTransfer(batchMinter, bal)`** — that line is deleted, with no fallback branch. It forwards through the streamer:

```solidity
// yield-claim-nft/src/dispatchers/NudgeRatchet.sol:156-161 @ d4cc563
if (bal > 0) {
    address streamer = nudgeStreamer;
    require(streamer != address(0), "NudgeRatchet: nudgeStreamer unset");
    IERC20(_token).forceApprove(streamer, bal);
    INudgeStreamer(streamer).collectNudge(batchMinter, _token, bal);
}
```

The corrected end-to-end flow, when `NudgeRatchet.batchMinter` is this batch minter and `dispatcherIndex` points at that ratchet:

```
batchMint :530  INudgeStreamer(streamer).pullPendingStream(token)   ← harvest into the pot
        │        (loops the whole whitelist, inside batchMint's nonReentrant guard)
        ▼
batchMint :535  snapshot = _snapshotRewards(minRewards, qualifies)  ← streamed value IS counted
        ▼
batchMint :626  nftMinter.mint(...)
        ▼
NFTMinterV2 :183  safeTransferFrom(msg.sender, config.dispatcher, price)
        ▼
NudgeRatchet :156-161  forceApprove(streamer, bal); collectNudge(batchMinter, _token, bal)
        ▼
NudgeStreamer :137-156  _settle at the OLD rate → safeTransferFrom(ratchet, streamer, bal)
                        → s.buffer += bal
                        → s.rewardPerSecond = (s.buffer * PRECISION) / s.duration   ← WINDOW RESET
        ▼
delivered LINEARLY to the batch minter over `duration` (D), harvested by the next batch's :530 pull
```

**The loop is not broken — it is METERED.** Verified at source, `NudgeStreamer` is **value-conserving**:

- `_settle` (`:182-190`) has **no fee, burn, skim or retention branch** — every settled unit is transferred to the recipient.
- `_accrued` (`:195-200`) caps at `buffer`. The cap prevents over-transfer; it never withholds.
- Floor-division dust stays in the buffer and streams out later.
- `registerStream` settles at the **old** rate before resetting, so no accrual is stranded.

**Total delivered = total deposited.** And `batchMint` pulls `pullPendingStream` over the whole whitelist at `:530`, immediately **before** `_snapshotRewards` at `:535`, so streamed value lands in the pot and is counted in the same call that pays it out.

**Steady state is numerically unchanged from the (incorrect) instantaneous model** — conservation guarantees a lossless loop has the same fixed point:

- equilibrium buffer `B* = C·D / T` (T = inter-batch interval)
- per-cycle recovery `A = C`
- net cash `A − C = 0`, plus `nudgeSize` NFTs, minus gas

**What metering DOES change — three costs the instantaneous model failed to charge the attacker:**

1. **Recovery is linear over `D`, not next-block.** Recovery is full only at `t = D`. Every "the second claim is a pure `C → C` round-trip" and "next block" claim in the original text is **withdrawn**.
2. **One full `C` is permanently escrowed in flight and never recovered by the searcher.** At mainnet config that is **350 USDC** of working capital locked in the streamer buffer for the life of the strategy. On exit it is not returned — it is **donated to whoever harvests next**.
3. **The exploit becomes an interruptible, multi-day race.** Any competing qualifying batch that lands first takes the pot. The searcher cannot close the loop atomically.

**Amortised NFT acquisition cost** (mainnet config: `price = 70`, `nudgeSize = 5`, `C = 350`, gas ≈ `21.60`; total outlay = `C + n·gas`, NFTs = `5n`):

| batches `n` | cost per NFT | vs. `price = 70` face |
|---|---|---|
| 1 | **74.32** | a **loss** |
| 10 | **11.32** | 84% discount |
| 50 | **5.72** | 92% discount |
| n → ∞ | **4.32** | 94% discount |

The single-shot attack is unprofitable. The finding is that a patient operator acquires the NFTs at up to a 94% discount while the protocol retains nothing but gas.

### Arming conditions — FOUR, all required

1. The payment token is whitelisted as a nudge token.
2. `dispatcherIndex` resolves to a dispatcher whose `primeToken()` is that token.
3. `NudgeRatchet.batchMinter` is this batch minter.
4. **The full ops ordering is complete**: `batchMinter.setNudgeTokenWhitelist(token, true)` → `nudgeStreamer.registerStream(batchMinter, token, duration)` → `ratchet.setNudgeStreamer(nudgeStreamer)`. This is a **hard** precondition, not a soft one: `nudgeStreamer == address(0)` reverts `"NudgeRatchet: nudgeStreamer unset"`, an unregistered pair reverts `NudgeStreamer__NotRegistered()`, and a non-whitelisted token reverts `NudgeStreamer__NotWhitelisted()` — each of which reverts the **entire `batchMint`**, because the dispatch happens inside the mint loop. An incompletely-wired deployment is not exploitable; it is bricked.

**All four legs were read at source. None was verified against a live deployment.** That is why the settling check above is given rather than asserted.

### `duration` (D) is an explicit severity parameter

Every quantity in Leg 2 scales with the streamer's registered `duration`: the escrowed capital is `C`, but the *time* to recover it, the width of the race window, and the number of batches needed to amortise are all set by `D`. **This run did not pin the deployed `D`.** The deployed value should be stated on the ledger entry; a long `D` materially weakens this leg, a short one materially strengthens it.

## Recommended Mitigation

Two independent controls. **Both should be adopted** — they act at different times and neither subsumes the other. Mitigation 1 is the durable fix; Mitigation 2 is the cheaper deploy-time guard that catches the misconfiguration before any value is at risk.

### 1. Make the payout value-aware (durable; closes both legs)

The gate and the payment must appear in one expression. The quantity needed is already computed at `:664` — the payment actually charged for this batch, `paymentAmount - refund`:

```solidity
// step 10 — cap the aggregate nudge payout against what the caller actually paid.
uint256 charged = totalPaid;                 // already computed at :664
uint256 budgetForNudge = charged;            // or `charged * capBps / 10_000`
for (uint256 i; i < tokenCount; ++i) {
    uint256 amount = snapshot[i];
    if (amount == 0) continue;
    uint256 valued = _valueInPaymentToken(_nudgeTokens[i], amount);
    if (valued > budgetForNudge) { amount = _scaleDown(amount, budgetForNudge, valued); }
    budgetForNudge -= _min(valued, budgetForNudge);
    ...
}
```

For the single-token, same-denomination case that this finding concerns, the minimal form needs no pricing at all: **cap the payment-token leg of the payout at `totalPaid`** (or a fraction of it). That turns the docs' "by construction" sentence into an actual construction. It bounds the **exit**, so it works regardless of how or when the payment returns — closing Leg 2 as a side effect.

A stricter variant: **make the gate a value gate** — require the aggregate snapshot value to be below the charged payment, and revert or scale down otherwise.

### 2. Reject a dispatcher that forms a payment loop, at configuration time (PRESERVED FROM M-02 — do not drop)

This is a **distinct and cheaper control** than Mitigation 1: it is a one-time, deploy-time check that converts the footgun into a revert at the moment an owner would arm it, which is the only moment an owner can act on it. Add to `setDispatcherIndex`:

```solidity
(address dispatcher,,,) = INFTMinterV2(address(nftMinter)).configs(newIndex);
address pt = ITokenDispatcherV2(dispatcher).primeToken();
if (isNudgeToken(pt) && _forwardsTo(dispatcher, address(this))) {
    revert BatchMint__DispatcherFormsPaymentLoop(newIndex);
}
```

`NudgeRatchet` exposes `batchMinter()`, so `_forwardsTo` is a one-call check. **Note the `d4cc563` correction:** the forward is now indirect (ratchet → streamer → batch minter), so `_forwardsTo` must follow the ratchet's declared `batchMinter` — which is still the correct target — rather than looking for a direct transfer.

### 3. Take a haircut (supplement only)

Retain a fixed fraction of each mint price at the protocol rather than forwarding the full balance onward, so the round trip is strictly lossy for the searcher. This weakens rather than removes the loop and should supplement, not substitute for, 1 and 2.

### 4. If neither code fix is adopted, the safe-config becomes a monitored control

If the payout is deliberately left unbounded, the condition *"keep Σ(pot_i) < nudgeSize × mintPrice"* must become an **enforced, monitored operational control**, not a one-time check. See **M-03**: that condition decays on its own from ordinary traffic, with zero owner actions.
