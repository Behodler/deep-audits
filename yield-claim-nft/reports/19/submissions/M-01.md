## Finding description and impact

### Summary

Stories 046 and 047 routed the nudge donations through `NudgeStreamer` specifically to defeat burst capture: a donation is buffered and released linearly, so no single caller can take a lump in one block. Four of the five donor paths were converted — three by story-046, a fourth by story-047. `NudgeRatchetDelayRelease.release()` was not, and it is the path that moves the largest single amounts.

At `src/dispatchers/NudgeRatchetDelayRelease.sol:108-111` the release is still a direct leaf transfer to the batch-minter:

```solidity
function release(uint256 amount) external onlyReleaser nonReentrant {
    IERC20(_token).safeTransfer(batchMinter, amount);
    emit Released(msg.sender, amount);
}
```

The lump lands on the batch-minter as an immediately claimable balance rather than as streamer buffer.

### Attack path

`release()` is `onlyReleaser`, but that only restricts *who calls it* — it does not conceal it. The transaction is visible in the mempool and its `amount` is in calldata. `BatchNFTMinterMultiToken` snapshots reward balances **before** the mint loop, so the reward a batcher receives is exactly the balance standing at the start of their call.

A searcher therefore:

1. Observes the pending `release(amount)`.
2. Back-runs it in the **same block** with `batchMint(count = nudgeSize, recipient = self, paymentAmount, minRewards = [amount])`.

Setting `minRewards` to the whole lump makes the capture risk-free: either the searcher takes the entire amount, or the call reverts `BatchMint__RewardBelowMinimum` and they pay only gas. No time passes, no warp is needed, and no market condition must hold. The pot is emptied in one transaction: `balanceOf(searcher) == LUMP`, `balanceOf(batchMinter) == 0`.

There is no misconfiguration and no owner error anywhere in this path. It is available on every release, indefinitely.

### Impact

The entire released lump is diverted from the honest batcher population to whichever searcher wins one block race. Measured in the PoC: a **50,000 USDC lump captured 100% in the same block** for a cost of five mint prices; the next honest batcher pays the same five mint costs and receives **0**.

The system-wide anti-burst property that four contracts' NatSpec advertises is not enforced on this donor — the protocol's stated distribution function is defeated on the highest-value path.

### Why Medium and not High

No assets are stolen in the C4 High sense. The captor is a qualifying batcher: they pay the required mint cost and receive value through the intended, sanctioned payout path. There is no accounting break, no unauthorized withdrawal, and no custodied user asset leaves to someone who did not pay for it. What is impaired is the protocol's stated function — a value leak under a stated assumption (a searcher exists and monitors the mempool), which is the C4 Medium definition.

Stated honestly: High is arguable, given 100% capture of a 50,000 USDC lump with no preconditions and honest participants receiving nothing. It is held at Medium because the recipient is a legitimate participant paid through the designed channel — this is mis-distribution of an incentive, not theft. It should be re-weighed to High if the released lump is shown to be **user-attributed** value rather than protocol-discretionary incentive.

This finding is the security framing of the same root cause reported under **F-03-046** in the spec-conformance report; they are two framings of one issue, not two issues. It is distinct from `phoenix-nft-staking` ledger entry `858e9e80` (same MEV class, different contract, different repository).

## Proof of Concept

`reports/yield-claim-nft/19/pocs/run19-Tier3Nudge.patch` — contract `Run19_T4_DelayReleaseBackrun`, 3/3 pass, applies cleanly (`git apply --check`). Real `NudgeStreamer`, real `BatchNFTMinterMultiToken`, real dispatchers; no `vm.warp` anywhere in the capture test — the capture is genuinely same-block.

- `test_T4_searcherBackrunsReleaseAndTakesTheWholeLump` — a 50,000 USDC lump is released; a searcher immediately calls `batchMint(count = 5, minRewards = [50_000e6])` and receives the full 50,000 USDC. `balanceOf(batchMinter) == 0` afterwards.
- `test_T4_honestBatcherIsFrontRunOut` — the next honest batcher pays the same five mint costs and receives **0**.
- `test_T4_contrast_streamedDonorIsNotBurstCapturable` — the **contrast arm**: the same 50,000 USDC routed through the streamer by `NudgeRatchet` yields the same-block back-runner **exactly 0**, with at least `LUMP − 1` still buffered in the streamer. This is direct empirical proof that the anti-burst invariant holds on the streamed donors and fails only on this path.

Stated precisely, because it bears on how much the contrast arm proves: the contrast test itself contains no `vm.warp` and asserts only the same-block outcome (zero captured, lump still buffered). It does **not**, on its own, exclude the possibility that the streamer swallows the value permanently. That the buffered value really does pay out is established by two **other** tests in the same suite, and the claim rests on them:

- `Run19_T1._accumulatePot` (the shared helper) warps a full `STREAM_DURATION` and asserts `pendingStream == 20 × RATCHET_PRICE`, i.e. the entire streamed donation becomes claimable, then flushes it onto the batch-minter.
- `test_T3_tailDrainsFullyAfterDonationsStop` runs 200 hourly donations, then warps one window past the last and asserts `usdc.balanceOf(streamer) == 0` — the buffer drains completely once donations stop.

Together these confirm the contrast arm's zero is a genuine same-block timing property rather than a harness that silently strands value.

## Recommended mitigation steps

Route `release()` through the same streamer the other four donors use, so the lump is buffered and released linearly instead of landing as an immediately claimable balance.

Note this is an **addition, not a rewiring**: unlike `NudgeRatchet`, `Uniboost`, `PromotionUniV2_Eth` and `BalancerPoolerV2`, the contract `NudgeRatchetDelayRelease` has **no `nudgeStreamer` storage field and no `setNudgeStreamer` setter at all** — it never touches the streamer. Both must be added, along with the `INudgeStreamer` import. Mirror the shape already shipped on `NudgeRatchet` (field, setter with a zero-address `require` and an update event) so the ops ordering documented in its NatSpec — whitelist, then `registerStream(batchMinter, _token, duration)`, then `setNudgeStreamer` — applies unchanged:

```solidity
// NEW state + setter (neither exists today):
address public nudgeStreamer;

function setNudgeStreamer(address newStreamer) external onlyOwner {
    require(newStreamer != address(0), "NudgeRatchetDelayRelease: zero nudgeStreamer");
    address old = nudgeStreamer;
    nudgeStreamer = newStreamer;
    emit NudgeStreamerUpdated(old, newStreamer);
}

// MODIFIED release():
function release(uint256 amount) external onlyReleaser nonReentrant {
    address streamer = nudgeStreamer;
    require(streamer != address(0), "NudgeRatchetDelayRelease: nudgeStreamer unset");
    IERC20(_token).forceApprove(streamer, amount);
    INudgeStreamer(streamer).collectNudge(batchMinter, _token, amount);
    emit Released(msg.sender, amount);
}
```

This makes the anti-burst property genuinely system-wide and matches the shape already shipped in `NudgeRatchet._dispatch`. Note that doing so brings this contract under the same mandatory-streamer liveness coupling reported in QA `L-01` (the Medium drafted as `M-02` was withdrawn and folded into it). The owner has accepted that coupling as universal across all donors, so no escape hatch is owed here either — and `NudgeRatchetDelayRelease` already has `rescueERC20` regardless.

If routing through the streamer is not acceptable for this path, a partial mitigation is to cap per-call reward payout as a fraction of the standing balance, or to split releases into many small amounts; both reduce, but do not eliminate, the capturable fraction, and neither restores the advertised invariant.
