## Finding description and impact

### Summary

`NFTMigrator.setInitialized()` validates V1→V2 index mappings only for the V1 indexes that exist at the moment it is called, and it is a one-way operation that permanently sets `initialized = true`. The V1 `NFTMinter` is an independently-owned contract (a distinct trust principal from the migrator owner) and can register a new dispatcher *after* the migrator has been initialized, growing `v1.nextIndex()`. Because `migrate()` iterates over the live `v1.nextIndex()`, any holder of such a late index hits `indexMapping[i] == 0`, causing `migrate()` to burn their V1 balance and then call `v2.mintFor(0, ...)`, which reverts with `"NFTMinterV2: index not registered"`. The entire transaction reverts, rendering migration unavailable for the affected holders.

### Vulnerability details

`setInitialized()` only checks mappings for indexes `1 .. v1.nextIndex()-1` at call time, then irreversibly flips `initialized` ([NFTMigrator.sol#L51-L58](https://github.com/Behodler/yield-claim-nft/blob/master/src/V2/NFTMigrator.sol#L51-L58)):

```solidity
function setInitialized() external onlyOwner {
    uint256 upperBound = v1.nextIndex();
    for (uint256 i = 1; i < upperBound; i++) {
        require(indexMapping[i] != 0, "NFTMigrator: missing mapping");
    }
    initialized = true;
    emit Initialized();
}
```

This validation captures only the index set known at initialization and is never re-evaluated. The V1 `NFTMinter` owner — a separate principal — can subsequently register a new dispatcher, which increments `nextIndex` ([NFTMinter.sol#L120-L128](https://github.com/Behodler/yield-claim-nft/blob/master/src/NFTMinter.sol#L120-L128)). The migrator's `indexMapping[newIndex]` stays at its default `0`.

`migrate()` loops over the *current* `v1.nextIndex()`, so it now visits the late index. For a holder with a non-zero balance there, it burns first and only then reads the (zero) mapping ([NFTMigrator.sol#L62-L76](https://github.com/Behodler/yield-claim-nft/blob/master/src/V2/NFTMigrator.sol#L62-L76)):

```solidity
function migrate() external {
    require(initialized, "NFTMigrator: not initialized");
    uint256 upperBound = v1.nextIndex();
    for (uint256 i = 1; i < upperBound; i++) {
        uint256 balance = IERC1155(address(v1)).balanceOf(msg.sender, i);
        if (balance > 0) {
            v1.burn(msg.sender, i, balance);
            uint256 v2Index = indexMapping[i];          // == 0 for a late index
            for (uint256 j = 0; j < balance; j++) {
                v2.mintFor(v2Index, msg.sender);        // mintFor(0, ...)
            }
            emit Migrated(msg.sender, i, balance, v2Index);
        }
    }
}
```

The call `v2.mintFor(0, msg.sender)` reverts because V2 dispatcher indexes start at `1`, so `configs[0].dispatcher == address(0)` ([NFTMinterV2.sol#L206-L214](https://github.com/Behodler/yield-claim-nft/blob/master/src/V2/NFTMinterV2.sol#L206-L214)):

```solidity
function mintFor(uint256 index, address recipient) external {
    require(authorizedMinters[msg.sender], "NFTMinterV2: caller is not authorized minter");
    require(configs[index].dispatcher != address(0), "NFTMinterV2: index not registered");
    ...
}
```

Since the revert unwinds the whole transaction, the preceding `burn` is rolled back — no assets are lost — but `migrate()` can never succeed for these holders while the mapping is missing.

A subtlety worsens the availability impact: because `migrate()` processes *all* of a caller's holdings atomically in one transaction, a holder who owns both a correctly-mapped index and a late unmapped index cannot migrate *any* of their NFTs. The revert at the late index rolls back the entire migration, including the otherwise-valid portion.

### Impact

- No direct asset loss: the V1 burn is rolled back with the rest of the transaction, and V1 NFTs retain their utility.
- Migration availability is denied to every holder of a V1 index registered after `setInitialized()`. A holder who owns both a valid index and a late index is blocked entirely, unable to migrate even their valid holdings.
- The condition is recoverable: the migrator owner can call `setMapping(lateIndex, v2Index)` to restore migration.

The trigger requires a privileged action by the V1 `NFTMinter` owner (registering a dispatcher post-initialization) and is recoverable by the migrator owner. These factors keep the severity at Medium rather than High. Critically, the V1 owner and the migrator owner are distinct trust principals, so this is not owner self-harm but a cross-contract ordering coupling between independently-owned contracts that silently bricks (burn-then-revert) instead of degrading gracefully.

## Proof of Concept

The validated Foundry PoC is at `workspace/yield-claim-nft/test/poc-M02-late-dispatcher-brick.t.sol`. It deploys the V1 minter, V2 minter, and migrator under three distinct owners, maps and initializes the two indexes that exist at init time, and then demonstrates three scenarios.

The setup wires the contracts with separate owners (`v1Owner != migratorOwner != v2Owner`), maps current V1 indexes `1` and `2`, and calls `setInitialized()`. A helper then performs the late dispatcher registration as the V1 owner:

```solidity
function _registerLateV1Dispatcher() internal returns (uint256 lateIndex) {
    Gather lateGather = new Gather(address(token), gatherRecipient, v1Owner);
    vm.startPrank(v1Owner);
    lateGather.setMinter(address(v1));
    lateIndex = v1.nextIndex();                 // index registerDispatcher will assign
    v1.registerDispatcher(address(lateGather), MINT_PRICE, 0);
    vm.stopPrank();
    assertEq(migrator.indexMapping(lateIndex), 0, "late index must be unmapped");
}
```

**Scenario 1 — late-index holder bricked** (`test_M02_lateDispatcherBricksMigrate`): after a late index `3` is registered (growing `v1.nextIndex()` to `4`) and a user mints one NFT at that index, `migrate()` reverts with the exact reason and the burn is rolled back:

```solidity
vm.prank(user);
vm.expectRevert("NFTMinterV2: index not registered");
migrator.migrate();

assertEq(v1.balanceOf(user, lateIndex), 1, "burn rolled back, NFT still held");
assertEq(v2.balanceOf(user, 1), 0, "no V2 minted");
```

**Scenario 2 — valid + late holder fully blocked atomically** (`test_M02_validHoldingsAlsoBrickedWhenLateIndexPresent`): a user holding two valid index-1 NFTs and one late index-3 NFT cannot migrate at all; the whole transaction reverts and the valid holdings are untouched:

```solidity
_mintV1(user, 1, 2);
_mintV1(user, lateIndex, 1);

vm.prank(user);
vm.expectRevert("NFTMinterV2: index not registered");
migrator.migrate();

assertEq(v1.balanceOf(user, 1), 2, "valid holdings untouched (rolled back)");
assertEq(v2.balanceOf(user, 1), 0);
```

**Scenario 3 — recovery via `setMapping`** (`test_M02_recoveryAfterOwnerAddsMapping`): once the migrator owner adds the missing mapping (after the V2 owner registers a corresponding V2 dispatcher), `migrate()` succeeds, confirming the brick is purely mapping-dependent and recoverable:

```solidity
migrator.setMapping(lateIndex, 3);

vm.prank(user);
migrator.migrate();

assertEq(v1.balanceOf(user, lateIndex), 0, "V1 burned after recovery");
assertEq(v2.balanceOf(user, 3), 1, "V2 minted after recovery");
```

All three tests pass against the submodule at commit `bc99ee3`. The revert string asserted in scenarios 1 and 2 is exactly `"NFTMinterV2: index not registered"`, matching `NFTMinterV2.mintFor`'s registration check for index `0`.

## Recommended mitigation steps

Any of the following addresses the issue; the first is preferred because it makes `migrate()` degrade gracefully without owner intervention:

1. **Skip unmapped indexes in `migrate()`** rather than burning and reverting. Validate the mapping before touching the holder's balance:

```solidity
for (uint256 i = 1; i < upperBound; i++) {
    uint256 v2Index = indexMapping[i];
    if (v2Index == 0) {
        continue; // index registered after init; not yet migratable
    }
    uint256 balance = IERC1155(address(v1)).balanceOf(msg.sender, i);
    if (balance > 0) {
        v1.burn(msg.sender, i, balance);
        for (uint256 j = 0; j < balance; j++) {
            v2.mintFor(v2Index, msg.sender);
        }
        emit Migrated(msg.sender, i, balance, v2Index);
    }
}
```

   This lets a holder migrate their valid indexes immediately and migrate the late index later once it is mapped, instead of being blocked atomically.

2. **Re-validate on each migration** by removing the one-way `initialized` assumption, or by re-running the full-range mapping check inside `migrate()` so that a missing mapping is surfaced before any burn occurs.

3. **Allow mappings to be extended after initialization** (which `setMapping`/`setMappings` already permit) and document the required ordering coupling: the migrator owner must add a mapping for any V1 index the V1 owner registers post-initialization before holders of that index attempt to migrate.

Additionally, consider documenting that the V1 `NFTMinter` and the migrator are independently owned and that the two owners must coordinate dispatcher registrations to preserve migration availability.
