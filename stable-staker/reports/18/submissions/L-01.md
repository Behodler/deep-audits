## Verification of the rationale — the bound is real, and was checked against source

The closure rests on a **checked fact**, not on an assertion. Verified against
`src/StableStakerV2.sol` at `cf8de27`:

```solidity
// :538-541 — the annihilation is capped at the caller's OWN principal
uint256 principalAsAntimatter = user.amount * scale;
uint256 capped = owed < principalAsAntimatter ? owed : principalAsAntimatter;
netWanted = capped / scale;                       // ⇒ netWanted <= user.amount, UNCONDITIONALLY

// :554 — the second clamp is therefore never taken: gross == netWanted ALWAYS
gross = netWanted > user.amount ? user.amount : netWanted;

// :559 — and that principal is CONSUMED, most of it landing in the minter as collateral
user.amount -= gross;
```

- The unbacked top-up per call is **1× the induced shortfall = `s * netWanted` ≤ `s ×` (the caller's
  **own** principal)**.
- At the live **120 bps** tolerance, minting **one** unit of unbacked phUSD costs roughly **83 units
  of the caller's own consumed principal**.
- **Aggregate** exposure across all stakers is bounded by **(total staked principal × `s`)** — *not*
  by the minter's daily cap.

The capital-efficiency argument **holds**.

## Finding description and impact

**Ledger fingerprint:** `9c5733dfad13be7c8d41c0dd5b00b5eae19587eba3169b5f8f00310f3237c027`

**Location:** `src/StableStakerV2.sol#L644-L648` (`_annihilateAndTopUp`), mint at `:646-647`.

### Summary

The story-028 shortfall top-up issues phUSD by calling the phUSD token contract **directly**. That
mint is gated only by `canMint` and a matching `mintVersion` — **no cap, no allowance, no
collateral** — and it **never increments `mintedToday`**, so `PhusdStableMinter`'s rolling 24h
`maxMintPerDay` is **structurally blind** to the path: it can neither refuse the mint nor account for
it afterwards.

**The route, not the value, decides the outcome.** The same protocol issues phUSD through two doors:
one metered and collateralised, one the minter cannot see.

### Vulnerability detail

The top-up, verbatim at `src/StableStakerV2.sol:644-648` — the mint itself is `:646-647`:

```solidity
// src/StableStakerV2.sol:644-648
phUSDMinted = target > delivered ? target - delivered : 0;
if (phUSDMinted > 0) {
    require(phUSDMintAvailable(), "StableStaker: phUSD mint unavailable");   // :646
    _phUSD().mint(address(this), phUSDMinted);                              // :647
}
```

`_phUSD()` resolves to `antimatter.phUSD()`, i.e. the `FlaxToken` itself, whose `mint` gates on
exactly two things — `canMint` and a matching `mintVersion`
(`lib/antimatter/lib/flax-token-v2/src/FlaxToken.sol:58-65`).

The only in-contract gate, `phUSDMintAvailable()`, is **not a value control**
(`src/StableStakerV2.sol#L1182-L1200`):

```solidity
// src/StableStakerV2.sol:1193-1200
if (!info.canMint) {
    return false;
}
(bool versionOk, bytes memory versionData) = token.staticcall(abi.encodeCall(IPhUSD.mintVersion, ()));
if (!versionOk || versionData.length != 32) {
    return false;
}
return info.mintVersion == abi.decode(versionData, (uint256));
```

It answers *"is minting switched on?"*. It does not answer *"how much, against what, and how much
already today?"*.

**Contrast the sanctioned route — `PhusdStableMinter.mint`**
(`lib/antimatter/lib/phUSD-stable-minter/src/PhusdStableMinter.sol:203-233`), which enforces
`!paused`, `config.enabled`, the rolling 24h window, **and takes a real stablecoin deposit that it
forwards into a yield strategy**:

```solidity
// lib/antimatter/lib/phUSD-stable-minter/src/PhusdStableMinter.sol:214-232
// Rolling 24h mint cap (disabled when maxMintPerDay == 0)
if (config.maxMintPerDay > 0) {
    if (block.timestamp >= config.lastMintTimestamp + 1 days) {
        config.mintedToday = 0;
        config.lastMintTimestamp = block.timestamp;
    }
    require(config.mintedToday + phUSDAmount <= config.maxMintPerDay, "Daily mint limit exceeded");
    config.mintedToday += phUSDAmount;
}

// Transfer stablecoin from caller to this contract
IERC20(stablecoin).safeTransferFrom(msg.sender, address(this), amount);
...
IMintableToken(phUSD).mint(msg.sender, phUSDAmount);
```

Four controls on one door; two checks — neither of them about value — on the other.

### Impact

**Scoped deliberately to the bypass itself** (see *Anti-double-count* below):

- **A solvency control that cannot see this path.** `PhusdStableMinter`'s rolling 24h
  `maxMintPerDay` is the protocol's per-window ceiling on phUSD issuance. This path is not subject to
  it and is not visible to it.
- **Zero collateral is taken.** The sanctioned route pulls stablecoin from the caller and forwards it
  to a yield strategy; the top-up deposits nothing. The phUSD it issues is unbacked by construction,
  not by accident.
- **`mintedToday` is never incremented.** After the bypass, the minter's own accounting still
  believes the window is largely unused — so the ceiling is not merely evaded once, it is left
  *mis-stated* for the remainder of the window, and subsequent sanctioned mints are sized against a
  counter that under-reports reality.

**For leak magnitude, see M-01 / `ss18m1`.** The 6.5425-USDe-class sandwich figure is stated **once**,
in M-01, and is deliberately **not** restated here. M-01 establishes *who can trigger* the top-up and
*what it costs*; this finding establishes that *nothing bounds its size*.

### Why Medium — the raise basis, stated plainly

The earlier Medium → Low downgrade rested on **avoiding double-counting the `slippageToleranceBps`
conditional with M-01**. That reasoning is wrong, for three independent reasons.

**1. The preconditions differ, and this one is strictly weaker.** M-01's empirical **142 bps
breakeven** gates *third-party attacker profitability* — at that block, with those pools, against
that victim size. This finding fires on **any shortfall from any source**: ordinary honest AMM
slippage, the N20-blessed **self-sandwich**, and (per N33) a zero-delivery strategy producing a
100%-inflation-funded payout. Not one of those needs an attacker, a profit, or a threshold. Pricing
the **weaker** precondition *lower* because the **stronger** one is priced at Medium is backwards.

**2. Size is not the point — structural blindness is.** The `90e18`-issued-against-a-`10e18`-cap
figure below demonstrates that the control **is not consulted at all**. It is **not** a claim that
9000 bps of exit slippage is required: a **1.1x cap breach is the same hole as a 9x breach**. The
size-independent evidence is the control described next — same value, same beneficiary, opposite
outcome, the only difference being the route.

**3. The mitigations are disjoint — which is the test for whether two findings are one.**

| | Mitigation |
|---|---|
| **M-01 / `ss18m1`** | Read, **bound and report `slippageToleranceBps`** from the `StableStakerV2` side. |
| **L-01 / `ss18l1`** (this) | **Route the top-up through `PhusdStableMinter`, or cap it locally.** |

**Neither discharges the other.** Bounding the tolerance does not restore the minter's cap or its
collateral deposit; routing/capping the top-up does not bound the tolerance. **Do not collapse
these two findings.**

### Lead with the size-independent control

**`test_ss18m3_negativeControl_frictionlessExit_sameSizedPayout_isRefusedByTheCap`** is the sharpest
evidence, and it does not depend on the size of the shortfall at all.

Same armed cap (`10e18`), same stake, same accrual, **the same `100e18` phUSD payout to the same
beneficiary**. The only difference is that the exit delivers in full (`setExitSlippageBps(0)`), so
the whole stable half routes **through** `PhusdStableMinter`:

```solidity
minter.setMaxMintPerDay(address(dai), MAX_MINT_PER_DAY); // 10e18
ys.setExitSlippageBps(0);                                // frictionless: no shortfall, no top-up
...
vm.prank(alice);
vm.expectRevert("Daily mint limit exceeded");
staker.autoAnnihilate(address(dai));
assertEq(phUSD.totalSupply(), 0, "CONTROL: an identically-sized COLLATERALISED payout is blocked outright");
```

**Same value, same beneficiary, opposite outcome. The only variable is the route.** A frictionless
exit paying Alice `100e18` phUSD is **refused**; a 90%-haircut exit paying Alice the **same
`100e18`** **succeeds**, because `90e18` of it took the unmetered `FlaxToken` door. The cap does not
govern issuance — it governs only whichever fraction of issuance happens to be collateralised.

### The bypass itself

`test_ss18m3_topUpBypassesTheDailyCapAndTheCollateralDeposit`, with the cap armed at `10e18`:

1. **The cap is real and armed.** A direct, sanctioned `minter.mint(dai, 11e18)` reverts
   `"Daily mint limit exceeded"`, consumes no allowance, and issues no phUSD.
2. **The top-up ignores it.** `autoAnnihilate` then issues **`90e18` in one transaction** —
   `assertEq(phUSDMinted, 90 ether, "exact top-up: 9x the whole daily cap, in a single transaction")`
   — and Alice is paid the full frictionless target of `100e18`, which reaches her wallet.
3. **Zero collateral for it.** Only the `5e18` **backed** half deposits collateral:
   `assertEq(collateralAfter - collateralBefore, 5 ether, "...the 90e18 top-up deposited none")`, and
   `assertEq(phUSD.totalSupply() - supplyBefore - (collateralAfter - collateralBefore) * 2, 90 ether,
   "90e18 phUSD exists against zero new collateral")`.
4. **The counter never sees it.** `assertEq(_mintedToday(), 5 ether, "the minter's rolling-window
   counter records ONLY the backed half — 90e18 of phUSD was issued invisibly to it")`, leaving the
   minter believing `5e18` of today's allowance is still unused **after `95e18` of phUSD was issued**.

### Negative controls — the cap is not merely unarmed

- **`capBindsOnTheBackedHalf`** — with the cap lowered to `4e18`, below the `5e18` backed half, the
  identical `autoAnnihilate` **reverts with the minter's own `"Daily mint limit exceeded"`**. The cap
  is live and *in-path* for the collateralised leg, so its total absence from the `90e18` leg is a
  **bypass**, not an unarmed control.
- **`topUpIsIdenticalWithTheCapDisabled`** — with the cap set to `0` (no limit at all), the top-up is
  **byte-identical at `90e18`**. The top-up leg is provably indifferent to the cap's value: `10e18`,
  `4e18` or `0` changes only the backed half.

### Mutation-falsifiable

Mutating the fixture's exit slippage from `9000` bps to `0` makes the positive test **fail** — with
no shortfall there is no top-up, so the bypass leg does not execute. The test cannot pass vacuously.

## Recommended mitigation steps

**Route the shortfall top-up through `PhusdStableMinter` so the rolling 24h cap and the collateral
deposit apply**, or — if the top-up must remain unbacked by design — **give `StableStakerV2` its own
independent, owner-set per-window mint cap on this path**, so that the amount of uncollateralised
phUSD issuable outside the minter's discipline is bounded *in code* rather than by the incidental
size of exit slippage.

A local invariant on the top-up as a fraction of the payout achieves the same bound in one line, and
is the same check M-01 recommends for a different reason:

```solidity
uint256 target = netWanted * scale + stableMinter.calculateMintAmount(token, netWanted);
phUSDMinted = target > delivered ? target - delivered : 0;
require(phUSDMinted * 10_000 <= target * maxShortfallBps, "StableStaker: top-up exceeds policy");
```

Secondary measures:

1. **Meter the bypass even if you keep it.** At minimum, report the uncollateralised issuance to
   `PhusdStableMinter` (or to a dedicated counter) so the protocol's per-window view of phUSD
   issuance is not silently under-stated for the rest of the window.
2. **Emit the unbacked figure distinctly.** `phUSDMinted` on `AutoAnnihilated` is currently the only
   trace; an explicit, indexed "uncollateralised issuance" signal makes the exposure monitorable
   off-chain without event-decoding archaeology.
3. **Assert on wiring.** `phUSD.setMinter(address(staker), true)` is a `FlaxToken`-level, unmetered
   grant (story 026). It deserves an explicit, documented acknowledgement at the point of granting
   that it confers issuance authority *outside* the minter's controls.
