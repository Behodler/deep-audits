## Finding description and impact

**Severity: LOW** (lowered from Medium post-review — see the banner above).

**Ledger fingerprint:** `5b6ea4c61d88e942d4d9f36495cb62b3397d3b305ba0d53aab107611f8ea5398`

### Summary

`autoAnnihilate` — the reward path every staker is steered into while `claimEnabled` is false — draws from the shared underwater-**withdrawal** buffer. One staker harvesting rewards can exhaust that buffer and leave a different, solvent staker unable to exit. No attacker and no adversarial configuration is required: an ordinary reward claim by an ordinary user causes it.

The contract's own NatSpec states the opposite as an invariant.

### Vulnerability detail

**The invariant, stated verbatim at `src/StableStakerV2.sol:485-488`:**

```
 *           The top-up is new phUSD, NOT a draw on this contract's idle stable balance: that
 *           balance is the shared underwater-withdrawal buffer, and the invariant that
 *           `autoAnnihilate` never spends a unit of it survives intact. No other staker's position
 *           is touched by one caller's exit haircut.
```

**The path that falsifies it.** `autoAnnihilate` routes its principal exit through `_routeExit` with the underwater guard on, at `src/StableStakerV2.sol:574`:

```solidity
uint256 received = _routeExit(token, gross, true);
```

and `_routeExit`'s underwater branch, at `src/StableStakerV2.sol:1314-1325`, returns the full requested amount **without any token arriving from the strategy** — it merely writes recorded principal down and signals "use the buffer":

```solidity
IERC20 t = IERC20(token);
if (guardUnderwater && _isUnderwater(token, strategy)) {
    // Underwater: try to satisfy the entire withdraw from the on-contract buffer.
    // Caller forwards the returned amount via safeTransfer, so we just signal
    // "use the buffer" by returning `amount` without touching the strategy.
    if (t.balanceOf(address(this)) >= amount) {
        emit BufferWithdrawn(token, msg.sender, amount);
        strategy.relinquishPrincipal(token, amount);
        return amount;
    }
    revert("StableStaker: strategy underwater");
}
```

The buffer is then actually spent at `src/StableStakerV2.sol:682`, where `Antimatter` is approved to pull that same idle balance out of the contract:

```solidity
IERC20(token).forceApprove(address(antimatter), netUsed);
antimatter.annihilate(
    token, address(this), annihilatable, annihilatable + stableMinter.calculateMintAmount(token, netUsed)
);
```

**The advertised top-up does not fire on the very path where the shortfall is paid.** On the buffer branch `received == gross == netWanted`, so `netUsed == netWanted`, so `delivered == target` and, at `src/StableStakerV2.sol:644`:

```solidity
phUSDMinted = target > delivered ? target - delivered : 0;
```

`phUSDMinted == 0`. The story-028 mechanism whose stated purpose is to keep the exit haircut off other stakers is inert precisely where it would be needed; the shortfall is instead paid out of pooled assets.

### Impact

C4 Medium — **availability**. Assets are not stolen, but a solvent staker's `withdraw()` reverts `"StableStaker: strategy underwater"` because a *different* staker harvested rewards. In the PoC, Bob's withdrawal succeeds at par in the counterfactual where the buffer is intact and reverts after Alice's `autoAnnihilate`.

There is a second, quieter effect on the same draw: the value `initiateMigration` measures as `R` (`R = IERC20(token).balanceOf(address(this))`, `src/StableStakerV2.sol:839`) is reduced by exactly the amount drawn, so every remaining staker's pro-rata migration credit `p_i * min(R,P) / P` is scaled down.

The conditions and the limits of that impact, stated here rather than in a footnote:

- **V2 is undeployed.** Mainnet runs the frozen V1 at `0xbce8ABC0`. This is a pre-deployment finding.
- **The strategy must be underwater.** This is a transient condition by design, and the denial clears when the strategy recovers — the denied staker is not permanently locked out.
- **The per-call draw is bounded** by the calling staker's own accrual and their own principal (`netWanted = capped / scale` where `capped = min(owed, user.amount * scale)`). It is not an unbounded drain.
- **No drain to insolvency was demonstrated.** The PoC exercises a single reward call; aggregate exhaustion across many callers was not tested.
- **No user loses principal.** The harm is a denied-and-deferred exit, plus a diluted migration credit — not a loss of booked position.

### The design intent is real, and this finding survives it

The underwater carve-out **is** evidenced as deliberate: the project's `CLAUDE.md` documents it, and `test/AutoAnnihilate.t.sol:389` — verified present at `cf8de27` — already asserts buffer consumption in `test_autoAnnihilate_underwaterStrategy_paysFromTheBuffer()`. That should be weighed openly, and a human may reasonably resolve this as won't-fix on intent.

It does not dispose of the finding, for two reasons:

1. **The known issue carrying that carve-out (N19) has no suppression authority.** N19 justifies itself by citing a `CLAUDE.md` section that does not exist at `cf8de27`. The run-18 known-issues re-extraction rules on it explicitly and twice: *"N19 — caveat STANDS, no suppression authority ... N19 evidences intent and nothing more"*, and sanitizer usage rule 3, *"N19 suppresses nothing (unanchored self-citation)."* Intent evidence is for a human to weigh, not a suppression to apply.
2. **N19's central claim is exactly what is disputed.** It asserts that `autoAnnihilate` *"shares the underwater path with `withdraw` and does not change it."* That equivalence does not hold. `withdraw` consumes the buffer **1:1 with a position leaving** — the buffer shrinks and so does the claim on it. `autoAnnihilate` is a **repeatable reward action**: the caller keeps their remaining position and can return as reward accrues, consuming buffer that was sized for withdrawals. That asymmetry, not the carve-out itself, is the finding.

### Why Medium and not High

No assets are stolen and no principal is lost; the denied staker's booked position is unchanged and the denial is transient, clearing when the strategy returns above par. The per-call draw is bounded by the caller's own stake and accrual, and no path to permanent insolvency was demonstrated. That is protocol function/availability impact — Medium — not direct loss of assets.

What the main test proves, in order:

- **The invariant is falsified.** The contract's idle stable balance strictly decreases, by exactly `netUsed`: `60e18 → 10e18` on a 50e18 annihilation.
- **The top-up did not fire.** `phUSDMinted == 0`, while Alice is nonetheless paid the full frictionless target of `100e18` phUSD.
- **`relinquishPrincipal` moved no assets.** Strategy principal is written down by the full gross while `dai.balanceOf(address(vault))` is unchanged — the 50e18 came from the shared pile.
- **Concrete harm to Bob.** Same block, unchanged 100e18 position, strategy still underwater:

```solidity

vm.expectRevert("StableStaker: strategy underwater");
staker.withdraw(address(dai), 50 ether);
```

- **The counterfactual**, run as its own test so the "before" state is unambiguous: with the buffer intact, Bob's identical withdrawal **succeeds at par**. That is what makes the revert a harm rather than a pre-existing condition.
- **Two negative controls pass** — a not-underwater real strategy and a selling strategy both fire the top-up and leave the buffer untouched, so the effect is specific to the underwater branch.
- **Mutation-falsifiable:** removing the vault loss makes the test **fail at its own precondition** (`assertLt(totalBalanceOf, principalOf, "precondition: _isUnderwater(dai, ys) is TRUE")`), so the test cannot pass vacuously.

## Recommended mitigation steps

Three options, to be weighed on how much reward-path availability the protocol wants to trade for withdrawal availability:

1. **Exclude the reward path from the underwater carve-out (recommended).** Make `autoAnnihilate` revert while the strategy is underwater rather than draw on the buffer — pass `guardUnderwater` through a mode that fails rather than one that spends. Rewards are deferrable; a solvent staker's exit is not, and the underwater state is transient by the design's own premise. This restores the `:485-488` invariant exactly as written.
2. **Reserve the buffer against outstanding withdrawal demand.** Let the reward path draw only from the buffer in excess of a reserve sized to pending/expected withdrawals, so a harvest can never consume the last unit a withdrawal needs.
3. **Cap reward-path buffer draws.** Bound the fraction of the idle balance any single `autoAnnihilate` may consume (e.g. a per-call or per-window bps ceiling), which limits denial without disabling harvesting outright.

If instead the behaviour is affirmed as intended, the **documentation fix is not optional**: the invariant at `src/StableStakerV2.sol:485-488` claims the exact opposite of what the code does, and a future reader relying on it would reason incorrectly about buffer sizing. Note that the code fix and the doc fix (**F-04**) land independently — resolving one does not discharge the other.
