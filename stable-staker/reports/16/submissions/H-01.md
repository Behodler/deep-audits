## What was disproved

The finding claimed a dormant pool **banks** emissions that the first staker then captures. **That is
false.** `_updatePool` fast-forwards the clock on the empty branch — `src/StableStakerV2.sol:816-819`:

```solidity
if (pool.totalStaked == 0) {
    pool.lastRewardTime = block.timestamp;
    return;
}
```

and `stake` calls `_updatePool` at `:327` **before** `pool.totalStaked += credited` at `:335`. At that
moment the pool is still empty, so `lastRewardTime` jumps to now and the new staker's `rewardDebt` is
set against an index that never advanced. **The dormant window is discarded, not banked.** A staker
entering after 10 idle days accrues only from that instant. This is textbook MasterChef, and it is
correct behaviour.

The PoC's 90-day warp occurred **after** the 1-wei stake, so it only ever demonstrated that a **sole**
staker holding dust collects the full rate **going forward**. The companion test
`test_emptyPoolAccruesNothing` measured `lastRewardTime` advancing with `accAntimatterPerShare`
unchanged — **that measurement was the refutation**, and it was mis-read as supporting evidence.

Consequently the "≈ $900,000 of unbacked phUSD created against ≈ $1e-6 of staked capital" framing does
not stand: the figure is the size of a 90-day **scheduled emission budget**, not net-new issuance and
not a measure of loss.

## What survives — stated, not inflated

Emission is time-denominated and **TVL-independent**, so an armed pool with negligible stake still
mints at the full scheduled rate, and since story-023 those tokens are claims on unbacked phUSD.

That is real. It is also bounded, and the bounds are part of the finding:

- **No other staker is diluted out of anything.** The empty window banked nothing, so nobody was
  deprived.
- **Any genuine staker immediately dilutes the dust holder pro rata**, from the moment they stake.
- **The tokens emitted are budgeted emission being misallocated** — not issuance conjured outside the
  schedule.

That is a **Low**.

## Owner triage — wont-fix, 2026-08-31

Closed **wont-fix**, in the owner's terms. This is **not** `fix-pending`: the owner is not fixing it,
they are living with it.

1. The behaviour is **intuitive and expected** — closer to a marketing/optics risk than a security defect.
2. **Day-1 exposure is zero:** an existing user base is being migrated in, so the pool is never empty at
   launch. The retired-pool and organically-emptied windows are **future** states, not present exposure.
3. **Realization is capital-positive for the protocol:** to annihilate, the redeemer must front matching
   stablecoin, which routes through the minter as real backing and **increases** locked
   protocol-owned capital.

**One caveat, preserved as context and not as a rebuttal:** `annihilate` adds **2x liability against 1x
backing**, so the collateralization **ratio** still slips even though absolute locked capital rises.
Point 3 is true of absolute capital, not of the ratio.

**Reopen trigger (`REOPEN-ss16h1`).** Revisit if a pool is ever left **armed** (`antimatterPerSecond > 0`)
with near-zero TVL after its users exit — a retired or fully-drained pool that is **not** disarmed via
`antimatterPerDay(token, 0)`. That is the state where the surviving misallocation actually bites.
Reopen with `/ledger stable-staker reopen 3102c29c`.

still passes, but it **proves a narrower claim than this report asserted**: that a sole dust-sized staker
collects the full scheduled rate going forward. It does not demonstrate capture of a banked window.

## Finding description and impact

### Summary

`StableStakerV2` emits Antimatter on a pure **time** denominator. `_updatePool` returns without accruing anything while the pool is empty, and once it is non-empty it computes the reward from elapsed time alone, with **no reference to `totalStaked`**. The result is a hard discontinuity at zero stake: an armed-but-empty pool banks nothing while it is empty, and the first depositor — **one wei is sufficient** — captures 100% of the subsequent full-rate stream. **[RETRACTED in part — "captures" overstates it: the window before the stake is discarded by the `:817-819` fast-forward, so a dust staker collects only the full rate *going forward* while it stands alone, and any genuine staker dilutes it pro rata immediately.]**

Since story-023 the emitted unit is Antimatter, which is redeemable through the **permissionless** `Antimatter.annihilate`. That function mints the antimatter half as **unbacked phUSD**. The over-emission is therefore not a redistribution among stakers; it is **realized dilution of the protocol's phUSD backing**, borne by phUSD holders. **[RETRACTED — what is emitted is budgeted, scheduled emission being misallocated, not issuance created outside the schedule. The ratio effect of `annihilate` is real and is preserved as the caveat in the banner; the "net-new dilution" framing is not.]**

### Vulnerability details

`src/StableStakerV2.sol:806-826` (root cause; the two load-bearing lines are `:817-819` and `:822`):

```solidity
806:    function _updatePool(address token) internal {
...
813:        PoolInfo storage pool = poolInfo[token];
814:        if (block.timestamp <= pool.lastRewardTime) {
815:            return;
816:        }
817:        if (pool.totalStaked == 0) {
818:            pool.lastRewardTime = block.timestamp;
819:            return;
820:        }
821:        uint256 elapsed = block.timestamp - pool.lastRewardTime;
822:        uint256 reward = elapsed * pool.antimatterPerSecond;
823:        if (reward > 0) {
824:            pool.accAntimatterPerShare += (reward * ACC_PRECISION) / pool.totalStaked;
825:        }
826:        pool.lastRewardTime = block.timestamp;
```

Line `:817` fast-forwards `lastRewardTime` past the empty window without advancing the index — nothing is banked. Line `:822` then pays `elapsed * antimatterPerSecond` regardless of how much stake is present; `totalStaked` appears only at `:824` as the *divisor of the share index*, so a sole staker's share of the window is 100% whether they hold one wei or one million USDC.

Entry costs one wei because `stake` only requires a non-zero credit:

```solidity
333:        require(credited > 0, "StableStaker: nothing credited");
```
(`src/StableStakerV2.sol:333`)

and `claim` mints the accrued amount directly:

```solidity
385:        antimatter.mint(msg.sender, owed);
```
(`src/StableStakerV2.sol:385`)

**Attack path** (two transactions, no privileged role, no race, no MEV requirement):

1. Observe a pool that is `Active` with `totalStaked == 0` and `antimatterPerSecond != 0`.
2. `stake(token, 1)` — one wei, satisfying `:333`.
3. Wait. `_updatePool` accrues the full rate to the sole staker.
4. `claim(token)` — the whole window's Antimatter is minted to the attacker (`:385`).
5. `Antimatter.annihilate(...)` — burn the AM and supply matching stablecoin; receive backed phUSD for the stable half **and an equal amount of unbacked phUSD for the antimatter half**.

The unbacked mint is:

```solidity
294:        _phUSD.mint(recipient, amount);
```
`lib/antimatter/src/Antimatter.sol:294` **at commit `a5570ce`** — this is the nested submodule pin that `stable-staker` records and compiles against (`git -C lib/stable-staker ls-tree HEAD lib/antimatter` → `a5570ce1e968…`; the PoC below compiles against that pin). *Note for readers navigating a different checkout:* the top-level `lib/antimatter` HEAD `3a96fb7` carries the identical call at `:263`; the two copies differ in that `a5570ce` declares `contract Antimatter is ERC20, Ownable, Pausable, ReentrancyGuard, IPausable` while `3a96fb7` has dropped the `Pausable` mixin. Cite `a5570ce:294` for anything compiled against this repository.

### Reachability — the enabling state is the default end-state, not a misconfiguration

**No *automatic* path zeroes `antimatterPerSecond`.** A remedy does exist and is stated here in full so the claim is not overstated: the owner-only setter `antimatterPerDay(token, 0)` writes `antimatterPerSecond = 0` —

```solidity
214:    function antimatterPerDay(address token, uint256 amountPerDay) external onlyOwner poolExists(token) {
215:        _updatePool(token);
216:        uint256 perSecond = amountPerDay / SECONDS_PER_DAY;
217:        poolInfo[token].antimatterPerSecond = perSecond;
```
(`src/StableStakerV2.sol:214-217`; `:217` is the **sole write site** of `antimatterPerSecond` in the contract — the other occurrences at `:24`, `:28`, `:33` are comments, `:70` is the declaration, `:140` is the event, and `:750`/`:822` are reads.)

**Why the remedy does not blunt the finding.** Disarming requires a *deliberate, unprompted owner transaction*. Nothing calls it: no lifecycle transition — `initiateMigration`, `finalizeAndReset`, the last `withdraw`, `emergencyWithdraw` — touches the rate, no contract path invokes it, and no runbook step in the project's documentation requires it. A pool that has been armed therefore **stays armed by default**, and armed-and-empty is the resting state of any pool users leave. The enabling state arises by the protocol doing *nothing*:

- **(a) Launch window** — `addToken` then `antimatterPerDay` before the first staker arrives; this is the wiring order the project's own `CLAUDE.md` documents.
- **(c) Retired pool** — an operator stops using a pool without disarming it.
- **(d) Organic emptying** — every staker withdraws. This is the end state of *every* pool.
- Additionally after `finalizeAndReset`, which revives a pool at its stale rate (reported separately as **L-08** in the QA report — downgraded from Medium this run because its severity basis was borrowed from this finding; it retains a **distinct remedy** and a distinct ledger entry).

The PoC reaches state (d) with **real calls only** — an honest staker stakes and withdraws in full. There is no `vm.store`, no cheat-code state injection, and no owner error anywhere in the path.

### Disclosed mitigating factor — the minter's rolling 24h mint cap

A throttle exists on the realization leg and is disclosed here in full, because omitting a mitigation that exists would discredit the rest of this report. It is **not** in `Antimatter`; it is one layer further down, in
`lib/stable-staker/lib/antimatter/lib/phUSD-stable-minter/src/PhusdStableMinter.sol` (pin `d6ed115`), inside `mint`:

```solidity
214:        // Rolling 24h mint cap (disabled when maxMintPerDay == 0)
215:        if (config.maxMintPerDay > 0) {
216:            if (block.timestamp >= config.lastMintTimestamp + 1 days) {
217:                // Window elapsed (or first mint: lastMintTimestamp == 0) -> start a new window
218:                config.mintedToday = 0;
219:                config.lastMintTimestamp = block.timestamp;
220:            }
221:            require(config.mintedToday + phUSDAmount <= config.maxMintPerDay, "Daily mint limit exceeded");
222:            config.mintedToday += phUSDAmount;
223:        }
```

`maxMintPerDay` is declared per stablecoin at `:30` (`uint256 maxMintPerDay;  // owner-set cap in phUSD (18 decimals); 0 = no limit`), is written by the owner-only `setMaxMintPerDay` at `:190`, and — decisively — is initialised to **`0` (disabled)** for every newly registered stablecoin at `:125`.

Because `annihilate` routes its **backed** half through `minter.mint(stable, stableAmount)` (`Antimatter.sol:282`), a cap breach reverts the **whole** `annihilate`, unbacked half included. So where a non-zero cap is configured, a single ≈900k realization does not fit in one transaction and the attacker must drip the annihilation across days.

**This does not change the severity, and the reasons are specific:**

1. **It gates realization speed, not the dilution.** The Antimatter is already minted and held by the attacker the moment `claim` returns (`:385`); nothing in the minter can claw it back. The cap converts a single-transaction realization into an N-day drip of the same total.
2. **It is off by default.** `registerStablecoin` sets `maxMintPerDay: 0`, and `0` means *no limit*. Absent a deliberate `setMaxMintPerDay` call per stablecoin, the throttle is inert.
3. **It is not a solvency control.** Even fully armed, it bounds phUSD minted per stablecoin per day across *all* callers; it does not distinguish backed from unbacked mints and does not restore collateralization.

**Two honest consequences for the rest of this report.** First, the "two transactions" framing above describes the *default* (uncapped) configuration; with a cap armed, the realization leg becomes `ceil(900k / maxMintPerDay)` transactions on successive days. Second, the PoC ran against a mock deposit sink and a freshly registered stablecoin, so it exercised the `maxMintPerDay == 0` path — **the live `maxMintPerDay` for each production stablecoin should be read on-chain before this report is relied on for a realization-time estimate.** The dilution figure is unaffected either way.

### Severity justification (C4)

**High.** Assets are compromised directly, by a valid attack path with no hypotheticals: two permissionless transactions produce ≈ $900k of unbacked phUSD. **[RETRACTED — severity is Low. The premise of this paragraph is the disproved banked-window mechanism.]** The value compromised is the protocol's phUSD backing — a protocol asset held on behalf of identifiable third parties.

**How the loss is established — stated precisely, because the obvious framing does not hold.** This report does **not** rest on "a phUSD holder is denied a redemption." It cannot: `PhusdStableMinter` is **mint-only**. Its entire external surface is `setPauser`, `pause`, `unpause`, `registerStablecoin`, `updateExchangeRate`, `setStablecoinEnabled`, `noMintDeposit`, `approveYS`, `setMaxMintPerDay`, `mint`, and three views — there is **no `redeem`, no `burn`, no `withdraw`** (verified at `lib/stable-staker/lib/antimatter/lib/phUSD-stable-minter/src/PhusdStableMinter.sol`, pin `d6ed115`). No holder is turned away at a redemption window, because no on-chain redemption window exists.

The argument that does hold is simpler and stronger: **`annihilate` raises the protocol's outstanding phUSD liability by `2·amount` while raising its backing by only `amount`, so the collateralization ratio falls at the moment of mint, unconditionally.** That is not a downstream market effect; for a stablecoin it *is* the definition of undercollateralization. Market depth governs how much of the shortfall the **attacker** converts into realized profit; it does not govern **whether the protocol lost**, which is settled inside the `annihilate` call itself and independent of any price assumption. The `assumptions` note that "phUSD trades near par" therefore bounds the attacker's extraction, not the protocol's loss.

**Plausibility: Plausible High.** No validator collusion, no oracle failure, no governance capture, no economic black swan. Two transactions and patience.

**Counter-arguments considered and rejected**, stated so a reader can weigh them:

1. *"This is Medium — it requires the owner to have armed a rate against a pool with no users, i.e. an external requirement."* Rejected: C4's Medium carve-out contemplates a precondition that must be **arranged**. Here no code path clears `antimatterPerSecond`, and windows (c) and (d) are what every pool becomes at end of life. A precondition the protocol reaches by doing nothing is the default configuration, not an external requirement.
2. *"No staker is short-changed — the pool was empty."* Correct, and it is why the harm had to be measured rather than assumed. The PoC runs the real `annihilate` and measures phUSD supply against backing. The harm lands on phUSD holders. That narrows *who* pays; it does not make the loss hypothetical.
3. *"The attacker must front ~900k stablecoin."* Rejected — see above; it returns in the same call.
4. *"This is an admin mistake and thus C4-invalid."* Rejected. The exploit is executed by an unprivileged external address; the owner's only contribution is an omission whose consequence (a zero-user pool carrying a live dilution liability) a competent, non-malicious owner would be surprised by. That is a non-obvious footgun, classified by the impact it unlocks.
5. *Cost basis / known-issue suppression.* The project's emission-cap statement bounds emission **quantity**; this finding concedes the cap holds and attacks the cap's **cost basis** (the cap is now a phUSD dilution budget). The statement "empty-pool windows accrue nothing" is true and off-point — the attack stakes one wei, so the pool is not empty.

## Recommended mitigation steps

(1) or (2) closes the primary path and (1) is the structural fix; (3) closes the lifecycle hole that produced it; (4) and (5) are operational and containment measures that reduce exposure without fixing the defect.

**1. Disarm on empty, or make emission stake-referenced.** The cleanest fix is to stop paying a time-denominated stream to a pool with no meaningful stake. Either zero the rate when a pool empties, or gate accrual on a minimum-stake floor:

```solidity
if (pool.totalStaked < MIN_ACCRUAL_STAKE) {   // e.g. a sane per-token dust floor
    pool.lastRewardTime = block.timestamp;
    return;
}
```

This preserves the existing "empty pools bank nothing" behaviour while removing the ability of a dust position to become the sole claimant of a full-rate stream.

**2. Bound the per-address share of a window.** Alternatively, cap the emission an account can accrue in a window by its share of a reference stake level, so a 1-wei position cannot receive a 100% share.

**3. Operational hygiene, and rate lifecycle.** Add an explicit `antimatterPerDay(token, 0)` step to the decommissioning runbook, and — because relying on a runbook is exactly what produced this — have the contract itself zero `antimatterPerSecond` whenever a pool transitions out of active use. In particular `finalizeAndReset` must zero the rate on revival — **that remedy is deliberately not covered by this finding and is written up as `L-08` in `qa-report.md`** (fingerprint `ss9l1-finalizeAndReset-revival-stale-emission-rate`, preserved verbatim). Leaving the rate armed on revival re-opens this same path, and `L-08` additionally carries a `yieldStrategy` re-binding leg this finding does not touch at all.

**4. Arm `PhusdStableMinter.setMaxMintPerDay` for every registered stablecoin.** This is a real, already-built operational control that is currently **disabled by default** (`maxMintPerDay: 0` at `PhusdStableMinter.sol:125`). It does not fix the defect — it caps the rate at which any single actor can convert Antimatter into phUSD, converting a one-transaction realization into a multi-day drip that a monitor can catch. Treat it as containment and time-to-detect, not as a remedy.

**5. Re-derive `antimatterPerDay` against the new premise.** A rate calibrated when the reward token had no redemption path is now a **phUSD dilution rate**. Independent of the code fix, every live `antimatterPerDay` value should be re-approved with that meaning stated.
