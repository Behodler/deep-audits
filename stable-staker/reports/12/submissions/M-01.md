## Finding description and impact

### Summary

`InPlaceMigrator.migrateIn` debits each parked user's principal accounting by the **requested** amount but re-credits the user only by the amount the new yield strategy actually books on the deposit leg. When the re-injection strategy haircuts deposits (a market/AMM/fee-bearing ERC4626 target), every re-injected staker is silently re-credited fewer shares than the principal that was parked for them. The shortfall is irrecoverable: there is no residual parked balance, no event, and no revert.

### Vulnerability details

The in-place migration round trip is: `initiateMigration` -> `migrateOut` (parks each user's principal in the migrator) -> operator resets the now-empty pool and wires a fresh strategy via `setYieldStrategy` -> `migrateIn` (re-injects parked principal into the same immutable staker via `depositFor`).

The accounting break is on the re-injection leg. In `InPlaceMigrator.migrateIn` ([InPlaceMigrator.sol#L215-L223](https://github.com/Behodler/stable-staker/blob/master/src/InPlaceMigrator.sol#L215-L223)) the migrator zeroes the user's parked balance and decrements the global `totalParked` by the **full requested `amt`**, then forwards that same `amt` to the staker:

```solidity
// InPlaceMigrator.migrateIn loop body
uint256 amt = parked[token][user];
if (amt == 0) { continue; }
parked[token][user] = 0;                 // L215  parked zeroed by the FULL requested amt
delete migrationBegin[token][user];
totalParked[token] -= amt;               // L217  global total reduced by the FULL requested amt
_parkedUsers[token].remove(user);
count++;
staker.depositFor(token, user, amt);     // L223  forwards the full requested amt
```

Inside `StableStaker.depositFor` ([StableStaker.sol#L630-L634](https://github.com/Behodler/stable-staker/blob/master/src/StableStaker.sol#L630-L634)), the user's recorded principal is increased not by `amt` but by `_routeDeposit`'s return value:

```solidity
uint256 received = _pullToken(token, msg.sender, amount);
uint256 credited = _routeDeposit(token, received);   // L631  strategy haircut: credited < amt
require(credited > 0, "StableStaker: nothing credited");
info.amount += credited;                              // L633  user re-credited only the haircut amount
pool.totalStaked += credited;                         // L634  pool tracks only the haircut amount
```

`_routeDeposit` ([StableStaker.sol#L757-L763](https://github.com/Behodler/stable-staker/blob/master/src/StableStaker.sol#L757-L763)) returns whatever the strategy's `deposit()` books. For an idle/direct/par/1:1-ERC4626 target this equals `amt` and there is no loss; but for a market/AMM/fee-bearing ERC4626 strategy, `deposit()` books **below** `amt`:

```solidity
function _routeDeposit(address token, uint256 amount) internal returns (uint256 credited) {
    IYieldStrategy strategy = yieldStrategy[token];
    if (address(strategy) == address(0)) {
        return amount;                       // idle hold: full credit, no loss
    }
    return strategy.deposit(token, amount, address(this));   // haircutting strategy books < amount
}
```

The net effect: parked accounting is debited by `amt`, the user's `userInfo.amount` is credited only `credited`, and the `amt - credited` delta is left in the strategy as protocol-owned surplus credited to no user. Because the parked balance is already zeroed by the full `amt`, the timeout escape hatch `claimTimedOut` (which reads `parked[token][msg.sender]`) can recover nothing for the shortfall — the user has no recourse.

### Impact

Each re-injected staker permanently loses `amt - credited` of principal, scaling linearly with the strategy's deposit slippage/fee and with position size. The PoC measures a 20 USDC loss on a 1,000 USDC re-injection at a 200 bps haircut; fuzzing over 1–500 bps shows the loss for every non-zero slippage. There is no event emitted for the shortfall and no residual balance, so the loss is silent and undetectable from on-chain accounting.

This is **not** an external-attacker theft. It is a silent per-user principal loss / mis-accounting that materializes when the operator wires a haircutting re-injection strategy. Consistent with the C4 Medium criterion, the loss is a **value leak with stated assumptions and external requirements** (the operator chooses a slippage/fee-bearing re-injection strategy; par/idle/1:1 targets preserve principal exactly).

It is also:

- A **Law-2 faithfulness break.** The migrator's own stated contract (story-012 AC-1, [InPlaceMigrator.sol#L169](https://github.com/Behodler/stable-staker/blob/master/src/InPlaceMigrator.sol#L169)) promises `migrateIn` "credit[s] each user the exact principal that was parked for them." The re-credited `userInfo.amount` is strictly less than the parked principal, breaking that guarantee.
- A **Law-3 non-obvious owner footgun.** A competent, non-malicious operator reaching for the sanctioned in-place "rewire" tool would reasonably expect a loss-neutral principal round trip. There is no migrator-side signal that re-injecting into a haircutting strategy crystallizes a per-user loss, so the operator is surprised — exactly the test for an in-scope operational hazard.

## Recommended mitigation steps

Make the re-injection accounting reflect the amount actually credited, or refuse to lose principal silently. Any of the following closes the gap (in rough order of preference):

1. **Credit the actually-received amount into parked accounting / refund the delta.** Have `depositFor` return `credited`, and in `migrateIn` decrement `parked[token][user]` and `totalParked[token]` by `credited` rather than the requested `amt`, leaving any shortfall still parked so the user can `claimTimedOut` the remainder — or transfer the `amt - credited` delta back to the user.

2. **Fail loudly on a haircut.** After the deposit, require `credited >= amt` (optionally minus a small explicit tolerance) and revert the slice otherwise, so the operator cannot unknowingly re-inject into a haircutting strategy:

```solidity
uint256 credited = staker.depositFor(token, user, amt);   // depositFor must return credited
require(credited + tolerance >= amt, "InPlaceMigrator: re-injection haircut");
```

3. **Block in-place migration to haircutting strategies.** Gate `migrateIn` (or `setYieldStrategy` while a parked set is outstanding) so the in-place flow can only target a strategy that conserves principal on deposit (idle/direct/par/1:1-ERC4626), and route impaired/market strategies through the cross-staker terminal migration path instead.

At minimum, emit a per-user shortfall event so the loss is never silent.

### Proof of concept

A validated, standalone Foundry PoC is provided at `reports/stable-staker/12/poc/PoC_M01_ReinjectionHaircut.t.sol` (`PoC_M01_ReinjectionHaircut::test_M01_reinjectionHaircut_silentlyLosesPrincipal`). It walks a single staker through the full in-place round trip on the project's real `StableStaker` + `InPlaceMigrator` contracts, wiring a strategy that haircuts deposits by 200 bps.

Measured before/after for a 1,000.000000 USDC position at a 200 bps haircut:

| Quantity | Value (USDC, 6 dp) |
|---|---|
| Parked at `migrateOut` | 1,000.000000 |
| Re-credited at `migrateIn` (`userInfo.amount`) | 980.000000 |
| **Silent shortfall (lost principal)** | **20.000000** |
| `migrator.totalParked` after `migrateIn` | 0 (zeroed by full `amt`) |
| Strategy physically holds | 1,000.000000 (delta credited to no user) |

The PoC asserts the user is re-credited strictly less than parked (`credited < parked`), that `totalParked` and the user's parked balance are driven to 0 (so `claimTimedOut` can rescue nothing), and that the strategy holds the full parked principal while attributing only `credited` to the staker.

**Haircut-specificity control.** The Tier-3 control `workspace/stable-staker/test/poc/InPlaceMigratorConservation.t.sol::test_par_conservationHolds_0bps` proves the round trip is exactly principal-conserving at 0 bps (par/idle/1:1 strategy), confirming the loss is caused by the strategy haircut and not by the migration mechanism itself. The companion fuzz test `testFuzz_haircut_conservationAlwaysBreaks` shows conservation breaks for every non-zero slippage in 1–500 bps. This is precisely the "stated assumptions + external requirements" boundary that places the finding at Medium rather than High.
